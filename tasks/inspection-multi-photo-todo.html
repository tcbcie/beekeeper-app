Multiple Photos per Inspection

Status: implemented, awaiting your browser test  ·  Date: 4 September 2026  ·  Doc: to become docs/features/inspection-multi-photo-plan.md

The problem, in your words: “I cannot attach more than one image. Even though it gives me the placeholder to attach a second one. However, if I do so, the first one is gone.”

1. Root cause — three layers, all real

Cause A — the state holds exactly one file

src/hooks/useImageUpload.ts:38-39 holds imageFile: File | null and one imagePreview. handleImageChange (:55-70) reads only e.target.files?.[0] and calls setImageFile(file), which replaces. The <input type="file"> at InspectionForm.tsx:2157-2162 has no multiple attribute, so even multi-selecting in the OS picker yields only file [0].

Cause B — the schema holds exactly one URL

inspections.image_url is a scalar text. There is nowhere to put a second photo. Verified live: 1,757 inspections, 74 with a photo.

Cause C — the phantom second slot (this is the bit that misled you)

In InspectionForm.tsx:2117-2164 the thumbnail and the dashed drop zone are siblings in a flex row. Only the thumbnail is conditional; the drop zone renders unconditionally. So once a photo is attached you get thumbnail + a full “Click to upload or drag and drop” box beside it, which reads exactly like an empty second slot. It is the same single-file handler. Dropping a second photo silently overwrites the first.

2. What we can reuse (this keeps the change small)

  • The inspection-images bucket already exists — public, 50 MB limit — and its storage RLS already grants authenticated insert/update/delete plus public read. No bucket or storage-policy work at all.
  • normaliseStoragePublicUrl (src/lib/storage-url.ts) already exists and is mandated for every stored URL.
  • ImageZoomModal already does zoom, pan and 44px controls; it only needs prev/next added additively.
  • The validated upload (magic bytes, MIME allow-list, 10 MB, MIME correction) already exists in useImageUpload.ts:88-160 — it is simply not the code that runs for inspections today (see D2).

3. Design

D1 — Data model: an array column, with the old column kept as a derived mirror

ALTER TABLE public.inspections
  ADD COLUMN image_urls text[] NOT NULL DEFAULT '{}';

UPDATE public.inspections
  SET image_urls = ARRAY[image_url]
  WHERE image_url IS NOT NULL AND image_url <> '';

ALTER TABLE public.inspections DROP COLUMN image_url;
ALTER TABLE public.inspections
  ADD COLUMN image_url text GENERATED ALWAYS AS (image_urls[1]) STORED;

Why an array and not an inspection_images child table (the diagnosis_images precedent):

text[] columnchild table
New RLS policiesnone — inherits inspections RLS wholesale4, and SELECT must re-derive can_access_hive() through the parent
The ~20 select('*') read sitesget the photos freeevery one needs an explicit join added
User data backup database-export.ts:187exported free by select('*')silently omitted unless registered
Photo orderarray order, no extra columnneeds a sort_order column — no precedent anywhere in this schema
Per-photo captions laterwould need a migrationfree

We are not asking for per-photo captions, so the array wins on every axis that matters. diagnosis_images is a child table because those rows carry description, diagnosis_type and a whole comments table — it is a standalone research gallery, not photos belonging to a parent record.

Why keep image_url as a generated mirror rather than delete it: the audit found 20+ places that read it. As GENERATED ALWAYS AS (image_urls[1]) STORED every one of them keeps working untouched and always shows the first photo — and there is still exactly one source of truth, so the two can never drift. Better still, any write site I miss fails loudly at the database instead of silently diverging.

Verified against the live database on a throwaway probe table, then dropped: image_urls = {a.jpg, b.jpg} → image_url = 'a.jpg'; empty array → NULL; and UPDATE ... SET image_url = ... is rejected with 42P10 / column "image_url" can only be updated to DEFAULT.

D2 — Route uploads through the validated path, and delete the duplicate

src/app/dashboard/records/page.tsx:711-755 is a second, weaker copy of the upload logic — no magic-byte check, no MIME allow-list, no 10 MB limit. It is the copy that actually runs for inspections. Extract the good implementation to src/lib/upload-image.ts, have useImageUpload call it (behaviour identical, its 9 existing callers untouched), and delete the duplicate. Uploading N photos needs a loop over one trustworthy function, so this is on the critical path rather than opportunistic tidying — and it closes a real validation hole.

D3 — Step 4 UI: a thumbnail strip, and no phantom slot

Cap 6 photos. Thumbnails stay 80×80 with the existing zoom badge and red remove button. The drop zone moves below the strip, is relabelled “Add more photos — 3 of 6 attached” once at least one is attached, gains multiple, and disappears at the cap. Selecting more than the remaining allowance keeps the first N and warns. The subscription gate (userHasActiveSubscription) is retained exactly as-is.

D4 — Reading surfaces

  • InspectionCard.tsx:103-124 — first thumbnail, with a +N badge when there are more; tapping opens the gallery at index 0.
  • ImageZoomModal.tsx — add optional images?: string[] and startIndex?: number with prev/next at 44px. The existing imageUrl prop stays and keeps working, so apiaries, varroa checks and diagnosis images are not touched.
  • records/page.tsx:331 — the Inspection → InspectionFormData mapping is an explicit field whitelist. image_urls must be added or photos vanish on every edit. Highest-risk line in the change.
  • Review step InspectionForm.tsx:410 — 'Photograph': 'Attached' becomes 'Photographs': '3 attached', and the hand-synced twin string at InspectionStepper.tsx:60 is updated to match.
  • Dirty-state InspectionForm.tsx:461 — imageFile !== null becomes “any new file staged, or any existing photo removed”.

5. Risks

  • The generated column rejects writes. That is the point, but a missed write site throws at runtime. The audit found exactly one (page.tsx:836, via a {...submitData} spread) — the spread needs an explicit carve-out. I will grep for every image_url write before running the migration.
  • Two tests mock useImageUpload — tests/components/records/inspection-stepped-flow.test.tsx:27-28 and inspection-dirty-state.test.tsx:41-42 (the latter asserts “treats a photograph-only edit as dirty”). Both need updating.
  • Backfill is one-way once image_url is dropped and recreated. Only 74 rows carry a photo; I will snapshot those 74 URLs to a table before the DDL so it is trivially reversible.
  • Offline is unaffected — confirmed there is no write queue, no background sync and no draft persistence for inspections (a File is not serialisable, which is why).

Verified against the live database

  • Migration inspections_multi_photo_image_urls: 1,757 inspections, 74 with photos, 74 mirrors populated, zero backfill mismatches against the snapshot.
  • A rolled-back probe confirmed a three-photo write, clearing to empty, and that a legacy image_url write is rejected.

One security defect I introduced, caught by get_advisors and fixed

I first created the pre-migration snapshot as public._inspection_image_url_backup_20260904. A table in public is exposed through PostgREST and it had no RLS — every account's photo URLs would have been readable by any authenticated caller. Migration move_inspection_image_backup_out_of_public moved it to a new backups schema with USAGE revoked from anon and authenticated. Confirmed after: 74 rows intact, nothing left in public, neither role able to see the schema. It is safe to drop once you are happy in production.

Two defects caught in the QA audit and fixed

  1. Partial uploads were orphaned, and retries duplicated them. If photo three of four failed, the first two were already in the bucket, the save aborted, and nothing would ever have referenced or removed them — then pressing Save again uploaded them a second time. Impossible with one photo; routine with six. The batch now removes anything it uploaded before bailing.
  2. Files were only validated at save. A too-large or non-image file was accepted into the strip and only rejected at the end, after the form was filled in. Validation now runs when the photo is picked, naming the offending file inline.

Second QA pass — four more defects, all mine, all fixed

  1. Critical: side effects inside React state updaters. useStagedPhotos created and revoked object URLs inside setStaged(prev => ...). Updaters must be pure and React re-runs them (always in StrictMode, and whenever a concurrent render is discarded). Each replay leaked a blob URL per photo; a replayed removal could revoke a URL belonging to surviving state, leaving a permanently broken thumbnail. The hook now keeps the ref authoritative and does all URL work outside the updater.
  2. High: the six-photo cap could be breached. Making the pick handler async for pick-time validation meant two picks could be in flight, both reading the same stale slot count. The cap is now enforced inside the hook against its own synchronously-updated list.
  3. High: orphans on any post-upload failure. The first pass only cleaned up when the upload loop failed — a database error or a rejected optimistic update still orphaned the photos. Cleanup now runs on every failure path, guarded by a recordSaved flag so it can never delete photos a saved inspection already references.
  4. Medium: the viewer could lock page scroll with nothing on screen. ImageZoomModal set body.overflow = 'hidden' before the early return that renders nothing, leaving the page unscrollable and undismissable. Now conditional. Also guarded % 0 in next/previous and memoised the gallery, which was re-parsing a URL per photo on every mousemove during a pan.

Two findings recorded and deliberately not changed: the ~28px remove button (your design call — see below), and a negligible sub-millisecond window where the saved-photo count could leave the cap off by one.

Security Batch 6: Database Rules (DB-04, DB-07, DB-08, DB-10, DB-11, DB-15)

Status: Done 17/10/2026; tested by you, committed and pushed. Findings: six Medium database findings from the Phase 1 audit.

Keep out of git until shipped: the repository is public and these holes are open. The plan and todo are committed together with the fix.

What I found (live database, checked 17/10/2026)

IDProblemWho uses it in the app
DB-04
  • The public trace functions (/trace/… and /j/… jar pages) send the apiary's exact coordinates to anyone, even when "share location" is off. The page only blurs them in the browser, with an offset anyone can reverse.
  • Separately, a "public batches" rule lets anyone without a login list every public batch row and its trace code straight from the table.
  • Both public pages use only the functions, never the table.
  • One catch: when you create a batch, the app reads other users' public batch codes to pick the next free L-YYYY-MM-NNN number. That number must be unique across all users. Other users' private batches are already invisible to that read, so collisions can already happen today.
DB-07When editing, a user can move their own inspection, feeding, harvest, varroa check, treatment, bench or hive into someone else's hive or apiary. The edit rules check only "it's mine", while the create rules also check access to the hive. The same gap exists in three related places: linking a harvest to a honey container (any harvest ID is accepted), GDD records (any apiary), and a hive's apiary.The record edit forms let you change the hive, which is legitimate between your own and team-shared hives. Nothing in the app moves a bench to another apiary.
DB-08The account reactivation request (no login) tells anyone whether an email belongs to a deleted account, and returns its user ID./reactivate only reads success and message.
DB-10Any logged-in user can add, edit or delete terminology entries. Hive history accepts a row for any hive, from anyone logged in.Terminology is edited only in Settings, which only power users and admins can open. History rows are added only for a hive the user has just created.
DB-11Every QR tag (code, hive, nuc, label, owner) can be read by anyone, without a login.Scanning happens under /dashboard, so it always needs a login. Tag pages read your own tags, team-shared tags, and tags on hives you can see.
DB-15Any logged-in user can publish a changelog entry on the About page.Only the CLI script writes it, using the secret key. No page in the app writes it.

The data check found no existing record that the new rules would block: only four inspections fail it, and those belong to team members on hives that were later archived, which they can't see anyway.

Plan: one database migration, plus one small code change

A. DB-07: edits must stay within hives and apiaries you can access

In the edit rules (WITH CHECK) for inspections, feedings, harvests, varroa_checks and varroa_treatments, add the same can_access_hive(hive_id) check the create rules already use. yard_benches gets can_access_apiary(apiary_id).
hives edit: the new apiary must be one you can access (or none). Owners and team members keep their current edit rights.
gdd_records create and edit: the apiary must be one you can access (or none).
container_harvests: you may only link a harvest you can see. The rule just checks the harvest exists for you, so the harvest table's own access rules decide.

B. DB-04: public trace pages

get_public_batch_info returns coordinates only when the apiary's "share location" is on. Even then it sends the same approximate point the community map already shows (same secret seed, same 5 km radius). Using one point everywhere means nobody can combine two different blurred points to work out the real spot. The page code stays as it is.
Remove the "anyone can read public batches" table rule. The public pages keep working through the functions.
New next_batch_code(date) function that finds the next free number across all users without revealing anything else. src/lib/batch-code.ts calls it instead of reading the table. This also fixes the existing collision when another user's batch is private.

C. DB-08, DB-10, DB-11, DB-15

DB-08: request_account_reactivation always returns the same success message ("If a deleted account exists for this email, your request has been sent to an administrator") and no user ID. One pending request per account is already enforced, so repeats add nothing.
DB-10: terminology stays readable by logged-in users. Adding, editing and deleting is limited to power users and admins, which matches who can open Settings today.
DB-10: hive_configuration_history insert requires changed_by to be you and the hive to be one you can access.
DB-11: qr_tags is readable only when logged in, and only for your own tags, tags shared with your team, and tags on hives you can access. Scanning a team-mate's tag on a shared hive still works.
DB-15: changelog: drop the "any user can create or edit" rules. The admin rule and the CLI script (secret key) stay.

Batch 35: Records and Hives

Status: Implemented 23/10/2026, waiting for your test. This is Phase 2 fix batch 22. It covers the open Medium findings in hives (C3-05, C3-11, C3-13) and in records and tasks (C4-08, C4-09, C4-12, C4-16, C4-20). Two agents checked each finding against the code and the live database, and I re-checked the key facts.

A. Varroa checks never create their treatment task: C4-08

When a varroa check passes the action threshold, the app is meant to add a "Treat hive X for varroa" task for the next day. It has never worked: the task is saved with the category "Treatment", but the database only accepts lowercase "treatment", so every insert is refused, and the failure isn't checked. 30 checks have passed the threshold, and 0 tasks exist.

The task is saved as an all-day "treatment" task. If it can't be saved, you get the same warning the inspection follow-up tasks show.
Editing a check so it newly passes the threshold also creates the task. Before, only new checks did.
The description no longer says "Infestation rate: undefined%", and it shows natural mite drop as mites per day, not a percentage.
The 30 missed tasks are not created after the fact. They date back to 13/09/2026 and earlier, so they would all appear as overdue at once.

B. Tasks list: C4-09

Old unfinished tasks disappear: the list only loads tasks from the last 12 months, so an unfinished task drops off the list once it is a year old. 124 overdue tasks will start dropping off from late November 2026. Now unfinished tasks always load, and finished ones keep the 12-month window.
The 1,000-task cap: the list is sorted oldest first and cut at 1,000, so a busy account would lose its newest tasks first. The busiest account has 275 today. Now the list loads in pages of 1,000 until everything is in.

C. Forms: C4-12, C4-20

C4-12, a form reset while you work: the photo loss itself was fixed in batch 14. Three smaller resets remain:
  • Opening a record from a shared-hive link could run twice and wipe photos you had just added. Each link is now handled once.
  • When the hive list reloads, the inspection and varroa check forms put the page's hive filter back over the hive you picked. In the inspection form, that also cleared your brood, frames and super values. Now a hive is only preselected while the form has none.
  • The varroa check form overwrote a Days value you had typed when its list reloaded. Now it only fills an empty field.
C4-20, "unsaved changes" when you changed nothing: the inspection and treatment forms fill in some values for you, such as the hive, frames, scale weight and weather. Those fills counted as your edits, so closing an untouched form asked about unsaved changes. Now automatic fills on an untouched form become part of its starting point. Anything you have changed still counts.

D. Hives and scales: C3-05, C3-11, C3-13

C3-05, wrong "Last changed by": any save of a hive, even just its notes, stamped it as a configuration change by whoever saved it. The check compared the saved configuration with the form's copy, and their fields are in a different order, so they never matched. 98 hives have a stamp newer than their last real configuration change. Now both sides are built the same way before comparing. The configuration history itself was already correct.
C3-11, one scale on two hives: assigning a scale to a hive never took it off the hive it was on. The screen even shows "Currently assigned to Hive X", but it doesn't move it.
  • Assigning a BEEP or Wolf scale now takes it off your other hive first, so it moves.
  • The database refuses the same scale on two hives in one account. No account has a duplicate today. The demo copy account has the same scales as the original, which stays allowed.
  • Errors are shown properly instead of a generic message.
C3-13, failures remembered as "nothing": the scale cache was fine; the problem is the bloom forecast on the dashboard weather row. If a lookup failed, it was remembered as "no blooms" for up to 24 hours, so predicted and confirmed blooms stayed empty all day. Failures are now not remembered, so the next visit tries again.

E. Closed without a change: C4-16

"A deleted treatment leaves its reminder behind": not real. A treatment reminder is a task linked to the treatment, and the database deletes it with the treatment. On the live database: 0 reminders left over from deleted treatments. I'll record this in the register.
Database changes: one migration, applied through MCP and saved in supabase/migrations/. It adds two indexes: one scale per hive within an account, for BEEP and Wolf separately. Both build cleanly on today's data. I'll also remove two lines from the configuration history trigger that never had any effect. I'll run the security advisors afterwards.

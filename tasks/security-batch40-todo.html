Batch 40: Teams, Queens and Tools

Status: Implemented 24/10/2026, waiting for your test. This is Phase 2 fix batch 27. It covers the open Medium findings in chunk 6 (teams, rearing groups, queens: C6-10, C6-16 to C6-19) and chunk 8a (Tools: C8a-05 to 07, C8a-13, C8a-16). Two agents checked each finding against the code, and I re-checked the key lines. No database change.

A. One team's details under another: C6-10

Apiary teams: tap "View Members" on team A, then team B. A big team A can answer last, so A's members, invitations and apiaries appear under B. B's Remove buttons then act on A's members, because each removes from the member's own team. Opening "Invite" or sharing an apiary for another team causes the same mix-up. Now only the latest team's answer is used. Each list belongs to the team on screen, and the spinner follows the right team.
Rearing groups: the same flaw. The worst case is Transfer, whose New Owner list first shows the previous group's members (the database refuses a wrong owner, so it's a confusing error, not a wrong transfer). Same fix, and Transfer and Invite now show a spinner while members load.

B. Failed loads shown as "nothing here": C6-16

A failed load currently shows the normal empty screen, often with an invitation to create something. These now show "Couldn't load …" with a Try again button (or keep what was on screen):
  • Queens list: shows "No Queens Found, Add Queen". A failed hive lookup marks every queen's hive "N/A".
  • Queen assignment history: shows "No history yet, Add entry", which invites duplicates.
  • Lineage: shows "No lineage data found".
  • Rearing group report: shows "No rearing data for October 2026". This feeds official NIHBS returns.
  • Rearing groups list and details: shows "You haven't joined any groups" and "No members".
  • Apiary teams list, team details and team apiaries: shows "Create Your First Team", "No members yet" and "No apiaries shared yet". Team error messages also said "Unknown error", because Supabase errors aren't plain JavaScript errors; they now show the real message.

C. Sizes for 50+ eyes: C6-17 to C6-19

79 places in 12 files across teams, rearing groups, queens, lineage, compare and the NIHBS return go to 48px. They are fields, icon buttons (34px today), 44px and 40px caps, chips and checkboxes. 16 fields go from 14px to 16px, including the NIHBS return's number boxes, which also stops iPhones zooming in. Class changes only.
Tabs everywhere (NavTabButton): the shared tab button is 38–46px tall, used for the queen detail tabs and most tab rows in the app. Adding the 48px minimum to it fixes every tab row at once, but every tab row grows a little taller. Done (you approved).

D. Tools: C8a-05, C8a-06, C8a-07, C8a-13

C8a-05, dead code: 8 old tool components and the 2 helper files only they use, about 2,500 lines, are never imported anywhere, not even by tests:
  • Apiary location analyser, association finder and hive strength analyser.
  • Honey super calculator, queen productivity tracker and seasonal task generator.
  • Treatment schedule planner and varroa drop calculator.
They're deleted. Nothing you use changes.
C8a-06, GDD tracker's bloom records: working out a bloom's GDD fetches the weather archive without checking the answer, and with no time limit. A future date (allowed today), a busy weather service or an error page leaves the record saved with no GDD and a vague message, or a spinner that never stops. It now uses the app's shared archive fetch, which checks the answer, gives up after 15 seconds and uses the same GDD formula. The bloom date can't be in the future.
C8a-07, silent failures: deleting a GDD record or switching its sharing does nothing visible when it fails. It now says whether it worked.
C8a-13, QR download clean-up: if a QR download fails part-way, a hidden link or file reference is left behind. Clean-up now always runs. Honey Traceability's batch QR download had its own copy with no error handling, so a failure did nothing. It now uses the shared download and tells you if it fails.

E. Closed without a change

C8a-16 (TBR planner is 1,011 lines): its logic already lives in a hook and a model file. What's left is display code, and it's already loaded on demand. Splitting it would add hand-offs between files without making it any safer.

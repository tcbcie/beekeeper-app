Virgin Queen nucs not counted as “hatched”

Symptom

Batch TQRQB_RZ02 has 5 confirmed Virgin Queen nucs, but the Grafting Batch table shows Hatched = “-”, and the NIHBS report omits them too. Batch TQRQB_RZ01 (4 virgins) reports Hatched = 4 correctly.

Root cause

The hatched/mated counters detect emergence only from the timestamp queen_emerged_at / mating_confirmed_at on the linked mating_nucs row (or graft status emerged/mated). They never look at the nuc’s own status field.

BatchNuc statusqueen_emerged_atCounted?
RZ01virgin (set via inspection)setYes
RZ02virgin (set directly on form/bulk)NULLNo

RZ02’s nucs were promoted straight to virgin without an inspection that stamps queen_emerged_at, so they are invisible to the counters even though “virgin” means the queen has emerged.

Fix

In all three hooks, add status to the mating_nucs select and treat nuc status as an additional signal:

  • virgin, mating, laying → hatched
  • mating, laying → mated

Review

Root-cause fix applied in three count hooks plus a shared constant; one-off data backfill for the affected batch.

  • graftConstants.ts: added shared NUC_HATCHED_STATUSES (virgin/mating/laying) and NUC_MATED_STATUSES (mating/laying) to avoid duplicating the lists.
  • useBatchGrafts.ts, useNIHBSReport.ts, useRearingGroupReport.ts: each now selects status from mating_nucs and treats those statuses as hatched/mated signals, in addition to the existing timestamp / graft-status signals.
  • Backfill: recomputed RZ02 from live data with the exact new definition (accepted 9, hatched 5, mated 0) and updated the stored queens_hatched = 5. The same formula reproduces RZ01 = 4 unchanged, confirming no regression.
  • Docs: updated the count definition in nihbs-monthly-returns.md.

Quality audit (no test code added)

  • Null safety: status checks are guarded (n.status && …includes(n.status)) so a null status can’t throw.
  • Backfill matches the writer: the SQL mirrors useBatchGrafts semantics (sold grafts use distribution data only, early-return) — consistent with the hook that persists the column, and scoped with IS DISTINCT FROM so it is idempotent.
  • No double counting: signals are aggregated into Set<graft_id>, so multiple nuc rows per graft collapse to one.
  • Grafting Batch table: reads the stored column; RZ02 is now correct via backfill, and any future batch re-persists on next open.

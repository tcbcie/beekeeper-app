Per-Jar-Size QR Codes

Problem

A batch can now hold multiple jar sizes (e.g. 227 g and 454 g). There is a single QR / trace link per batch, and the scanned public page lists all net weights — so a consumer holding a 227 g jar can't tell which figure applies to them.

Design — deep-link by net weight (no schema change)

Keep the one trace_code per batch. Generate one QR per jar size, each pointing to /trace/{code}?w={net_weight_g}. The public page reads the w query param and, when it matches a jar, shows only that jar's net weight as the hero figure.

Why key on net weight, not the jar row id: editing a batch re-creates its batch_jars rows (the transactional replace_batch_links does delete+insert), so jar UUIDs change on every edit. A printed QR encoding a UUID would break after the next edit. Net weight (g) is stable and is exactly the consumer-facing figure, so it is the correct, durable key. If the user changes a jar's net weight, the old sticker is stale anyway (the jar's weight genuinely changed).

Behaviour

  • Scanned with ?w=227 → hero "Net Weight: 227 g"; other sizes not shown (no ambiguity).
  • Scanned with no param (or a non-matching weight) → current behaviour: list all sizes' net weights.
  • Everything else on the page (origin, story, dates, map, feedback) is identical regardless of w.

UI — edit form & QR modal

  • When a batch has 2+ jar sizes with a net weight: render one labelled QR per size (e.g. "227 g jar", "454 g jar"), each linking to its ?w= URL.
  • When a batch has a single jar size: keep the current single QR (with its ?w= so it's consistent), exactly as today.
  • QR modal (the qrBatch download view): same — list per-size QRs, each with its own Download PNG button. The download handler is generalised to take the SVG element id + filename (currently hard-codes a single qr-code-svg id).

Files

  • get_public_batch_info RPC — unchanged (already returns jar_weight_g per jar; we match client-side).
  • src/app/(trace)/trace/[batchCode]/page.tsx — accept searchParams.w; scope the Net Weight hero when it matches.
  • src/components/tools/TraceabilityTool.tsx — per-jar QR rendering in the edit-form box and the qrBatch modal; generalise downloadQrCode; add a jarTraceUrl(code, grams) helper.
  • docs/features/honey-traceability.md — document per-jar QR deep-linking.

Tasks

1. Public page: read ?w=, scope Net Weight hero to the matching jar
2. getTraceUrl(code, grams?) + jarsWithWeight() helper + generalise downloadQrCode(elementId, filename)
3. Edit-form trace box: per-jar QRs when 2+ sizes (single otherwise)
4. qrBatch modal: per-jar QRs + per-jar download
5. Update documentation
6. User verifies build & tests

Review

  • Public page (page.tsx): now reads searchParams.w (validated as digits). When it matches a jar's jar_weight_g, the Net Weight hero shows only that figure; otherwise the full multi-size list (unchanged).
  • Helpers: getTraceUrl(code, grams?) appends ?w= when a weight is given; jarsWithWeight(batch) returns jar rows that carry a net weight; downloadQrCode(elementId, filename) now targets any SVG by id (was hard-coded to one).
  • Edit-form box: 2+ weighted jars → one labelled QR + link per size; single/none → original single trace link (now carrying its ?w=).
  • QR modal: 2+ weighted jars → stacked per-size QRs each with its own Download PNG (unique SVG ids, scrollable); single/none → unchanged single QR.
  • No DB/schema change — deep-link keyed on net weight (g), durable across the delete+insert jar churn on edit.

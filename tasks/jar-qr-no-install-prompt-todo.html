No App Install Prompt on Jar QR Pages

Status: plan, awaiting approval  ·  Date: 29 October 2026

Your instruction: a customer who scans the QR code on a jar is prompted on their phone to install the app, which we do not want.

1. Root cause

Our own amber “Install HiveCraic” banner is not the culprit — since batch 47 it only shows under /dashboard (src/components/InstallPrompt.tsx:108).

The prompt the customer sees is the browser’s own install offer (Chrome’s “Install app” / Samsung Internet’s home-screen icon). A browser offers this on any page that links a web-app manifest. The root layout links /manifest.json on every page, including the public jar pages:

// src/app/layout.tsx:49  (root layout → applies to every route)
manifest: "/manifest.json",
Scan jar QR → /j/{code} (public, (trace) group) ↓ root layout adds <link rel="manifest"> ↓ phone browser: "this site is an installable app" ↓ customer sees "Install HiveCraic" ← unwanted

Chrome no longer needs a service worker for this, so the manifest link alone is enough to trigger it.

2. Fix (one line of real change)

Tell Next.js not to emit the manifest link for the public traceability route group. Next merges metadata per segment, and a child setting manifest: null removes the parent’s link (checked in node_modules/next/dist/lib/metadata/resolve-metadata.js: target[key] = source[key] || null). Both public scan pages (/j/{code} and /trace/{batchCode}) sit under src/app/(trace)/layout.tsx, and neither page sets manifest, so the layout’s value holds.

// src/app/(trace)/layout.tsx
import type { Metadata } from 'next'

// Jar buyers are not app users: no manifest means the phone browser does not offer to install the app.
export const metadata: Metadata = {
  manifest: null,
}

What stays the same: the dashboard, login and every other page keep the manifest, so beekeepers can still install the app exactly as before. The payment link and the page content are untouched.

QA audit (qa-engineer)

  • No Critical, High or Medium findings.
  • Type check: manifest?: null | string | URL in Next’s Metadata type, so null is the supported way to remove it. npx tsc --noEmit: no errors. ESLint on the file: clean.
  • Inheritance: neither /j/[code] (static metadata) nor /trace/[batchCode] (generateMetadata) sets manifest, so the layout’s null holds for both.
  • Navigation: the only links on these pages are back to /j/… (lot finder) and the external payment link, so a buyer never lands on a page that still carries the manifest.
  • ⚪ Low, left as is: the service worker still registers on these pages (ServiceWorkerRegistration.tsx), and the iOS apple-mobile-web-app-capable meta still renders. Neither triggers an install offer on its own — iOS never prompts, and Chrome needs the manifest — so changing them would widen the change for no gain.

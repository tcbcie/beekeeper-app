Batch 23: Faster Page Loads (Request Chains)

Status: Done 22/10/2026. Tested by you; committed and pushed. This is Phase 2 fix batch 10; the rest of the request-chain work is batch 24.

Many pages wait for one database request to finish before starting the next, even when the second doesn't need the first's answer. Each wait is a full round trip to the server, which is noticeable on mobile data. Two pages also load all their data twice. The fixes regroup existing queries with Promise.all. Each query and its error handling stay as they are; only the waiting order changes.

A. Pages that load everything twice

Queen rearing (batches) (C5b-10): setting the user id gave the fetch functions new identities, which re-ran the start-up effect, so about 9 requests ran twice. Fix: the effect depends on [router] only, the same pattern as the hives list.
Queens (C6-05): the same cause, about 11 requests twice. Same fix.
Queen rearing tab bounce (C5b-11): changing tab briefly switched back to the old tab before the address caught up, which mounted the tab twice and fetched twice. Fix: the tab follows the address only.

C. Lists too long for the web address (queen report error)

A breeder queen with hundreds of daughters made the sister-ratings request so long that the server refused it (C6-15). New small helper src/lib/supabase-chunk.ts → fetchInChunks(ids, query): it splits long id lists into groups of 100, runs them together, and merges the results. Where the old query used order or limit, the merged result is re-sorted and re-cut, so averages and "latest" values stay correct.
Used at the five places that can grow with the account: queen sister ratings, the queens list's hive lookup, and the queen tracker's weights, source queens and mothers.

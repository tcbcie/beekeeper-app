Security Batch 11: API Low Findings (API-09 to API-17)

Status: Done 18/10/2026; committed and pushed at your request.

What's open

IDProblem
API-09A role change sends the target's whole profile row back to the admin's browser (including scale tokens and the Stripe customer ID). The page never uses it. The "can't demote the last admin" check can be beaten by two admins demoting each other at the same moment, and it counts deactivated admins. The error response also includes internal error text.
API-10An association code's maximum uses is checked at checkout but only counted after payment, so simultaneous checkouts can go over the limit. Each extra use still pays €12; the loss is the discount.
API-11The admin "add from URL" fetcher (knowledge base and news) checks the address text only. It follows redirects without re-checking them, never resolves DNS, and misses IPv6, most of 127.x, 0.x and 100.64/10. An admin-supplied URL could therefore reach internal addresses. Admin-only.
API-12About 20 places return raw error text to the browser: BEEP and Wolf connect, devices, scales and disconnect; the admin knowledge-base routes (which also return the caller's role on a 403); admin news; update-user-role; the storage clean-up cron; and Google's error text in geocoding.
API-13/auth/verify passes type and redirect_to straight to Supabase. Whether that becomes an open redirect depends on the Supabase redirect allow-list, which isn't visible from the repo.
API-14beep/connect can be used to test BEEP email and password pairs from our servers: there's no attempt limit, and BEEP's own error message is echoed back.
API-15The Stripe webhook activates on "checkout completed" without checking payment_status === 'paid'. It's safe today (card only), but it would break if a delayed payment method were ever added.
API-16beep/disconnect, wolf-waagen/disconnect, geocode and news/search don't refuse deactivated accounts.
API-17The sign-in callback logs the profile's email and original email.

Plan

API-09: return only { success }. A database trigger refuses any change that would leave no active admin, locked so simultaneous changes are checked one at a time. The route's own check stays for the friendly message. No more error details in the response.
API-10: the code counter (increment_code_uses) locks the code and reports when the payment pushed it over its limit. The customer has already paid €12 in good faith, so the subscription is still honoured. The overrun is recorded in the admin audit log (association_code_over_limit) so you can see it.
API-11: the fetcher follows redirects itself (at most 5), re-checking every hop. It resolves the hostname and refuses private, loopback, link-local, carrier-grade NAT and IPv6 private or loopback addresses. It also refuses raw IPs written in decimal or hex.
API-12: every listed route returns a short, plain message ("Could not connect to BEEP. Check your email and password.", "Failed to fetch scales" and so on). The details go to the server log only. The knowledge-base 403 no longer includes the role.
API-13: type must be one of signup, recovery, magiclink, email_change or invite. redirect_to must be on our own site; otherwise it's dropped and Supabase uses the default. You: check that the Supabase Auth → URL Configuration "Redirect URLs" has no wildcards such as *.vercel.app.
API-14: BEEP and Wolf connect allow 5 attempts per user per hour (the shared limiter), with a generic failure message.
API-15: the webhook only activates when payment_status is paid; anything else is logged and acknowledged without activating.
API-16: add the deactivated-account check to those four routes.
API-17: remove the profile log line.
Verify: rolled-back tests for the two database changes, type-check and lint, qa-engineer, docs and the findings register.
You: build and test: change a test user's role; connect or disconnect BEEP or Wolf (and a wrong password); add a knowledge-base article from a URL; sign-in email link or password reset. Then commit and push.
Confirmed by you: honour and log. when two people pay with the last remaining use of an association code at the same moment, the second one has already paid €12. I suggest we honour it and record it in the audit log, rather than refunding or charging the difference automatically. OK?

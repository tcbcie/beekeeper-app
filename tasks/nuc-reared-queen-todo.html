Mark, Number & Distribute a Queen Reared in a Mating Nuc

Status: awaiting your approval  ·  Date: 29 August 2026

The problem, in your words: where a graft goes directly into a mating nuc, and a queen subsequently emerges and mates, there is no way to (a) mark that queen, (b) assign a number to her, or (c) distribute her.

1. Root cause

Confirmed against the live database and the code. There are two separate causes, not one.

Cause A — a mating nuc has nowhere to record the queen reared inside it

mating_nucs.queen_id looks like it should hold the nuc's queen. It does not — it holds the mother/breeder queen. The nuc setup form labels it "Grafted from" (MatingNucsTab.tsx:1129-1143), it is auto-filled from the selected cell's breeder (MatingNucsTab.tsx:1160-1161), and the nuc card renders it as "Breeder Queen: …" (MatingNucsTab.tsx:1672).

Verified across all 142 rows in mating_nucs: not one queen_id points at a queen with source_graft_id set. Every one points at a breeder. On your nuc 198, queen_id → UGX1.4, queen_role = 'breeder', born 2025-05-25 — the mother, not the daughter that emerged on 27/07/2026.

There is therefore no column anywhere in the schema for the daughter queen reared in a nuc.

Cause B — every queen action is gated on graft_id, which is NULL for a direct graft

Nuc 198 has graft_id = NULL and batch_id = NULL (no batch was chosen at setup, so the "Cell/Graft" picker never appeared). Every queen-level action is hidden behind that column:

This exactly reproduces your screenshot: nuc 198 is status mating (labelled "Mated", MatingNucsTab.tsx:126-128), which is in NUC_DISTRIBUTABLE_STATUSES = ['virgin','mating','laying'] — so the only reason the Distribute icon is missing is the null graft_id. Likewise the expanded panel offers only "Add Inspection", with no Mark Queen button.

And even where marking is allowed, it writes the number to batch_grafts.queen_number (NucInspectionPanel.tsx:400-407) — a table whose batch_id is NOT NULL. A batch-less nuc has no row there to write to.

2. What we can reuse (this keeps the change small)

The hard part is already built. The "distribute a registry queen" feature (docs/features/distribute-registry-queen.md) added a second, graft-free source to graft_distributions:

-- already in production
graft_id / batch_id  →  nullable
source_queen_id      →  uuid REFERENCES queens(id)
CHECK: exactly one source (graft pair XOR source_queen_id)

There are already 2 live rows using it (distribution_type = 'mated_queen', graft_id IS NULL). DistributeGraftModal already accepts a sourceQueenId prop, and create_queen_for_distribution / promote_distributed_queen_on_mating already handle the queen-sourced branch — including the Queen Ledger, CRM order linking, mating confirmation, recipient queen minting and the failure report.

So requirement (c) needs no new distribution machinery at all — only a real queens record to point at, plus the two gates relaxed.

3. The plan — three small steps

Step 1 — one new column

Applied via the Supabase MCP connection (no SQL file, per project convention — will be noted in memory alongside the other live-DB-only objects).

ALTER TABLE mating_nucs
  ADD COLUMN reared_queen_id uuid REFERENCES queens(id) ON DELETE SET NULL;

CREATE INDEX mating_nucs_reared_queen_id_idx
  ON mating_nucs (reared_queen_id) WHERE reared_queen_id IS NOT NULL;

queen_id keeps its current meaning (the breeder). Nothing existing changes meaning, so no data migration and no risk to the batch-driven flow.

Step 2 — mint the queen on demand; marking is optional

Revised after review. The first draft made marking the step that minted the queen. That is wrong: marking must stay optional — you may have an unmarked virgin you want to distribute, and requiring a marking first would block a legitimate sale. Minting and marking are now separate.

One new RPC, idempotent and atomic, called by both actions. All its marking parameters are optional, so it can mint a bare, unmarked, unnumbered queen:

ensure_nuc_reared_queen(
  p_nuc_id         uuid,
  p_queen_number   text DEFAULT NULL,
  p_marking_colour text DEFAULT NULL,
  p_marked_date    date DEFAULT NULL
) RETURNS uuid
  • Mark Queen → calls it with number/colour/date.
  • Distribute → calls it with no optional args, then opens the modal with the returned queen id. An unmarked queen distributes perfectly well.
  • Either action can come first, or marking can be skipped entirely.
  • Guarded on nuc status ∈ virgin | mating | laying — before there is a virgin there is no queen to mint. Raises otherwise.
  • If reared_queen_id is already set → UPDATE that queen's number/colour.
  • Otherwise INSERT a queen and link it:
    • mother_id = the nuc's queen_id (the breeder) — this is what gives the new queen her lineage
    • birth_date = queen_emerged_at (falls back to setup_date)
    • mated_date = mating_confirmed_at
    • status = active if mated, else virgin; queen_role = 'production'
    • subspecies / lineage inherited from the mother
    • source = 'Own Breeding', matching the existing ensure_reared_queen_record RPC
    • marking_color from the emergence year — note queens has no marked boolean, only a colour; marked-ness stays on mating_nucs.queen_marked_at
  • Duplicate number guard: raise a clear "A queen numbered X already exists in your register" — exactly what ensure_reared_queen_record does. There is no DB uniqueness on queens(user_id, queen_number); it is an app convention, and silently minting a second queen "53" would be worse than an error.
  • Then stamps mating_nucs.queen_marked_at.
  • SECURITY DEFINER, search_path = public, GRANT EXECUTE TO authenticated — per the two standing gotchas in project memory.

UI: in NucInspectionPanel.tsx, show the existing Mark Queen button when there is a graft or the nuc has reached virgin/mating/laying. The existing inline form (auto colour + Queen # input) is reused as-is; only the save handler branches: graft present → today's behaviour, unchanged; no graft → call the new RPC. (handleMarkQueen already tolerates a null graft at :401-409, so this is a smaller change than it looks — the button is simply never rendered today.)

Must fix at the same time — the marking colour. markColour is derived from getQueenColorFromYear(emergenceDate) (NucInspectionPanel.tsx:322), and emergenceDate is passed as nuc.rearing_batches?.emergence_date (MatingNucsTab.tsx:1718) — the batch's date. Nuc 198 has no batch, so the form would show "Unknown" and the queen would be created with no marking colour. Fix: fall back to the nuc's own queen_emerged_at (then setup_date). One-line prop change.

Step 3 — Distribute

Two gates relaxed in MatingNucsTab.tsx:

  • Line 1644 — show the Send icon whenever the status is distributable (virgin | mating | laying) and the nuc is not retired. The nuc.graft_id requirement is dropped: no marking and no graft needed.
  • Line 1793 — when there is no graft, call ensure_nuc_reared_queen(nuc.id) first, then render the same DistributeGraftModal with sourceQueenId instead of graftId/batchId.

Everything downstream — recipient selection, CRM order linking, the Queen Ledger, mating confirmation — works already through the registry-queen path.

4. Resulting flow for nuc 198

Both routes work, and neither depends on the other.

  1. Marking route. Expand nuc 198 → Mark Queen now appears (status is "Mated") → enter #53, the number you had to type into an inspection note as free text → a real queen record is created: mother UGX1.4, born 27/07/2026, mated 27/08/2026, blue.
  2. Distribution route. The Send icon now appears too — whether or not she was ever marked. Distributing an unmarked virgin mints her silently and hands her to the existing registry-queen flow.

Decided — an unmarked queen is numbered Nuc 198

queens.queen_number is NOT NULL, so a queen minted by the distribute route with no marking still needs one. She is minted as Nuc <nuc_number> and that value is overwritten the moment you mark and number her properly. This mirrors the graft flow's existing graft.queen_number || 'Cell #' + cell_number fallback (useGraftDistributions.ts:321). No extra clicks at distribution time.

5. Decisions I have made (tell me if you disagree)

  • CONFIRMED — marking is optional and never a prerequisite. The queen is minted on demand by whichever action happens first. An unmarked virgin can be distributed; a queen can be marked and never distributed; a queen can be neither.
  • CONFIRMED — marking allowed from virgin onward. Before there is a virgin there is nothing to mark, so that is also the floor for minting.
  • CONFIRMED — queen_role = 'production', so she appears in the Queen Register as a normal queen. Promoting her to a breeder node stays a separate, existing action.
  • queen_id is not renamed. It means "breeder" in ~15 places; renaming buys nothing and risks plenty.

  • cell_introduced_at is displayed and exported but never written by any code path.
  • Retire is not hidden for sold nucs (MatingNucsTab.tsx:1662), contradicting docs/features/lock-sold-nuc-cards.md:12.

  • "Breeder Queen" is resolved differently on the card (mating_nucs.queen_id) than in NucReportsTab.tsx:156 (batch_grafts.breeder_queen_id) — the two surfaces can disagree.
  • Stale docs: mating-nucs.md:26 omits graft_introduced, and both it and nuc-inspection-status-sync.md:13 claim dead/missing leaves the graft unchanged, but NucInspectionPanel.tsx:212 sets it to failed.
  • You cannot distribute a queen to yourself unless the batch belongs to a rearing group you are in. search_users_for_distribution excludes auth.uid(), so the "App User" tab can never return you; only the "Group Member" tab can. 9. Why the queen must exist independently of both marking and distribution

Worth stating explicitly, because it inverts how the app works today.

There are exactly three code paths that can create a queens row: the manual Add Queen form, create_queen_for_distribution (fires only when a distribution is saved and a recipient app user is set), and ensure_reared_queen_record (whose only UI lists grafts that already have a distribution row).

So today the app can only say "distribute in order to create the record" — never "create the record, then decide what to do with her."

That is the deeper reason your nuc 198 queen does not exist anywhere: she was never distributed, so nothing ever minted her.

The fix is not to move that trigger onto marking — that would just swap one mandatory gate for another, and marking is genuinely optional. Instead the queen becomes real as soon as she is real: once a virgin has emerged in the nuc, any action that needs a queen record mints one. Marking, numbering and distribution then all become independent, optional things you can do to her, in any order or not at all — which is how it works at the hive.

Two defects caught and fixed during the audit

  1. The PostgREST embed break. Adding a second FK to queens made every bare queens(queen_number) embed from mating_nucs ambiguous — five call sites that would have failed at runtime, three of them in the AI tools. All now name their constraint explicitly.

Nuc card header shows “Cell #6” after the queen has a number

Problem

Nuc 124 (batch TQRQB_RZ06) has queen number 48, but its card subtitle still read TQRQB_RZ06 · Cell #6 · Breeder Queen: 1B · Mating Site: AP03 - Stephen. Once a queen has her own number, the cell she was grafted from is no longer the useful identifier.

Root cause

src/components/batches/MatingNucsTab.tsx:1632 swaps “Cell #N” for the queen’s identity only when the marked flag is set. But queen_number and queen_marked were written independently — the Queen Tracker’s number field (updateGraftQueenNumber, src/hooks/useBatchGrafts.ts) wrote only the number. Live data confirmed all three combinations existed:

StateRows beforeRows after
Numbered + marked5059
Numbered, not marked90
Marked, no number (valid)1111

Nuc 124’s graft was one of the nine: queen_number = '48', queen_marked = false.

Decision

Rico chose to treat “has a number” as implying “is marked” — a queen can only carry a number because someone marked her to put it there. So this is fixed as a data invariant, not as a display special-case. The reverse does not hold: a queen marked with colour alone, and no number, stays valid.

With the flag corrected, the existing subtitle logic renders the right thing on its own, so MatingNucsTab.tsx needed no change at all.

update batch_grafts set queen_marked = true
where queen_marked = false and nullif(trim(queen_number), '') is not null;

Nine rows corrected across all accounts; verified numbered_not_marked = 0 afterwards.

2. Write path — src/hooks/useBatchGrafts.ts

Setting a number now sets the flag with it. Two hardening points came out of the audit: the value is trimmed at this chokepoint (so a whitespace-only entry cannot claim the queen is marked), and clearing the number omits queen_marked from the payload entirely rather than re-sending the locally held value — my first draft wrote it back, which could clobber a change made in another tab. 

const updates = trimmed
  ? { queen_number: trimmed, queen_marked: true }
  : { queen_number: null }

3. Unmark path — src/hooks/useBatchGrafts.ts

The audit caught a hole: the Queen Marked checkbox could be unticked on a graft that carries a number, immediately re-breaking the invariant and reproducing the original bug.

My first attempt disabled the checkbox; Rico chose the other direction — keep it clickable and clear the number on unticking. So QueenTrackingSection.tsx is back to its original state, and the enforcement lives in the hook instead, in both updateGraftQueenMarked and the bulk handleTableBulkQueenMarked.

The number is not recoverable from anywhere else, so both paths confirm before clearing, and the bulk one reports how many numbers will go: 

Unmarking this queen also clears her number (48). Continue?
Unmarking also clears the queen number on 3 of the 12 selected cells. Continue?

Unticking a queen who was marked with colour alone is unaffected — no number, no prompt. The number input remounts empty on its own, because its key already includes graft.queen_number.

Batch 14: Phase 2 Data-Loss Bugs

Status: Done 19/10/2026. Tested by you; committed and pushed. You chose batch 14 first, so part E moves to batch 15. You said no to dropping push keys from the export. This is Phase 2 fix batch 2.

Four agents checked all 15 findings against the code and the live database (read-only). Every one is real; none was already fixed. They also found three more data-loss bugs next to them (marked new). Each fix is a few lines in the place that causes the bug, with no refactors. The one exception is bulk nuc creation, which needs a database function to be atomic.

Proposed split. Batch 14 is parts A–D, all small app-only changes. Batch 15 is part E, mating nucs, which includes a migration and a data repair. That keeps each test round short. Or say "all in one" and I'll do both together.

A. Records (Records page and Tasks)

C4-01: every refetch put the skeleton back, which unmounted an open record form and silently lost your edits (for example when you change the ownership filter). Fix: delete the setLoading(true) in fetchAllData (useRecordsData.ts:628). The first load still shows the skeleton; later refetches keep the list on screen.
C4-01b (new): the five record forms reset themselves when the hive list or the apiary filter changes, which also wipes the open form and drops a varroa photo. Fix: re-load a form only when the record being edited changes. Remove hives, selectedApiaryId from the four simple forms' effect dependencies. In InspectionForm, skip the reset when initialData is the same object as before (two lines).
C4-03: editing an inspection overwrote its weather with today's, or with nothing if the weather call failed. Fix: fetch and write weather only for new inspections (records/page.tsx:790-836).
C4-04: harvest moisture was shown and editable but never saved. Fix: add moisture_content to the harvest payload (records/page.tsx:1303).
C4-05: editing a task set completed: false and user_id to the editor, so done tasks reopened and a team-mate's edit took ownership of the task. Fix: set those two fields on insert only (tasks/page.tsx:407-444).
C4-06: opening an old inspection reshaped its brood frames to the hive's current boxes. That could wipe the recorded brood total, or drop boxes that have since been removed. Fix: when editing the same hive, the brood box list comes from the inspection's saved boxes (InspectionForm.tsx:1105). New inspections and hive changes work as before.

B. Rearing batches (batch editor)

C5b-01: pressing Enter (or "Go" on a phone) in a queen number, weight or date field, or in any of the four graft modals, submitted the batch form and closed the editor, losing what you typed. Fix: one onKeyDown on the grafts section wrapper (BatchFormSection.tsx:974). Enter in an input there just commits the field. Notes boxes still accept new lines.
C5b-02: the timeline recalculated every date on any change, so manual Acceptance, Cage and Hatch dates never stuck, and saved custom dates were replaced when an old batch was opened. Fix: work out the timeline only when you change the graft date, and for a new batch's defaults. The effect is replaced by a small helper called from the graft date field.
C5b-03: the hatched and mated counts (they feed NIHBS) were saved before distributions had loaded, or after their fetch failed, so they were written too low. Fix: useGraftDistributions also returns an error flag, and the count save waits until distributions have loaded without error.
C5b-03b (new): if the grafts fetch failed, the batch counts were saved as 0. Fix: return after the error toast, as the other two fetches already do (useBatchGrafts.ts:114).
C5b-04: if creating the recipient's queen failed, the error was ignored and the queen went missing while the app said "Distribution recorded". Fix: check the RPC error and show a warning: "Distribution recorded, but the recipient's queen record could not be created." The RPC is safe to re-run, so a retry can't make duplicates.

C. Tools

C8a-01 / C8a-02: with a P&L or Purchases edit form open, clicking Edit on another record saved the first record's values onto the second. Fix: key={record?.id ?? 'new'} on both forms, so they reload for each record (one line each). No other Tools form has this bug.

D. Complete export

C2-03: the complete (SQL) export, both the admin export and the personal one in Settings, left out 10 tables of real data, so a restore would lose them, schema included. Fix: add batch_breeder_queens, batch_jars, crm_customer_credit, crm_customers, crm_order_items, crm_orders, queen_assignments, queen_weights, trace_labels and yard_benches to DATABASE_EXPORT_TABLES. Five system tables stay out on purpose: rate-limit events, the admin audit log, the invoice send log, the storage cleanup queue and Stripe webhook events. The personal JSON/CSV export also gets trace_labels.

E. Mating nucs: moved to batch 15 (see tasks/security-batch15-todo.html)

C5a-01: every time the nuc list loaded, a "self-heal" set grafts back from emerged to in_nuc, so "virgin seen" never stuck. The live data shows the damage: 15 grafts are in_nuc while their nuc says virgin. Fix: the self-heal moves only sealed/caged cells (drop 'emerged', MatingNucsTab.tsx:312).
C5a-01 repair (needs your OK): set those 15 grafts back to emerged, via MCP, after a count check.
C5a-02: saving or editing an inspection applied only that inspection's status, so a backdated "virgin" moved a laying nuc (and its mated graft) backwards. Delete already replays all inspections in date order. Fix: move that replay into one helper used by save, edit and delete. It also:
  • stops if the read fails, instead of resetting the nuc to "setup";
  • never resets a hand-set status on save;
  • breaks same-day ties by entry order;
  • leaves sold grafts alone (3 live nucs are exposed to that today).
C5a-03: bulk nuc creation is four separate writes, so a failure part-way leaves orphan rows, and a retry is then blocked. Fix: one database function, create_mating_nuc_bulk. It runs as the user (RLS still applies), re-checks ownership, graft status and duplicate numbers, and does all the writes in one transaction. The hook makes a single call. Execute is granted to signed-in users only.

Batch 25: Admin, Tools and Exports

Status: Implemented 22/10/2026, waiting for your test. This is Phase 2 fix batch 12 and the last request-chain batch. Three agents explored the admin, Tools/finance and research/profile areas, and the key facts were checked against the live database.

Found while exploring: two exports lose data. The settings export for regular users and the member export on the profile page both read each table without paging. Supabase returns at most 1,000 rows per request, so any larger table is cut to 1,000 rows with no error. The live database already has tables over that size: knowledge base 5,609, changelog 2,397 and inspections 1,888. A busy beekeeper's backup would be missing records. Fixed in part A.

A. Exports (C2-10, plus the 1,000-row data loss)

Shared helper fetchAllRows(client, table, filter?) in src/lib/database-export.ts. It reads a table 1,000 rows at a time, ordered by id, until a short page comes back. batch_breeder_queens has no id, so it's ordered by its key (batch_id, queen_id). This was checked: it's the only one of the 72 tables without id.
Settings export (regular users): 72 tables one after another → 6 at a time, every row. The output keeps the same table order, so restores are unchanged.
Member export (profile page, JSON and CSV): it already loads its tables together. Each table is now read in full.
Admin export route: the 13 schema look-ups run together instead of one after another, and the 72 tables run 4 at a time (pages inside a table stay in order). The output order and error handling are unchanged.
Shared mapInGroups(items, fn, size) moves from Mel's scale tools into src/lib/supabase-chunk.ts, so the exports and the scale tools use the same helper.

B. Admin (C9a-20, C9a-21, C9a-23, C2-15)

Ticket list fallback: 1–2 profile look-ups per ticket → one chunked look-up for all names. The fallback also ignored the status filter (All, Open, ...); it now applies it.
Transfer apiaries dialog: the apiary list and the user list load together instead of one after the other.
Apiary hive counts (admin): one count query per apiary → a single query with an embedded count (hives(count)). There's exactly one link from hives to apiaries (checked).

C. Tools, finance and traceability (C8a-08 to C8a-10, C8b-18)

Category look-ups in Profit & Loss (4 round trips → 1), Purchases, jar sizes (Traceability), jar sales and research key events. Each first looked up the category id, then its values. Now there's one query each, using the existing join already proven in the GDD tracker. There's exactly one link between the two tables (checked). Errors are logged instead of silently giving empty lists.
GDD tracker and containers: their independent loads run together.
Traceability batch preview: the producer and apiary look-ups run together. The extra harvest look-up is removed, because the floral source is already loaded with the containers. A cancel flag stops an older preview overwriting a newer one (C8b-13). The batch list stops loading full container records it never uses.
CRM order page: recipient labels load together with the customer, stats and credit (3 steps → 2). Invoice: the customer comes with the order (2 → 1).

D. Research and profile (C7b-20, C7b-21, C7b-02)

Diagnosis images: images and comments load together. The comments query no longer sends every image id in the URL, which broke after a few hundred images; the database already limits comments to images you can see. Names use a chunked look-up. The spinner always stops, even on errors.
Wild colonies: both lists load together. C7b-02: an error no longer leaves the spinner running for ever.
Profile page: two start-up look-ups (role and account date) are removed. The page never uses either result, but waited for both before showing.

Not changed (noted)

  • Queen productivity tracker: nothing uses it. It reads a harvest_records table and queen columns that don't exist (checked), so it could never have worked. It belongs to the dead-component clean-up (C8a-05), not a speed fix.
  • Transfer dialog: the user list shows no e-mail address, because /api/users/list doesn't return one. This is minor and separate.

Follow-up: Tighten hives Row Level Security

STATUS: DONE. Applied to production via migration tighten_hives_rls_owner_and_team_scope. Security advisors re-run: hives no longer appears in rls_policy_always_true and no new hive-related findings were introduced. Decisions taken: edit/delete = hive owner only; SELECT/INSERT scoped via can_access_apiary.
Original severity: Critical. The hives table had fully permissive RLS. Every authenticated user could read, modify, and delete every hive in the database. Data was scoped only by application-layer query filters, which any client could bypass. This task replaced the open policies with owner/team-scoped ones.

Proposed Policies

Scope by hive owner OR an apiary the user can access. Reads/edits follow the same accessibility as the apiary; delete is intentionally stricter (owner only) so a team member cannot destroy another member’s hive.

-- SELECT: own hives + hives in any apiary I can access
USING (user_id = (select auth.uid())
       OR (apiary_id IS NOT NULL AND can_access_apiary(apiary_id, (select auth.uid()))))

-- INSERT: I must be recorded as owner, and the target apiary (if any) must be one I can access
WITH CHECK (user_id = (select auth.uid())
            AND (apiary_id IS NULL OR can_access_apiary(apiary_id, (select auth.uid()))))

-- UPDATE: same accessibility for the existing row and the resulting row
USING (user_id = (select auth.uid())
       OR (apiary_id IS NOT NULL AND can_access_apiary(apiary_id, (select auth.uid()))))
WITH CHECK (apiary_id IS NULL OR can_access_apiary(apiary_id, (select auth.uid())))

-- DELETE: owner only (stricter than view/edit)
USING (user_id = (select auth.uid()))
Decisions to confirm before implementing:

  • Moving a hive out: the UPDATE WITH CHECK above lets a hive be set to apiary_id NULL or to any apiary the user accesses. Confirm that is desired.

Tasks & Events — Mobile Triage

Status: T1–T9 implemented (T9 added 04/09/2026 after the owner reported cards still filling the screen). Type-check clean, lint clean, suite shows no regression. Awaiting your browser test.
Date: 04/09/2026  ·  Feature plan: docs/features/tasks-mobile-triage-plan.md  ·  File touched: src/app/dashboard/tasks/page.tsx

Your brief: opening tasks on a phone is overwhelming when there are a lot of them; the priority is not clear; there is no prefiltering; there is just a lot of scrolling and the user loses interest.

1. What I measured

Read-only queries against the live database, 19 accounts holding tasks. The numbers are worse than the brief suggests.

MeasureValue
Incomplete items across all accounts160
…already past their date153 (96%)
…due today1

…that are anything else43

Worst account34 incomplete, all 34 overdue by 90+ days

So the screen is not a task list. It is a 96%-overdue archive, sorted so the stalest item is at the top, with no word anywhere on it saying "overdue".

2. Root causes

RC1 — The screen opens on filters, not on work

page.tsx:751 is grid grid-cols-1 sm:grid-cols-2 lg:grid-cols-3. On a phone that is one column: five stacked selects (six for team members), each a 20px label plus a 48px fj-control, at gap-4.

5 × (20px label + 4px + 48px control) + 4 × 16px gap = 424px
+ "Filters" header (~40px) + Card padding (~32px)    ≈ 496px

On a 390 × 844 phone, with the app header and bottom navigation, that is most of the first screen. No task is visible on first paint. Hives and Records both had this and both were fixed in Phase 4. Tasks was missed.

RC2 — The screen has no notion of "due"

filteredTasks (page.tsx:496) is a plain .filter() over the fetch order, start_date ascending. No sort control, no re-sort. So the top of the list is the most neglected item and today's work is at the bottom after 150+ cards — and nothing on any card says a task is late. The concept already exists twice in this codebase (getOverdueTasks in src/lib/ai/tools/tasks.ts:70, alerts.todayTasks in the dashboard RPC) and never reached this screen. Mel can tell you that you have 46 overdue tasks; the Tasks page cannot.

RC3 — Three quarters of the list is machine-generated calendar noise

sync_batch_dates_to_tasks() (migrations/create_batch_events_trigger.sql) writes four rows per rearing batch:

Titleevent_typecategorypriority
Acceptance Check: {batch}eventqueen_rearinghigh
1st Cage Option: {batch}eventqueen_rearinghigh
2nd Cage Option: {batch}eventqueen_rearinghigh
Expected Emergence: {batch}eventqueen_rearingnormal

They are informational milestones with no completion path — nothing ever ticks them — so they accumulate permanently. 116 of the 160 incomplete rows are these. Twenty batches a season means eighty permanent red-flagged entries that were never yours to do. They are cleanly separable: all 116 carry a non-null batch_id.

RC4 — Priority shouts on 58% of the list

page.tsx:887 renders the priority badge unconditionally, normal and low included. With RC3 on top, "HIGH" is on more than half of every screen, so it carries no information. The Visit Checklist already gets this right (page.tsx:1432 hides normal); the main list does not.

RC5 — Cards are tall

One card can carry six badges wrapping over three lines, then a description (129 of 160 rows have one), an equipment line, a date row and up to three association chips — roughly 200px on a phone. Fifty-one incomplete tasks is about fifteen screens of scrolling.

RC6 — No search

Phase 4 gave Hives and Records a search box. Tasks has none, so a known task can only be reached by scrolling.

4. The plan

Nothing below is a new component. Every piece already has a house pattern, listed in section 4 of the feature plan.

  • ☑ T1 — Triage presets, always visible, carrying counts. Replaces the Status select. Styled exactly as the Records time-period pills (RecordFiltersBar.tsx:99-146), in a flex flex-wrap gap-2 row under the header.
    PillPredicate
    Due now (default)!completed && start_date <= today
    This week!completed && today < start_date <= today + 7
    Later!completed && start_date > today + 7
    Donecompleted
    Alleverything fetched
    Counts computed under the other active filters, the way timePeriodCounts already is on Records, so the number on a pill is what tapping it gives. Persisted as tasks:view with a membership validator, not a type check — Phase 4 recorded that a type-only validator lets a retired enum value through.
    This is the prefiltering that is missing: the default answers "what do I need to do", and the counts answer "what is the priority" before anything is tapped.
  • ☑ T2 — Sort by urgency, not by age alone. Within the active preset: start_date ascending, tie-broken by PRIORITY_ORDER (urgent 0, high 1, normal 2, low 3), promoted out of UpcomingEvents.tsx into one shared constant so the dashboard widget and the list agree.
  • ☑ T3 — Say "overdue". On an incomplete card dated before today, the date line turns red and reads Overdue — 12 days, using the same definition as getOverdueTasks so Mel and the screen tell one story. A card dated today reads Today. One line of the card, not a new badge.
  • ☑ T4 — Quieten the badges. Priority badge only when high/urgent (the Visit Checklist rule, applied to the main list). Type badge only when the row is not a plain task. The 📧 Email Reminder badge comes off the card — it applies to 13 of 160 rows, it is a setting rather than a property of the work, and it is visible in the edit form. A typical card goes from four-to-six badges down to none or one.
  • ☑ T5 — Collapse the secondary filters. The whole filter Card becomes a FilterDisclosure with storageKey="tasks:filtersOpen", an active count and Clear filters. Inside, one flex flex-col sm:flex-row sm:flex-wrap gap-3: Type, Category, Ownership, Apiary, Hive. Apiary and Hive keep routing through useSelection and are counted — an apiary chosen on the Hives screen would otherwise silently shorten this list with no visible cause, which is exactly what the count badge exists to prevent.
    First screen: ~496px of filters → one 48px control.
  • ☑ T6 — Search. Ephemeral useState, no debounce (house convention), matching title, description, notes and equipment. Placeholder Search tasks, notes or equipment. Empty state No tasks match your search.
  • ☑ T7 — Deep-link safety. UpcomingEvents links to /dashboard/tasks?task=<id> for items 1 to 7 days out. With Due now as the default those rows are filtered out, and the scroll-to-highlight effect is guarded by filteredTasks.some(t => t.id === highlightedTaskId) (page.tsx:646) — so it would silently do nothing and you would land on a screen that does not contain the task you tapped. Applying a ?task= deep link therefore also sets the preset to All. ?hive= and ?apiary= need no override.
  • ☑ T8 — Verification. Type-check, lint, test suite, then update this record and the feature plan with a review section. You test the build.

4b. T9 — the compact card (added after first browser test)

Owner feedback, 04/09/2026: "on a mobile screen, every single task is taking up way too much space, almost filling the entire screen."

Correct, and RC5 was the finding this plan deliberately deferred — the same call Phase 4 made about the Hives compact view. It is now the binding constraint, so it has been done.

Why a card was ~380px

The width was the hidden cause. On a 390px phone the content column was:

390 − 32 page padding − 4 accent border − 32 card padding
    − 44 checkbox − 12 gap − 88 Edit/Delete column  ≈ 174px

The two permanently visible icon buttons took a quarter of the screen width for actions used rarely. Everything then wrapped against the remaining 174px: title over three lines, badges over two rows, description over four, the date line over three, association chips over two.

What the collapsed card carries now

┌──────────────────────────────────────┐ │ [○] Treat hive 12 for varroa [⌄]│ │ 06/08/2026 · Overdue — 21 days │ │ · Hive 12 · Home Apiary URGENT │ └──────────────────────────────────────┘

Title clamped to two lines, then one wrapped line of context: date, lateness, hive, apiary, and a priority badge only when it is high or urgent. Content column is now ~210px and the card is roughly 74–98px instead of ~380px — about seven cards a screen instead of one and a half.

Description, equipment, times, end date, the remaining badges, the batch chip and both actions move into a panel opened by the chevron. One card open at a time, following expandedNucId in MatingNucsTab. The chevron is a real IconButton with aria-expanded and aria-controls, not a click handler on the card — a bare <div> target would have no keyboard path, which is the defect Phase 4 recorded on the Records cards.

Edit and Delete are now labelled buttons rather than a bare pencil and bin. On a long list those icons are a guess, and this audience should not have to guess before deleting something. Demoting Delete into the panel also follows Phase 4’s destructive-action hierarchy.

Association lookups moved to Maps built once (hiveById/apiaryById/batchById). They were three .find() calls per card inside the render loop — O(tasks × hives) on every keystroke of the new search box. checklistGroups now shares them instead of rebuilding two of its own.

Third QA pass — five findings on the new card

🟠 A long title became unreachable on a phone. line-clamp-2 plus a title attribute works on a desktop hover and nowhere else — and expanding the card did not un-clamp it, so the tail of a long title could not be read on the very device the card was compacted for. Fixed: clamped while collapsed, whole while open.

🟡 The expanded card repeated the date on nine rows out of ten. The time block fired on all_day, and a live count showed 144 of 160 outstanding rows are all-day single-day tasks — so most expanded cards would have printed "04/09/2026 (All day)" directly beneath "04/09/2026 · Overdue — 12 days". Fixed: the block renders only when there is a start time or a differing end date, which is 9 rows rather than 144.

🟡 An empty badge row. A task with no category, type, reminder, team flag or batch rendered an empty flex container still contributing its space-y-3 margin — 8 outstanding rows today. Fixed with a hasDetailBadges guard.

🟡 aria-expanded with no aria-controls. The panel had no id to point at. Fixed using the same convention as FilterDisclosure: the attribute is set only while the panel exists to be referenced.

🟡 A deep-linked task arrived collapsed, showing less than the dashboard widget that was tapped to reach it. Fixed: a ?task= link now opens that card as well as ringing it.

⚪ Noted, not changed: a task attached to an archived hive renders "Hive Unknown", because fetchAssociations loads only non-archived hives. Pre-existing, and a live count returns zero such rows today, so it is recorded rather than fixed.

5. Decision taken

Option (b) — hide batch milestones by default, with a pill to bring them back. Implemented as an includeBatchMilestones toggle persisted at tasks:milestones, default off, rendered as a purple pill at the end of the preset row. The options considered were:

What should happen to the 116 batch milestones? They are 72% of the incomplete list, they are all flagged high, and none of them can ever be ticked off. Any amount of filtering and sorting is fighting this.

(a) Leave them, rely on the existing Type filter. Zero risk. But the default view stays three-quarters noise, which is your complaint. That Type select already exists and defaults to "All Types"; it has evidently not been enough.

(b) Default the primary view to tasks and reminders, with an always-visible Batch milestones (n) pill in the preset row.  ← chosen. Nothing is hidden — the count is on screen at all times, which is the standard this codebase already set for collapsed filters — and one tap brings them back. The default view drops from 160 items to 43. Small, contained, entirely client-side.

(c) Give the milestones a real completion path so they leave the list once the batch passes them. Correct in principle, and the only option that actually stops the accumulation. But it is a queen-rearing change touching a database trigger, and it is a much larger piece of work than this one. I would record it as a follow-up rather than do it here.

6. Edge cases I will handle

  • A stale tasks:view value — validated by membership, not type.
  • "Due now" can legitimately be empty. A tidy account lands on an empty screen, so the empty state must name the preset ("Nothing due now", other counts still visible on their pills) rather than the generic "No tasks or events found", which would read as data loss.
  • The 12-month fetch window. fetchTasks is bounded to start_date >= today − 1 year, .limit(1000). Search and the All pill cannot find what was never fetched, and the pill counts are counts of the fetched set. Same honesty limit Phase 4 recorded for the Records 500-row cap. Not widened here.
  • The Visit Checklist must not change. checklistTasks deliberately ignores every page filter; it must keep ignoring the new preset too, so the preset goes nowhere near it.
  • openChecklist seeds the modal's apiary picker from filterApiary — still works with apiary inside the disclosure.
  • Counts must be computed under the other filters, or a pill promises ten and delivers two.
  • Two persisted keys added (tasks:view, tasks:filtersOpen), one (tasks:status) retired and simply no longer read.

7. Out of scope

  • Giving batch milestones a completion path (decision option c).
  • Widening the 12-month / 1000-row fetch window.
  • Task assignment to team members — there is no assigned_to column.
  • Recurrence — the columns exist and nothing writes them.
  • A calendar or month view.
  • Known defect, recorded not fixed: records/page.tsx:1141 writes category: 'Treatment' (capital T), which violates tasks_events_category_check and fails. Already noted in bulk-apply-treatment-feeding-plan.md:158-160.
  • Consolidating the three overlapping task types (HiveTask, the local TaskEvent, the local UpcomingEvent).

8. Database work

None. Every change is client-side in src/app/dashboard/tasks/page.tsx. No schema, RLS policy, RPC, trigger or index is altered. idx_tasks_events_user_start_date already covers the fetch; the live schema was read only to produce section 1.

First QA pass — three defects in my first draft

🔴 The deep link silently undid the fix. The first draft had a ?task= link call setView('all') and setIncludeBatchMilestones(true). Both are persisted. So one tap on a dashboard event would have permanently reset the preset to "All" and switched the batch milestones back on — restoring the exact 160-row list this work exists to avoid, with no way for the beekeeper to know why. Fixed by leaving both preferences alone and having filteredTasks admit the highlighted row directly, so the deep-linked task appears and is scrolled to without touching a saved preference.

🟠 The milestone pill lied whenever any other filter was set. batchMilestoneCount counted every incomplete milestone in the account, ignoring apiary, hive, ownership, search and the active preset. With an apiary selected it would have promised 116 and delivered three — the precise failure section 6 of this document warns about for the preset counts. Fixed by extracting passesFilters as a shared predicate and counting milestones that pass it and the current preset, so the pill states exactly how many rows toggling it will add. That also fixed a quieter second bug: in the Done view the old count was always 0, so the pill vanished while still suppressing completed milestones with no way to reveal them.

🟡 Ad-hoc date arithmetic. dueLabel computed the overdue span with raw Date.parse millisecond division. Fixed to use the existing differenceInCalendarDays and parseLocalDate helpers, so it agrees with every other day count in the application.

Also added role="group" with a label on the preset row, so a screen reader announces what the pills filter rather than reading five loose toggle buttons.

Second QA pass — a further six findings

A second independent audit was run over the implemented code. Two findings were material.

🟠 The ownership filter could apply with no control on screen. tasks:ownership is persisted, but its <select> renders only when isTeamMember is true, and activeFilterCount also counts it only when isTeamMember is true — while the filter itself ran unconditionally. A beekeeper whose team access ends keeps a stored value of 'team', whose predicate excludes every row they own. The result is an empty list, no visible control, nothing on the Filters badge, and no way to clear it. The new preset-aware empty state makes this worse, not better: it says "Nothing due now" with total confidence. Fixed by gating the predicate on isTeamMember too, so the filter, its control and its count can never disagree. Pre-existing in structure, but newly reachable in a way that reads as data loss.

🟠 The deep-linked row stayed pinned forever. highlightedTaskId is set on arrival and never cleared. Before this work that was cosmetic — a blue ring that outstayed its welcome. But the fix for the earlier critical finding has filteredTasks inject that row whatever the preset, so the ring became a task permanently wedged into every subsequent view: a card plainly not due, sitting in "Due now", undismissable short of reloading. Fixed by treating the highlight as spent the moment the beekeeper steers the list themselves — changing preset, toggling milestones or clearing filters all release it. This is the second-order defect of my own first-pass fix, which is exactly what a second pass is for.

🟡 role="group" mislabelled the milestone toggle. The group label reads "Filter tasks by when they are due", and the milestone pill sat inside it — but it filters by what a row is, not when it is due. Fixed by moving it out of the group. The first attempt used display: contents on the group wrapper and was rejected on review: that property has a history of dropping the element carrying the role out of the accessibility tree entirely, which would have removed the label it was added to provide. Real nesting instead.

🟡 A guard that did not guard. dueLabel wrapped its day count in Math.max(1, …) to floor it — but parseLocalDate returns an Invalid Date for anything that is not a YYYY-MM-DD prefix, and Math.max(1, NaN) is NaN. The floor silently passed NaN through to the card as "Overdue — NaN days". Fixed with an explicit Number.isFinite check falling back to the bare word "Overdue", which stays true whatever the date said.

🟢 PRIORITY_ORDER was exported mutable. Harmless while it was private to UpcomingEvents; less so now it is shared, where a stray write would silently reorder the dashboard widget as well as the list. Frozen and typed Readonly.

🟢 The inactive milestone pill dimmed an interactive control (text-text-secondary) while its four neighbours used text-foreground. For an audience of 50+ with reduced eyesight, a control should not be the faintest thing in its own row. Matched to the others.

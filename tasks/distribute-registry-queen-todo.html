Distribute a manually-added registry queen

Goal

A queen added by hand to the Queen Register (no graft, no rearing batch — e.g. a bought-in queen, a caught swarm, or a queen recorded retrospectively) currently has no way to be distributed. Give it the identical distribution capability the batch/graft and mating-nuc distribution points already have: same modal, same recipient options, same recipient-side queen creation, same mating confirmation and Queen Ledger outcome tracking.

Root blocker: every distribution is hard-anchored to a graft. A registry queen has none.

Approach — and why

Three options were considered:

OptionVerdict
A. Synthesise a placeholder batch + graft for each manual distributionRejected. Pollutes batch counters, NIHBS monthly returns and rearing-group reports, which count grafts/distributions by batch_id. Invents fake breeding records.
B. A separate queen_transfers table (the route hinted at in docs/features/redistribute-existing-queen.md:61-64)Rejected. Would require duplicating the modal, the list, recipient queen minting, mating confirmation, CRM order linking, the Queen Ledger and the reports. That is the opposite of “exactly the same”.
C. Let graft_distributions carry a second, mutually-exclusive source: a queenChosen. One nullable column + relaxed constraints. Every existing read, write, outcome flow and report keeps working unchanged; the new source type simply flows through them.

The table name becomes slightly inaccurate, but renaming it would touch ~15 files for no functional gain. Not worth the churn.

Design

Data model (one migration, applied via Supabase MCP)

ALTER TABLE graft_distributions
  ALTER COLUMN graft_id  DROP NOT NULL,
  ALTER COLUMN batch_id  DROP NOT NULL,
  ADD COLUMN source_queen_id uuid REFERENCES queens(id) ON DELETE CASCADE;

-- Exactly one source: a graft (with its batch) OR a registry queen.
ALTER TABLE graft_distributions ADD CONSTRAINT graft_distributions_source_check CHECK (
  (graft_id IS NOT NULL AND batch_id IS NOT NULL AND source_queen_id IS NULL)
  OR (graft_id IS NULL AND batch_id IS NULL AND source_queen_id IS NOT NULL)
);

-- Mirrors UNIQUE(graft_id): one live distribution row per queen, so
-- "distribute again" is an UPDATE, exactly like graft redistribution.
CREATE UNIQUE INDEX graft_distributions_source_queen_unique
  ON graft_distributions (source_queen_id) WHERE source_queen_id IS NOT NULL;

-- Recipient-side idempotency key for queen-sourced distributions
-- (the graft path keeps using queens.source_graft_id).
ALTER TABLE queens
  ADD COLUMN source_distribution_id uuid REFERENCES graft_distributions(id) ON DELETE SET NULL;
CREATE UNIQUE INDEX queens_user_source_distribution_unique
  ON queens (user_id, source_distribution_id) WHERE source_distribution_id IS NOT NULL;

Existing rows are unaffected (all have graft_id + batch_id, source_queen_id NULL) so the CHECK is satisfied retroactively. Index on source_queen_id also serves lookups.

RPC changes

  • create_queen_for_distribution — drop both existing overloads, recreate with one extra parameter p_source_distribution_id uuid. Idempotency branches: use source_graft_id when a graft is present, otherwise source_distribution_id. Dropping the legacy 20-arg overload at the same time avoids PostgREST named-argument ambiguity. Needs an explicit GRANT EXECUTE TO authenticated.
  • promote_distributed_queen_on_mating — currently returns early when graft_id IS NULL. Add the queen-sourced branch: locate the recipient queen by source_distribution_id = p_distribution_id. Without this, confirming mating on a registry-queen distribution would silently do nothing.

UI — reuse, do not duplicate

DistributeGraftModal becomes source-agnostic: graftId/batchId/cellNumber become optional and a sourceQueenId prop is added. Every other field — group member / app user / other beekeeper tabs, distribution date, recipient apiary & hive, mating location, CRM order linking, club-member flag, notes — is untouched and works as-is.

Entry point: the queen detail page header, in the same slot as the existing Send redistribute icon (queens/[id]/page.tsx:359-368). The gate canRedistribute splits into two cases so the two paths never overlap:

QueenActionWrite path
has source_graft_id + batch_idRedistribute (unchanged)redistributeQueen — UPDATE
no source_graft_id (registry queen)Distribute (new)createDistribution — INSERT

Status → distribution type mapping mirrors the graft rule: cell → queen_cell, virgin → virgin_queen, active → mated_queen. After a successful save the donor queen goes status = 'distributed' and is detached from its hive — identical to the existing redistribute post-actions.

Provenance for the recipient

The graft path derives the recipient's queen provenance from the batch (createQueensForRecipient). For a registry queen there is no batch, so a sibling helper derives it from the donor queen instead — birth date, marking colour, subspecies, mating station/eircode, mother snapshot — reusing the existing buildLineageString and formatQueenSnapshot helpers so the lineage string stays consistent with the edit form.

Deliberately out of scope

  • Renaming graft_distributions → queen_distributions. Cosmetic; ~15 files.
  • Batch-page distribution list. It is filtered by batch_id, so registry-queen distributions correctly never appear there. They surface in the Queen Ledger instead.
  • Bulk distribution of registry queens. The graft flow has it; adding a multi-select to the queens list is a separate, larger UI job. Single-queen distribution first.
  • NIHBS / rearing-group reports. These are explicitly batch-scoped returns; a bought-in queen passed on is not batch-reared output and must not inflate them.
Decisions confirmed:
  • Queen Ledger: included. Registry-queen distributions appear alongside batch-reared ones with full outcome tracking (mating confirmed, overwintered, offspring hybridised, queen failed). Tasks 11–12 are in scope.
  • Entry point: queen detail page only. The Send icon in the header action row, the same slot as the existing Redistribute button. No queens-list row action.

Review

All 14 tasks complete. npx tsc --noEmit reports 0 errors in src/ (the remaining errors are pre-existing test-mock typing issues in tests/, untouched by this work), and ESLint is clean across all six changed files.

Database (4 MCP migrations, no SQL file)

  • distribute_registry_queen_schema — relaxed graft_id/batch_id, added source_queen_id, the XOR CHECK, the partial unique index, and queens.source_distribution_id + its partial unique index.
  • create_queen_for_distribution_queen_source — dropped both stale overloads (20-arg and 21-arg) and recreated with p_source_distribution_id. Verified only one overload now exists, so PostgREST named-argument resolution stays unambiguous.
  • promote_distributed_queen_on_mating_queen_source — this one mattered: the function previously returned early whenever graft_id IS NULL, so confirming mating on a registry-queen distribution would have silently done nothing.
  • graft_distributions_source_queen_ownership_guard — see security note below.

Both callable RPCs verified as authenticated + service_role only — no anon/public exposure. The trigger function has EXECUTE revoked from all client roles.

Security gap found and closed

The new column introduced an authorisation hole: RLS on graft_distributions only checks user_id, and a CHECK constraint cannot reach another table, so a caller could have pointed source_queen_id at a queen belonging to someone else. A BEFORE INSERT OR UPDATE trigger now rejects that. Rather than amend the existing ALL RLS policy (which would have put the working graft path at risk), the guard is purely additive.

Constraint verification

Ran a DO block against the live database that exercised every new constraint and then aborted, rolling the whole block back. All five assertions passed:

Confirmed afterwards that count(*) where source_queen_id is not null is 0 — nothing was left behind in production data.

Design change made during implementation

  • redistributeQueen handles both sources. Originally scoped as INSERT-only for registry queens, but leaving it graft-only would have meant an unkeyed UPDATE if it were ever called with a queen-sourced row. It now keys on source_queen_id when there is no graft, and refuses outright when neither is present.

QA audit — findings and fixes

A Principal Quality Architect pass over the diff found four defects, two of them serious. All are fixed; tsc --noEmit is clean in src/ and ESLint is clean.

SevDefectFix
High Unbounded request URL in the Ledger. My first cut replaced the group query's rearing_batches!inner filter with a pre-resolved .in('batch_id', […]). That list grows with every batch a group ever creates (18 today, unbounded over time); at a few hundred it overflows the server's URL limit and the entire group scope throws. The original filter was bounded by the number of groups. Restored !inner for the group query via a per-query select (distributionSelect(innerBatch)). Since a dynamic select loses supabase-js's row inference, rows are cast to an explicit DistributionQueryRow type — which also removed the duplication that pushed me down the batch-id route in the first place.
High Registry cells/virgins inherited the donor's mating station. The page passed defaultMatingLocation for every registry queen. For an unmated cell or virgin this stamps a station it has not mated at — and worse, it silently satisfies the modal's “apiary or mating location required” check, so the user is never prompted for the real destination. This is exactly the defect fixed for the batch flow in distribute-mating-location-todo.html. Pre-fill only when queen.status === 'active'.
Medium Duplicate queen numbers in the recipient's register. There is no DB uniqueness on queens(user_id, queen_number), and registry numbers are the donor's own — typically “1”, “2”. Distributing queen “1” to someone who already has one silently created a confusing duplicate. (ensure_reared_queen_record guards against this; the distribution path did not.) New internal next_free_queen_number() suffixes until free (1 → 1-2), bounded at 50 attempts. Applied only to the queen-sourced branch — graft tags and Cell #N keep their exact value. Verified live: M31-01 → M31-01-2, unused numbers untouched.
Medium Donor queen lookups not user-scoped. Three queries fetched queens by id alone, relying on RLS. The project convention is explicit user scoping, and queens RLS could widen for team-shared records. Added .eq('user_id', …) to the donor fetch, its mother lookup, and both Ledger queen lookups; plus an early return when there is no authenticated user.

Accepted, not fixed

  • Self-distributing a registry queen mints a second record in your own register while marking the original distributed — the graft path behaves identically, so this is consistent rather than a regression.
  • queen_marked always reads false for registry rows in the Ledger (it comes from the graft, which does not exist).
  • Deleting a registry-queen distribution does not revert the donor's distributed status — no UI exposes that deletion.

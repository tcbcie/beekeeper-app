WP10 – Make appearance preferences explicit

Plan: docs/features/mobile-first-implementation-plan.html (WP10 and refinements). Findings: F11, V21. No database change: the choice is kept on the device, as now.

What the code does today

  • The choices. Profile → Appearance offers three buttons: Light ("Field"), Dark ("Evening") and Auto ("6am-8pm"). Auto means light from 6am to 8pm and dark otherwise, by the device's clock, checked once a minute.
  • The default. Nothing is saved for a new user, so they get Auto by the clock. Nothing in the app follows the phone's own light or dark setting.
  • Where it lives. The choice is stored in the browser under theme. Two places apply it: the start-up script in layout.tsx, which runs before the first paint, and theme-provider.tsx. They hold duplicate copies of the same rule.
  • The buttons have no selected state for screen readers.
  • Browser bar colour (V21). The page carries two theme-color tags, one for a light phone and one for a dark phone. The app updates only the first. On a phone set to dark, the bar can stay dark while the app is light.
  • Charts read the theme from the page itself, so they need no change.

Changes

  1. A "Use device setting" choice (F11), in theme-provider.tsx and the start-up script in layout.tsx.
    • The new stored value system follows the phone's light or dark setting, read with prefers-color-scheme.
    • It updates straight away when the phone switches, for example at sunset.
    • A phone change affects only this choice. Light, Dark and the schedule ignore it.
  2. Saved choices are kept exactly.
    • Light stays Light and Dark stays Dark.
    • A saved Auto keeps working by the clock, as before. It is never quietly switched to the device setting. Its label changes, see D1.
  3. Default for people who never chose: see D2. The start-up script and the provider use the same default, so the first paint matches.
  4. Clear choices in theme-switcher.tsx.
    • The buttons become a radio group with a hidden "Appearance" legend, using RadioChoiceOption (green when chosen, as elsewhere). The chosen option is announced.
    • Each option is at least 48px, one per row on phones and two per row from sm up.
    • The descriptions say what each choice does:
      • Light: "Easiest to read outdoors"
      • Dark: "For evenings and low light"
      • Use device setting: "Follows your phone or computer"
      • The schedule: see D1
    • The Profile intro line: "Your choice is kept on this device."
  5. Browser bar colour (V21): the start-up script and the provider update every theme-color tag, not just the first, so the bar always matches the app.

Decisions (both accepted as recommended, 05/11/2026)

  1. D1 – Keep the clock schedule? Anyone who picked Auto chose it on purpose.
    • Recommended: keep it as a fourth choice, "Light by day", described as "Light 6am to 8pm, dark after". Existing Auto users keep their behaviour, under a clearer name.
    • Alternative: remove it. Anyone with Auto saved would then move to "Use device setting", which changes their behaviour, so the plan advises against it.
  2. D2 – Default for people who never chose (everyone with nothing saved, including new users).
    • Recommended: Use device setting. It respects what the person already set on their phone, and is how most apps behave.
    • Alternative A: Light. The app is designed light-first for outdoor work, and dark only when chosen.
    • Alternative B: keep the clock schedule as the default (no change in behaviour).

    Whatever is chosen, existing users with nothing saved will see the new default on their next visit. Anyone who wants something else picks it once.

Not changed

  • Where the choice is stored (this device only) and its key.
  • manifest.json colours (installed app splash) stay cream.
  • offline.html, which already follows the device setting.
  • Map styles and chart colours.

Review

Built as planned in 4 files: theme-provider.tsx, layout.tsx (start-up script), theme-switcher.tsx and the Profile intro line. No database change.

  • Provider:
    • New stored value system, which is the default when nothing valid is saved.
    • The device-setting listener runs only while that choice is active. The minute timer runs only for Light by day.
    • Every theme-color tag is updated. Theme is exported for the switcher.
  • Start-up script:
    • The same four values and default.
    • The storage read has its own guard, so a blocked storage (private window) still gets the device setting at first paint. Before, the script stopped and left the page light until the app loaded.
  • Switcher: a fieldset with a hidden "Appearance" legend, four RadioChoiceOptions (green, at least 48px), one column on phones and two from sm.
  • Checks: type check clean, lint clean, full suite passes (881 passed, 23 skipped). No test covered the theme. No build run.
  • QA audit: one Medium, fixed.
    • Safari before 14 (older iPads) has no addEventListener on media queries, so the new listener would have thrown and crashed the app. It now falls back to addListener.
    • No Critical or High.
  • Low:
    • If Next places its theme-color tags after the start-up script, the script adds its own tag and the app corrects all of them once it loads. That is the same as before, and why V21 still needs a phone check.
    • An older copy of the app still open in another tab ignores the new system value until it reloads.
  • Docs: dark-mode-consistency-fixes-plan.md §10, profile-page-split.md, the WP01 baseline and both plans. .claude/skills/ui/SKILL.md still describes the old clock Auto. It has changes of yours that are not committed, so I left it alone.

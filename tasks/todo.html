Team Member Hive Placement into a Team Apiary

Problem

A team member (not the team owner) has two hives in their own apiary and needs to move them into the team’s apiary. More generally, members should be able to place hives into an apiary the team owner has shared with the team. Today only the apiary owner can add hives to it.

Root Cause (investigation)

  • Apiaries are never owned by a team — they stay owned by an individual (apiaries.user_id) and are shared into a team via the team_apiaries join table. Members get read access via the can_access_apiary() SQL function.
  • The blocker was not RLS. The hives table policies are all USING (true) — gating is entirely in application code.
  • The actual block lived in the create-hive handler in src/app/dashboard/hives/page.tsx: before insert it fetched the apiary and threw if apiary.user_id !== userId (“does not belong to you”).
  • The apiary dropdown already lists team-shared apiaries (labelled “(Shared)”), and the edit path had no such check — so moving an existing hive via Edit already worked. Only direct create was blocked.

Chosen Approach

Relax the create-time check so the selected apiary may be one the user owns or one shared with a team they belong to — exactly the set already shown in the dropdown (apiaries state = own + team-shared). The hive record keeps user_id = the placing member; the team sees it via the apiary sharing. Minimal, single-spot change.

Change Made

File: src/app/dashboard/hives/page.tsx (create branch of the submit handler). Replaced the database ownership lookup + “does not belong to you” error with:

if (dataToSubmit.apiary_id && !apiaries.some(a => a.id === dataToSubmit.apiary_id)) {
  throw new Error('Cannot create hive: you do not have access to the selected apiary.')
}

This also removes a redundant DB round-trip. No schema or RLS changes were needed.

Senior Code Review — Risk Findings

SeverityFindingStatus
Critical The hives table has fully permissive RLS (SELECT/INSERT/UPDATE/DELETE = true). Any authenticated user can read or modify every hive in the database; only app code scopes data. This predates this change. Tracked as a separate follow-up task per user decision.
Low A now-redundant check_user_owns_apiary RPC “test” remains just below the changed code. It only logs and never blocks, so it is harmless; left untouched to keep the diff minimal. Optional cleanup.
Note — moving existing hives: the user’s two hives can be moved today with no further change: open each hive → Edit → change Apiary to the team apiary (labelled “(Shared)”) → Save.

Review Summary

One small, contained edit removes the artificial restriction that stopped team members placing hives in a shared team apiary, bringing the create flow in line with the already-working edit/move flow and the dropdown’s contents. Hive ownership semantics are unchanged (the placing member owns the record; the team sees it through apiary sharing). The pre-existing wide-open hives RLS is flagged as Critical and tracked separately.

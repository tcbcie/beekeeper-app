Distributed queens — hive placement, stage & lifecycle

Full design: docs/feature/distributed-queen-hive-placement-lifecycle-plan.md.

What & why

When a cell/virgin/mated queen is distributed to an app user and assigned to a destination hive, place it in that hive and show it in the recipient's registry clearly badged by stage, with all provenance details, and support the lifecycle:

Cell  →(hatch day)→  Virgin  →(mating)→  Mated

Already true today

Distributing to an app user already creates the recipient's queen record with the lineage snapshot (mother queen, lineage, hatch/birth estimate, marking, subspecies). Gaps: not placed in a hive; virgin vs mated not distinguished (both active); no lifecycle promotion.

Confirmed decisions

TopicDecision
Stage modelNew virgin status (Cell / Virgin / Mated=active)
Hive placementAuto-place on distribution; cell shown as “Cell”, promoted on hatch
Occupied hiveOld queen → superseded, then place new
LifecycleBoth promotions (Cell→Virgin hatch day; Virgin→Mated)
Hatch dayManual “Mark as emerged”, pre-filled with estimate

Plan (phased — each change small)

  • Phase 1 — stage in registry: add virgin to types/queen.ts helpers and queens/page.tsx (filter, form, badge, summary count, sort priority).
  • Phase 2 — distribution stage + placement: in useGraftDistributions.ts map types to cell/virgin/active and thread recipient_hive_id to the RPC (single only). Extend RPC create_queen_for_distribution (via Supabase MCP migration) to place the queen in the recipient's hive — superseding any existing queen — guarded to the recipient's own hive.
  • Phase 3 — lifecycle on queen detail: in queens/[id]/page.tsx add “Mark as emerged” (Cell→Virgin, records hatch day) and “Mark as mated” for virgins (Virgin→Mated, records date/location + sets hive queen_mated). Render the virgin badge.
  • Phase 4 — hives show stage: hive detail/list (and any dashboard tile that assumes mated) show a Cell/Virgin/Mated badge for the current queen. Files confirmed after a focused look; includes a no-regression check for cell/virgin queens.
  • Phase 6 — breeder mating-confirmation propagates: add queens.source_graft_id (MCP migration) set at creation; new SECURITY DEFINER RPC promote_distributed_queen_on_mating that, when the breeder confirms mating in the tracker, promotes the linked recipient queen cell|virgin→active with date/location and flips its hive queen_mated — guarded to the recipient’s rows. Wire into setDistributionMatingConfirmation/updateMating (best-effort).
  • Phase 7 — docs: update batch-distributions / queen-rearing / queen-tracker docs and cross-reference the editable-lineage doc.

Out of scope

  • Reverting a promotion when the breeder un-confirms mating (mated→virgin).
  • Bulk hive placement (one hive, many grafts); moving an already-placed queen between hives.

Review

  • Phase 1 — virgin status added to the registry: filter, edit form, status badge (blue), summary count, sort priority (queens/page.tsx). No DB constraint change needed.
  • Phase 2 — distribution now maps queen_cell→cell / virgin_queen→virgin / mated_queen→active and threads recipient_hive_id + installed date + source_graft_id to the RPC. The create_queen_for_distribution RPC (Supabase MCP migration) now places the queen into the recipient's hive, superseding any existing queen, guarded to the recipient's own rows. Added column queens.source_graft_id.
  • Phase 3 — queen detail page: Mark as emerged (Cell→Virgin, records hatch day, pre-filled estimate), Mark as mated for cells & virgins (sets active + flips the hive to mated), Mark as failed for both; Virgin badge rendered.
  • Phase 4 — Stage badge (Cell / Virgin / Mated) on the hive detail page and a compact Cell/Virgin chip on the hive list card; virgins are now assignable to hives.
  • Phase 6 — new promote_distributed_queen_on_mating RPC (SECURITY DEFINER) wired into setDistributionMatingConfirmation: the breeder confirming mating promotes the linked recipient queen cell|virgin→active and flips its hive — best-effort, idempotent, guarded.
  • Phase 7 — new docs/features/distributed-queen-hive-placement.md; cross-referenced from batch-distributions & queen-tracker docs.

Defensive notes: all cross-account writes live in SECURITY DEFINER RPCs and only ever touch the recipient's own queen/hive; placement & propagation are guarded by user_id = recipient and (for propagation) caller-owns-distribution; both promotion routes converge on the same record with no conflict; bulk distribution never auto-places.

Tech debt noted: the Cell/Virgin/Mated badge classes are now inlined in three places (registry, detail, hive) — candidate for a shared helper later.

Not build-tested locally (per project workflow). Suggested manual test: distribute a cell to an app user + pick their hive → confirm it appears in their registry as “Cell” and in the hive; Mark as emerged → Virgin; confirm mating in the tracker → recipient queen becomes mated and the hive flips.

Repository improvement programme — audit follow-up (July 2026)

Source: full repository + database audit (three exploration agents + live Supabase advisor review, 22 July 2026). Phases are ordered by risk and user payoff. Each phase is small, self-contained, and independently shippable. Phase 1 is a live security issue and goes first.
Why Phase 1 cannot wait: three SECURITY DEFINER functions are executable by the anonymous role today:
  • hard_delete_user(uuid) — no admin check in the body; anyone with a user UUID can permanently delete that user and all their data.
  • get_users_with_email() / get_user_email() — no caller check; dumps every user's email, name, mobile number, subscription details.
  • execute_safe_query(text) — runs arbitrary SELECT as definer: a full read bypass of RLS across all 77 tables.
In total 66 SECURITY DEFINER functions are anon-executable and 10 views are flagged security_definer_view at ERROR level.

Phase 1 — Security migration (do first)

One migration applied via the Supabase MCP (per project convention — no SQL files to run manually). Frontend impact: none expected for normal users; the admin Settings page calls these functions as an authenticated admin, which keeps working.

  • ☑ 1.1 Inventory all 66 anon-executable SECURITY DEFINER functions and classify each — done: 13 trigger-only, 7 service-role-only, 31 authenticated-only, 3 genuinely public RPCs, 19 RLS helper predicates (kept callable — TO public policies evaluate them on anonymous requests, e.g. invitation links).
  • ☑ 1.2 Migration phase1_security_hardening_guards_and_revokes applied via MCP: revokes + explicit grants per class, plus ALTER DEFAULT PRIVILEGES … REVOKE EXECUTE … FROM PUBLIC so future functions are locked by default.
  • ☑ 1.3 Internal admin checks added to hard_delete_user, soft_delete_user, restore_deleted_user, get_users_with_email (now returns empty for non-admins). get_user_email stays authenticated-only (needed by team pages); anon revoked.
  • ☑ 1.4 execute_safe_query is called by the admin export API route (service-role client) — locked to service_role only instead of dropping.
  • ☑ 1.5 search_path = public, extensions pinned on every remaining public function without one (advisor count 70 → 0).
  • ☑ 1.6 Six views flipped to security_invoker (active_profiles, deleted_profiles, users_with_registration_codes, users_needing_subscription_reminder, crm_customer_summary, hive_configuration_history_with_location) — admin UI keeps working via the "Admins can view any profile" policy. Four kept definer by design: shared_apiaries_obfuscated, wild_colonies_obfuscated, shared_gdd_records_community, public_galway_gdd.
  • ☑ 1.7 Dropped always-true policies: anonymous INSERT on profiles, open INSERT on subscription_history and batch_feedback (all writes go through SECURITY DEFINER functions / service role). Dropdown category/value writes now admin-only. No-policy RLS on crm_invoice_email_log / stripe_webhook_events confirmed intentional (service-role-only tables).
  • ☐ 1.8 Enable leaked-password protection — needs the Supabase dashboard (Authentication → Settings), cannot be set via SQL. User action.
  • ☑ 1.9 Advisors re-run: security findings 230 → 81; remaining items are the intentional public/authenticated RPC surface, the 4 intentional definer views, 1.8 above, and public storage bucket listing (see review). User regression test requested: login, admin user management (settings), invitation acceptance by link, public trace page, CRM customers list, dropdown management.

Phase 2 — Quick speed wins (small diffs, felt immediately in the field)

  • ☑ 2.1 Queens page N+1 fixed: per-queen hive query and per-parent queen queries replaced by one batched .in('queen_id', …) hives query and one batched missing-parents query. A 100-queen account now loads with 2-3 requests instead of 100-300.
  • ☑ 2.2 Hives page: duplicate full-inspections fetch removed (last-inspection dates now derived from the already-fetched newest-first set); initialFetchFilters ref stops the filter effect re-running the entire ~12-query chain when filtersLoaded first flips — the page previously loaded twice on every visit.
  • ☑ 2.3 Service worker: cache-first branch for /_next/static/* (content-hashed, immutable). Old entries purged on CACHE_NAME bump as before; API/HTML behaviour unchanged.
  • ☑ 2.4 Tasks page: tasks_events fetch now bounded to the last 12 months + future with .limit(1000); user ID resolved from the local session (getCurrentUserId) instead of a network auth.getUser() round trip.

Phase 4 — Shared team-access helper (unlocks perf + DRY together)

Phase 5 — Database performance migration

  • ☑ 5.1 Migration rls_initplan_wrap_auth_calls: generated rewrite of every policy calling bare auth.uid()/role()/jwt()/email() or the zero-arg admin helpers into initplan form. Advisor count 143 → 0.
  • ☑ 5.2 Migration consolidate_permissive_select_policies: the busiest CRUD tables (inspections, hives, queens, tasks_events) turned out to already be single-policy; the real duplication was on lookup/embed tables. Merged same-role SELECT pairs on profiles (4 public policies → 1 — evaluated in embeds on nearly every page), apiaries, batch_grafts, batch_breeder_queens, rearing_batches, gdd_records, subscription_history. Warnings 155 → 119; the remainder are role-split or admin/owner pairs on small, low-traffic tables (wild_colonies, conservation_areas, support_tickets…) left for clarity.
  • ☑ 5.3 Migration add_covering_indexes_for_unindexed_fks: generated covering index for every FK not already prefix-covered. Unindexed FKs 33 → 0. Dropping the 34 pre-existing unused indexes deferred — cannot rule out seasonal usage (harvest/treatment queries peak in summer/autumn); revisit with a full year of pg_stat_user_indexes data.
  • ☑ 5.4 Advisors re-run: performance findings 366 → 188 (the 68 "unused index" INFOs now include the 33 brand-new FK indexes, which naturally start at zero scans).

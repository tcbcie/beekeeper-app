Reusable jar-label QR codes for honey provenance

Raised: 27 August 2026 · Status: decisions locked (§10) — awaiting go-ahead, nothing built yet

Decisions taken 27 August 2026.
  • Two label designs — one per jar size. Two rows in the table, permanently.
  • Lot and BBD go on the label — either printed into the run, or hand-written into a printed placeholder. Either way the lot is on the jar, so the exact-batch fallback always works.
  • current is the resolve mode, and the only one built in v1.
  • The public page does not repeat the jar size — it is printed beside the QR already.

1. The problem

Today the QR code is minted per batch. BatchesTab.tsx:605 builds:

https://www.hivecraic.com/trace/{trace_code}[?w={net_weight_g}]

… where trace_code is an 8-character code stored on the batch row (batch_runs.trace_code), and ?w= narrows the public page to one jar size within that batch.

That model assumes one print run per batch. The new requirement inverts it:

  • Labels are printed commercially, in large quantities, well in advance.
  • There is one label design per jar size (e.g. 227 g, 340 g, 454 g).
  • Each design will be applied across many batches over months or years.

So the QR can no longer name a batch. It must name something permanent, and the batch has to be resolved at scan time.

Two facts still have to be physically on the jar — and this shapes the whole design.
The lot mark and the best-before date are mandatory on-pack information under EU food labelling rules; a QR pointing at a web page does not satisfy either. Both change per batch, so either the print run is batch-specific, or the label carries a printed placeholder that is written in at bottling.

Confirmed: lot and BBD will be printed into the run or hand-written into a placeholder. Either way the lot code is on the jar. That gives a guaranteed fallback — a consumer can always identify their exact batch by reading it — which is what makes the whole scheme safe rather than a guess. (Still worth confirming the exact format requirement with your packaging supplier before committing to a run.)

2. What we can and cannot honestly promise a scanner

This is the crux, and it drives the recommendation.

ScenarioCan a static QR resolve it correctly?
Jar bought this week, from current stockYes — the label points at whatever is being bottled now
Jar bought in March, scanned in SeptemberNo — the label has since moved on to a later batch

A design that silently shows “the current batch” and nothing else will, sooner or later, tell a customer their jar came from a batch it did not. For a feature whose entire value is trust, that is the one failure mode we cannot ship. Everything below is built so the right lot stays reachable.

3. Recommendation — Jar Labels: a permanent code that points at a batch

Recommended approach.

Introduce a Jar Label: a small, permanent, user-owned record representing one printed label design. The QR encodes the label; the label points at the batch currently being bottled into it.

Printed label (thousands) → Jar Label code (permanent) → Batch (re-pointed each bottling)
This is a pattern the app already runs in production. QR Tags (docs/feature/qr-tags.md) do exactly this for hives — a permanent HC-XXXXXX badge code reassigned to whichever hive it is stuck to. Same indirection, same reassignment UI, same public-read RLS shape. We are reusing a proven idea, not inventing one.

Scale check — this is small

You need one code per label design, not one per jar. Two jar sizes = two rows in the table, permanently. There is no bulk-generation UI to build and no thousands of codes to manage. That is what keeps this change genuinely small.

The scan flow

Consumer scans the 340 g label ↓ /j/HJ4K7P ↓ get_public_jar_label_info('HJ4K7P') ↓ ● Label facts → product name, jar size, net weight (printed, so always true) ● Current batch → lot code, bottled date, BBD, origins, story, map ● Footer → "Bought a while ago? Find your lot →"

The footer link is the honesty valve, and it costs one line of UI. It opens a short list of this producer’s public batches bottled into that jar size, plus a “type the lot from your jar” box. A customer with a nine-month-old jar reads L-2026-01-003 off the lid and lands on the exact right page.

4. Flexibility: what appears when the QR is scanned

Two independent knobs, both requested.

4a. Resolve mode — which batch is shown

v1 builds current only. A scan shows the batch the label currently points at, with the “find your lot” footer beneath it. That is the behaviour you asked for and it is one render path.

The resolve_mode column is still created, with a CHECK constraint listing all three values, so the other two modes can be switched on later without a migration and without reprinting anything:

ModeWhat a scan showsv1
currentThe batch currently assigned, with the “find your lot” footerBuilt
pickThe lot chooser first: “Which lot code is on your jar?”Deferred — nearly free once the chooser exists, it just renders first
landingProduct and producer story only, no batch claim at allDeferred

Because the code never changes, the mode is switchable at any time on already-printed labels. That is the flexibility the print-in-advance constraint takes away, given back — at the cost of one column today.

4b. Presentation layering — what fields are shown

The public-page copy fields (public_title, public_origin, public_story, show_apiary_image, show_feedback) currently live only on batch_runs, which means retyping them for every single batch. With generic labels that gets worse, not better. Resolve each field through three layers, first non-null wins:

LayerOwnsWhy there
1. Batch (batch_runs)Lot code, bottled date, BBD, origins, floral sources, per-batch story overrideFacts that are only true of this batch
2. Jar Label (trace_labels)Product name, jar size, net weight, default title/origin/story, display togglesFacts printed on the label, plus the presentation that suits this product
3. Producer default (profiles)Fallback title, origin line, story, togglesSet once, inherited by everything

Per-label display toggles let one design read as a rich story page and another as a bare compliance card:

show_story ☑ show_origin_map ☐ show_apiary_image ☑ show_lot_details ☑ show_floral ☑ show_feedback ☐
Net weight stops being a URL hack — and stops being displayed. The jar size and net weight are printed on the label right beside the QR, so the page does not repeat them; there is no ?w={grams} and no Net Weight row. The columns still exist on trace_labels because they identify the design and key the lot chooser (§5) — they are simply not rendered. The existing ?w= deep-link stays in place for legacy batch QRs already on jars in the wild.

5. Proposed schema — one new table

CREATE TABLE trace_labels (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id           UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
  code              TEXT NOT NULL UNIQUE,        -- 'HJ4K7P', unambiguous alphabet
  name              TEXT NOT NULL,               -- 'Wildflower 340 g'
  jar_size_ml       INTEGER,
  jar_weight_g      INTEGER,                     -- printed net weight
  current_batch_id  UUID REFERENCES batch_runs(id) ON DELETE SET NULL,
  resolve_mode      TEXT NOT NULL DEFAULT 'current'
    CHECK (resolve_mode IN ('current', 'pick', 'landing')),  -- only 'current' rendered in v1
  is_active         BOOLEAN NOT NULL DEFAULT true,
  public_title      TEXT,
  public_origin     TEXT,
  public_story      TEXT,
  show_story        BOOLEAN NOT NULL DEFAULT true,
  show_origin_map   BOOLEAN NOT NULL DEFAULT true,
  show_apiary_image BOOLEAN NOT NULL DEFAULT true,
  show_floral       BOOLEAN NOT NULL DEFAULT true,
  show_lot_details  BOOLEAN NOT NULL DEFAULT true,
  show_feedback     BOOLEAN NOT NULL DEFAULT true,
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  assigned_at       TIMESTAMPTZ
);
No assignment-history table in v1. The lot chooser is derived: public batches belonging to this user whose batch_jars rows carry a matching jar_weight_g. That is the same set in practice, and it avoids a second table plus the write path needed to keep it correct. A real history table can be added later if the derived list proves too loose.

Code generation reuses generateTagCode() from src/lib/qr-tags.ts (already excludes 0/O and 1/I/L) with an HJ prefix, so a hand-typed code is unambiguous.

RLS

  • SELECT — public read, same as qr_tags, so the scan page works for any visitor
  • INSERT / UPDATE / DELETE — owner only
  • The public RPC is SECURITY DEFINER and returns batch data only when batch_runs.is_public = true

6. Route and backward compatibility

URLResolvesStatus
/trace/{8-char}A specific batch, as todayUnchanged. Jars already in circulation keep working, forever
/trace/{8-char}?w={g}One jar size within that batchUnchanged
/j/{code}A jar label → its current batchNew
/j/{code}?lot=L-2026-01-003A jar label → that specific batchNew — what the lot chooser links to

A separate /j/ path rather than overloading /trace/: it is shorter (denser QR, so it prints smaller and scans better on a curved jar), and it keeps the two resolvers from having to disambiguate code formats.

The public page is largely shared. get_public_jar_label_info(p_code, p_lot) resolves label → batch and returns the same JSON shape that get_public_batch_info already returns, plus the label block. The existing page component then renders both sources with no fork in the rendering logic.

7. What the printed label carries

+----------------------------------+ | WILDFLOWER HONEY | pre-printed | Pure Irish Honey | pre-printed | | | NET WEIGHT 340 g | pre-printed - one design per size | | | +----------+ LOT ......... | ◀ printed per run, or hand-written | | QR code | BBD ......... | ◀ printed per run, or hand-written | | | | | +----------+ Scan to trace | pre-printed, never changes | this honey | | | | Rico Zmarzly, Co. Galway | pre-printed +----------------------------------+

Only two things vary per batch, and both are on the jar by law anyway (§1): the lot and the best-before date. Whether they are printed into the run or written into the placeholder by hand, they add no cost — and they are what makes the lot fallback in §3 always work.

Everything else on the label — product name, net weight, QR, producer block — is fixed for the life of the design. Two designs, two QR codes, printed once.

8. Alternatives considered

OptionVerdict
Keep per-batch QRs, print labels per batchRejected — defeats the whole point of bulk commercial printing
Static QR to a producer landing page only; consumer always types the lotViable and perfectly honest, but every scan demands typing. Survives as the deferred resolve_mode = 'landing' rather than becoming the default
Pre-print the label body only; apply a QR + lot sticker per batch from the QL-820NWBThe most rigorous option — every jar carries its true batch. Rejected as the default because it puts a per-jar sticker step into every bottling run. Still available: nothing here blocks it, and per-batch QRs keep working
Label points at current batch, no lot fallbackRejected — will eventually show a customer the wrong provenance
Serialised QR per jar (unique code on every label)Rejected — needs variable-data printing and a code-to-batch write per jar. Vastly disproportionate

Plan correction — §4b had the resolution order backwards.
§4b specified batch → label → default. The live data killed it: all 8 public batches already carry a public_title (and a story), so a batch-first rule would mean the label’s copy fields could never fire — dead UI.

Shipped as label → batch → default. It is also strictly more expressive: to use a batch’s own wording you leave the label field blank, whereas batch-first offered no way to make a label title win short of blanking it on every batch. A printed label is a product whose name is on the jar in ink — the page must not contradict it. §4b above is left as written so the change is visible.
One asymmetry worth knowing: the apiary photo is only fetched by get_public_batch_info when the batch has show_apiary_image set, so a label’s photo toggle can hide the photo but never reveal one the batch has switched off. The toggle hint in the form says so rather than leaving the user to discover it.

Date: 21 June 2026  |  Scope: (1) Frequent spurious logouts on flaky mobile connections; (2) Filters / apiary & hive selections not persisting across the app. Status: AWAITING YOUR APPROVAL — no code changed yet.

Part 1 — Spurious Logouts

What actually happens (root causes)

The Supabase client itself is configured correctly (@supabase/ssr v0.7, persistSession, autoRefreshToken, PKCE in src/lib/supabase.ts). The logouts are not a token-refresh bug — they are caused by our own code treating transient network failures as authoritative "you are signed out / deactivated" signals.

CRITICAL — Root cause #1: The 30-second periodic account check forces a logout on any transient error.

src/app/dashboard/layout.tsx:99-123 calls getAccountStatus() every 30s. getAccountStatus() (src/lib/auth.ts:166-211) returns the string 'error' when the profiles query fails — including when the network request simply never completed on a mobile dead-spot. The layout then does if (status !== 'active') → signOut() → router.push('/login'). So a single failed background request while the phone is on a flaky connection logs the user straight out.

This is currently deliberate "fail-closed" behaviour (see the docstring at auth.ts:156-165) so a deactivated account can't linger during a DB outage. The flaw: it cannot tell "the server told me NO" apart from "I couldn't reach the server." Only the former justifies a logout.

HIGH — Root cause #2: onAuthStateChange ignores the event type.

src/contexts/AuthContext.tsx:101-111 uses _event (ignored) and only checks session?.user. It does not distinguish SIGNED_OUT / TOKEN_REFRESHED / token-refresh failures. Any callback delivering a null session clears user immediately, and the dashboard layout (layout.tsx:35-36) redirects to /login with no grace period.

HIGH — Root cause #3: ~26 pages redirect to /login on a transient null.

Pages call getCurrentUserId() (src/lib/auth.ts:7-16), which returns null on a getSession() error exactly as it does for "genuinely logged out". Each page then does if (!id) { router.push('/login') } (e.g. crm/orders/page.tsx:97, dashboard/page.tsx:131, +24 more). No retry.

Typical failure on mobile: on /dashboard/hives -> brief signal drop -> 30s account check's profiles query fails -> getAccountStatus() returns 'error' -> layout: status !== 'active' -> signOut() + push('/login') -> signal returns, but user is already on the login screen

Proposed fix (minimal, surgical)

The principle: only log a user out when we have a positive, server-confirmed reason (real sign-out, confirmed deactivation, or a token we know is expired). Treat "couldn't reach the server" as transient — keep the session, optionally retry.

  • auth.ts: add a distinct 'unreachable' result to AccountStatus (offline / network fetch failure) separate from 'error' (server responded but data missing). Detect via navigator.onLine === false or a fetch/network error shape.
  • layout.tsx (periodic + initial check): treat 'unreachable' as "keep the user signed in, try again next tick" instead of signing out. Keep fail-closed logout only for the authoritative 'deactivated' (and, after N consecutive confirmed failures, 'error') — not for transient unreachable.
  • layout.tsx: add a short grace window / single retry before the if (!user) redirect so a momentary null from a token refresh doesn't bounce the user out.
  • AuthContext.tsx: in onAuthStateChange, only clear user on a genuine signed-out event; ignore spurious null sessions while navigator.onLine === false (re-use the existing tryOfflineFallback logic that already lives in this file).
  • AuthContext.tsx: add an online event listener that calls refreshUser() when connectivity returns, so the session is re-validated cleanly instead of left stale.
  • Open security decision below — how strict to stay on the deactivation check determines exactly how lenient we make this.

Part 2 — Filter / Selection Persistence

Current state (mapped)

There is no shared concept of a "currently selected apiary/hive". Each page manages its own filters, with four inconsistent patterns:

PageFiltersPersisted?
Hivesapiary, ownership, scales, sortsessionStorage (lost on tab close)
Batches / Reportsactive tab / sectionURL params
Queenscompare selection onlypartial (sessionStorage); main filters none
ApiariescategoryFilternone
Recordshive, apiary, period, ownership, type (useRecordFilters)none
Taskstype, category, status, hive, apiary, ownershipnone
Reports (sub-reports)apiary, hive, date rangenone

Existing reusable pattern to follow: the theme provider (src/app/providers/theme-provider.tsx) already does the localStorage + Context + hook pattern cleanly.

Proposed fix

Introduce one small reusable persistence hook and apply it incrementally — no big rewrite. Each filter keeps its existing useState shape; we only swap the initialiser/setter.

  • New src/hooks/usePersistentState.ts: a thin useState wrapper that reads/writes localStorage under a namespaced key (e.g. hivecraic:filters:<page>:<field>), SSR-safe, with a validator callback so a saved apiary/hive id that no longer exists is discarded (re-using the validation idea already in the Hives page). Survives tab close, unlike today's sessionStorage.
  • Optional shared selection decision below: a tiny SelectionContext holding a global "last selected apiary" (and hive) so choosing an apiary on Hives pre-selects it on Records/Tasks/Reports too.
  • Migrate pages one at a time, smallest first, in this order: Apiaries → Tasks → Records (useRecordFilters) → Queens → Reports sub-reports → upgrade Hives from sessionStorage to the shared hook.
  • Each migration: change only the filter declarations; leave all rendering/filtering logic untouched to minimise risk.
  • Update docs/features with the persistence behaviour.

Decisions (confirmed 21 June 2026)

  1. Logout strictness: RELAX for transient errors. Keep the user signed in when the server is unreachable/offline; log out only on confirmed sign-out, server-confirmed deactivation, or known-expired token. Deactivation is still enforced whenever the server is genuinely reachable.
  2. Filter scope: Per-page filters + a shared "last selected apiary/hive" that carries across Hives / Records / Tasks / Reports.
  3. Storage lifetime: localStorage — survives browser/app restart.

Review

Part 1 — Logouts (implemented)

Four small, surgical edits across three files. No behaviour changed except that a server we cannot reach is now treated as transient instead of as a logout.

  • New distinction: 'unreachable' (no authoritative answer — keep the user) vs 'error' (server answered with a problem — still fail-closed).
  • Deactivation still enforced: whenever the server is genuinely reachable, a deactivated/locked account is signed out within ~30s exactly as before. We only relaxed the offline / no-answer case.
  • Grace period: a momentary null user (e.g. mid token-refresh) now waits 1.5s before redirecting; if the session recovers the redirect is cancelled.
  • Recovery: the online event re-validates the session cleanly when connectivity returns.

Not changed (deliberately, to stay minimal): the ~26 page-level getCurrentUserId() redirects. getSession() reads from local storage and does not fail on a network blip for a valid cached session, so these are a much rarer path; the layout/context fixes address the dominant cause. Can revisit if testing shows residual issues.

Please test using the checklist in docs/features/auth-transient-logout-fix.md (DevTools offline toggle past 30s; flaky mobile navigation; server-side deactivation still logs out; manual sign-out still instant).

Part 2 — Filter persistence (implemented, primary pages)

Two reusable primitives plus minimal per-page edits (only filter declarations changed; rendering/filtering logic untouched).

  • usePersistentState — localStorage-backed useState drop-in. Survives navigation and full browser/app restart (the old Hives sessionStorage did not).
  • SelectionContext — shared apiary/hive that carries across pages. Hives and Tasks both bind to it, so picking an apiary on one pre-selects it on the other.
  • Per-page persistence applied to Apiaries, Queens, Tasks, Hives and Records filters.
  • Staleness guarded: a saved apiary/hive that has since been deleted is cleared once data loads, so a user is never stuck staring at an empty list.

Reports extension (done): a small useReportFilters hook gives all 6 report sub-components shared apiary/hive (carries from Hives/Tasks and between reports) plus a per-report persisted date window — existing setFilters(prev => ...) call sites unchanged.

Records shared selection (done): useRecordFilters now sources apiary/hive from SelectionContext while persisting its other filters per-page. Public hook API unchanged (apiary/hive setters route to the shared store, the rest to the persisted store); filters is a memoised composition so downstream filtering memos keep stable deps. All four filter surfaces (Hives, Tasks, Reports, Records) now share one live apiary/hive selection.

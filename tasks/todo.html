Mother queen blank in queen detail / lineage views (multi-breeder batches)

Context

Follow-up to the Queen Tracker fix. The same root cause — multi-breeder batches store the mother per cell in batch_grafts.breeder_queen_id while rearing_batches.mother_queen_id is NULL — meant distributed queen records were created with a blank mother, so the queen detail page, provenance panel, and lineage tree showed no mother.

Fix 1 — forward (code): src/hooks/useGraftDistributions.ts

createQueenForRecipient now resolves the mother per cell:

  • The graft fetch also pulls breeder_queen_id + queens!batch_grafts_breeder_queen_id_fkey(...).
  • The cell’s breeder queen takes precedence; the batch-level mother_queen_id queen is the fallback (single-breeder / legacy).
  • The resolved values feed the snapshot (distributed_mother_queen), subspecies, the lineage dam label, and the self-distribution mother_id FK — all consistently.

The edit-form auto-fill in queens/page.tsx only runs when mother_id is empty; since the FK is now linked at creation for self-distributions, no change was needed there.

Fix 2 — backfill (data): 5 existing distributed queens

Forward fix only helps new distributions, so the 5 already-distributed queens from batch TQRQB_RZ03 were corrected to the values the fixed code would now produce (all self-owned, so mother_id linking is safe):

Out of scope

The mating-nuc creation path (useMatingNucBulk / MatingNucsTab) also seeds mating_nucs.queen_id from the batch mother_queen_id and would behave similarly for multi-breeder batches — a separate feature, not part of the queen detail/lineage view.

Review

  • Root cause fixed, not patched: mother is resolved per cell at the single point of creation, mirroring the Queen Tracker fix.
  • Backward compatible: single-breeder / legacy cells fall back to the batch mother queen; behaviour identical to before.
  • Defensive: null-safe breeder resolution; mother_id still only written for self-distributions (RPC re-checks recipient ownership).
  • Data integrity: backfill scoped by id, ownership-verified, with the 6W update guarded so it could not clobber an already-set value.

TBR Swarm-Prevention Planner

Goal: A live, interactive planner that recommends when to perform a Total Brood Removal (TBR) so the colony, after its induced brood break, rebuilds its forager force to peak across the summer nectar flow (e.g. bramble/blackberry) — bridging the gap between the early spring crop and the summer crop while controlling swarming.

Decisions locked: Placement = card on the existing /dashboard/tools page · Persistence = live calculator only (no DB writes) · Crop dates = 3-tier resolution · Prediction = GDD-projection (early/late aware) · Optimisation = maximise foragers across the summer flow.

1. The biological model

Day T = the day TBR is performed (all brood removed, foundation/empty comb given). The model is a simple daily cohort simulation driven by a handful of adjustable constants:

ConstantDefaultMeaning
Re-lay delay4 daysTime for the colony to draw enough comb before the queen resumes laying (T+4).
Egg → emergence21 daysWorker development. First new brood emerges at T+25.
Emergence → forager21 daysHouse-bee phase. First new foragers at T+46.
Queen lay rate1200 eggs/dayAdjustable 1000–1500 (slider). Sets the rebuild slope.
Forager active span21 daysHow long a bee forages before dying — governs how fast the standing force decays during the gap.

Key derived milestones from T

Forager-force curve (what the chart shows)

For each day d we sum the cohorts that are currently in the foraging window:

  • emergence(d) = steady rate L for d < T; 0 for T ≤ d < T+25 (brood gap); L for d ≥ T+25 (rebuild).
  • foragers(d) = sum of emergence(e) for every e where e + 21 ≤ d < e + 21 + 21.

This produces: a steady force → a decline through the gap (the standing force ages out and is not replaced from ~T+21) → a trough around T+42–46 → recovery from T+46. The "bridge" the beekeeper relies on is visible as foragers keep being recruited from already-emerged house bees up to ~T+21.

Scoring & recommendation

For each candidate T the model scores the average forager force across the summer-flow window [flowStart, flowEnd], subject to T ≥ spring-crop end (so the spring crop is harvested first). The recommended T* is the date that maximises that score. The beekeeper can then drag the TBR slider away from T* and watch the score and curve respond.

2. Crop-date resolution (3 tiers, per apiary)

Location is mandatory — the beekeeper picks the apiary first; the GDD curve, observed dates and the 2–3 week regional spread all flow from it. The spring/summer crops are selectable (rapeseed-led in the east, dandelion-led in the west).

TierSourceUsed when
1 — ObservedThe apiary's actual gdd_records.start_date for that crop, this season.A record already exists this year → use the date directly.
2 — Averaged + projectedHistorical average GDD-at-bloom for that crop at that apiary, projected onto this year's GDD accumulation curve.Prior-year history exists but no record yet this season. Warm year → earlier date.
3 — General estimatevegetation_info.typical_gdd_range midpoint + bloom_period, projected onto this location's GDD curve.No history at all for that crop at that apiary.

GDD projection (how Tier 2/3 turn a GDD threshold into a date)

  • Accumulated GDD to today comes from the existing fetchCurrentYearGDD(lat, lon) in src/lib/gdd.ts.
  • Forward projection uses the location's recent average daily GDD accrual (keeps it simple and within existing Open-Meteo data — no new API). A warm season raises both the accumulated total and the daily rate, so the predicted bloom date pulls earlier automatically.
  • Predicted date = today + (targetGDD − accumulatedGDD) / dailyRate. Each resolved crop date carries a tier badge so the beekeeper knows how confident it is.

3. Interface

  • Apiary picker (required) and spring-crop / summer-flow pickers, pre-filled from what the apiary actually has records for.
  • Forager-force chart (Chart.js — already installed): the forager curve over the season with shaded bands for spring crop, the brood gap, and the summer flow.

What was built: a live "TBR Swarm Planner" tool, reachable from Dashboard → Tools → Hive Health → TBR Swarm Planner. No database changes, no new dependencies.

Files

  • NEW src/types/tbr.ts — model interfaces & default constants.
  • NEW src/lib/tbr-model.ts — pure model: UTC-safe date maths, the forager-force cohort simulation (closed-form gap overlap), flow-coverage scoring, optimal-date search, and the 3-tier crop-date resolver with GDD projection.
  • NEW src/hooks/useTbrPlanner.ts — loads apiaries + vegetation reference + per-apiary GDD records, fetches the apiary's GDD accumulation & recent daily rate from Open-Meteo, auto-selects sensible default crops, and assembles the plan.
  • NEW src/components/tools/TBRPlanner.tsx — apiary & crop pickers with tier badges, the recommendation panel, the Chart.js forager-force curve (custom canvas plugin shades the spring-crop & summer-flow bands and draws TBR / first-forager marker lines), the TBR-date and lay-rate sliders, milestone cards, and an advanced disclosure for the biological constants.
  • EDIT src/app/dashboard/tools/page.tsx — added the tbr section (type, URL whitelist, card, tab).
  • NEW docs/features/tbr-swarm-planner.md.

Defensive choices

  • All simulation loops are bounded (MAX_SIM_DAYS); out-of-order date ranges return empty/zero instead of looping.
  • Open-Meteo fetch is abortable, time-guarded and falls back gracefully — if a location has no coordinates and no records, the UI explains why no plan can be shown rather than failing.
  • GDD projection clamps a non-positive daily rate to avoid divide-by-zero; "already reached" thresholds are surfaced honestly rather than back-dated.
  • User crop/apiary choices are preserved against the auto-default logic via refs.

Caveats

  • Forward GDD projection uses recent average daily accrual (not a live forecast) — simple and location-aware; can be upgraded to the Open-Meteo 16-day forecast later if wanted.
  • Spring-crop and summer-flow window lengths default to 30 / 35 days (SPRING_CROP_DURATION_DAYS / SUMMER_FLOW_DURATION_DAYS).
  • Per project rule, the production build was not run here — please test in the app.

Post-build audit hardening

  • Critical: parseISODate/toISODate hardened so a malformed date (e.g. a bad gdd_records.start_date) degrades to the epoch instead of throwing RangeError and crashing the render.
  • High: GDD projection now anchors on the archive's real last date (asOf) — removing the ~5-day late bias — and falls back to the season's average daily accrual instead of a meaningless 1 GDD/day.
  • High: a spring crop dated after the summer flow is now ignored (band suppressed) rather than corrupting the plan bounds.
  • Medium: latitude/longitude coerced & validated (PostgREST can return numeric as string); failed record fetches are now logged; the monotonic recommendation invariant is documented.

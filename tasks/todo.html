Nuc brood evidence does not clear the “Virgin Queen” status

Reported: 16 August 2026 · Status: awaiting approval

1. Symptom

Mating nuc 138 has an inspection dated 16/08/2026 recording Queen Seen and Eggs, yet the nuc card still shows the purple Virgin Queen badge. The same queen, once distributed, is written into the recipient’s records as a virgin queen (see queen 41 on hive 65-HMN+, badge “Virgin”).

2. Root cause (confirmed against the live database)

The nuc status auto-sync in src/components/batches/NucInspectionPanel.tsx (handleSubmit, lines 176–223) branches only on the explicit Queen Status dropdown (formData.queen_status). The brood-evidence checkboxes — Eggs Present, Larvae Present, Capped Brood — are saved to the row but never influence the status.

When the beekeeper ticks “Queen Seen” + “Eggs Present” and leaves the dropdown on “Select status”, queen_status is null, no branch fires, and the nuc keeps whatever status it had — virgin.

How that leaks into distribution and the recipient’s queen record

nuc inspection (eggs, no dropdown status) | status sync ignores brood evidence v mating_nucs.status = 'virgin' (should be 'mating' / "Mated") batch_grafts.status = 'in_nuc'/'emerged' (should be 'mated') | DistributeGraftModal: TYPE_FROM_GRAFT_STATUS[graft status] v graft_distributions.distribution_type = 'virgin_queen' (should be 'mated_queen') | createQueensForRecipient(...) v queens.status = 'virgin', queens.mated_date = null --> "Virgin" badge on the hive card

This is exactly what happened to queen 41: source nuc 172, inspection 16/08/2026 with eggs and a blank dropdown, distributed the same day as virgin_queen.

Secondary defect found

getNucDistributionType() in MatingNucsTab.tsx:125 returns virgin_queen for a nuc whose status is mating — but the UI labels mating as “Mated” (NUC_STATUSES, line 110). Only laying maps to mated_queen. This is the fallback used when the graft row is missing, so a nuc shown as “Mated” can still be distributed as a virgin.

3. Proposed fix

Rule: eggs or larvae in a mating nuc are proof the queen is mated. When an inspection records them and the beekeeper leaves the Queen Status dropdown blank, treat the inspection as mated — the nuc badge becomes Mated. No new status is introduced.

An explicit dropdown choice always wins — the derivation only fills the gap when the dropdown is empty. This fixes the reported case without ever overriding what the beekeeper deliberately selected.

Change 1 — derive the status (2 call sites, ~6 new lines)

Add one small helper in NucInspectionPanel.tsx:

// Eggs or larvae in a mating nuc prove the queen is mated.
// Only used when the beekeeper left the Queen Status dropdown blank.
const deriveQueenStatus = (
  status: string | null,
  eggs: boolean,
  larvae: boolean
): string | null => {
  if (status) return status
  return eggs || larvae ? 'mated' : null
}
  • ☐ Use it in handleSubmit where const qs = formData.queen_status is read (line 177).
  • ☐ Use it in handleDelete’s recalculation loop (line 272), so deleting an inspection recomputes the nuc from the same rule. This requires adding eggs_present, larvae_present to the select on line 254.

Existing behaviour is untouched: mated already maps to nuc status mating (badge “Mated”), mating_confirmed_at = inspection date, and graft status mated.

Change 2 — fix the distribution-type fallback (1 line)

const getNucDistributionType = (status: string): 'virgin_queen' | 'mated_queen' => {
  if (status === 'laying' || status === 'mating') return 'mated_queen'
  return 'virgin_queen'
}

6. Review

Completed 16 August 2026. Decisions taken: brood rule = eggs or larvae (capped brood excluded); full backfill approved.

Revision after first review. The first pass derived laying. On feedback this was changed to mated: all we need to know from brood evidence is that the queen is mated, so the nuc shows the existing Mated badge and no extra status is brought into play. The three backfilled nucs were moved from laying to mating to match. Downstream behaviour is identical either way — both stamp mating_confirmed_at and advance the graft to mated.

Code changes

src/components/batches/NucInspectionPanel.tsx — new helper, applied at both sync points:

// Eggs or larvae in a mating nuc prove the queen is mated. Only applied when the beekeeper
// left the Queen Status dropdown blank — an explicit choice always wins.
// Capped brood is excluded: a nuc is often seeded with a frame of capped brood at setup.
// Unrecognised stored values are treated as "no explicit choice" so they cannot silently
// suppress the evidence-based fallback, and the result is always a known status.
const deriveQueenStatus = (status: string | null, eggs: boolean, larvae: boolean): string | null => {
  if (status && QUEEN_STATUSES.includes(status)) return status
  return eggs || larvae ? 'mated' : null
}
  • handleSubmit — const qs = deriveQueenStatus(formData.queen_status || null, formData.eggs_present, formData.larvae_present). Everything downstream is unchanged: mated already sets nuc status mating (badge “Mated”), stamps mating_confirmed_at, and advances the graft to mated. No new status is introduced.
  • handleDelete — same helper inside the replay loop, and the select widened to fetch eggs_present, larvae_present so deleting an inspection recomputes the nuc by the identical rule.

src/components/batches/MatingNucsTab.tsx — getNucDistributionType now returns mated_queen for mating as well as laying, matching the “Mated” label the UI already shows.

Four production lines changed in total. No schema change, no new component, no new dependency.

Two deviations from the original plan, both deliberate:
  • Nuc A5 was left as virgin — correctly. It had brood in June/July, but its latest inspection (25/07/2026) explicitly selects “Virgin” and re-stamps queen_emerged_at — a supersedure. The new rule never overrides an explicit choice, so virgin is the right answer and the record was not touched.
  • Nuc “Mini - Nuc 1” was added. Its last inspection explicitly says “Mated” with eggs and mating_confirmed_at was already stamped, yet the status had been left on virgin — a stale status from a separate cause. Corrected to mating.
  • The mated_at_eircode on queens 41 and 47 was left as the real eircode. The existing promote_distributed_queen_on_mating RPC would have overwritten it with the distribution’s mating_location (“AP03 - Stephen”, an apiary name rather than an eircode) — that quirk was not replicated.

Verification queries after the backfill returned zero rows for both “nucs whose latest inspection derives to mated/laying but are still pre-mated” and “queens still marked virgin”.

Storage Cleanup for Replaced and Deleted Photos

Status: implemented, needs CRON_SECRET in Vercel  ·  Date: 4 September 2026

Your instruction: “now fix the storage cleanup for replaced and deleted photos” — the follow-up I deliberately left out of the multi-photo work.

1. Why the obvious fix is the wrong one

The obvious fix is to delete the object next to each .delete() and each replacement, the way DiagnosisImagesTab.tsx:111-143 does. That cannot work here, and the reason is in the schema:

inspections.hive_id    -> hives     ON DELETE CASCADE
varroa_checks.hive_id  -> hives     ON DELETE CASCADE
inspections.user_id    -> profiles  ON DELETE CASCADE

Deleting one hive (hives/page.tsx:137-141) removes every inspection and varroa check beneath it entirely inside the database. No client code sees those rows, so no client-side handler can ever clean up after them. This is the single biggest leak in the app and it is invisible to the approach above.

Worse, hard_delete_user (UserManagement.tsx:674) purges every record a user owns. After it runs the user no longer exists, so nothing running as that user could ever tidy up. Any design that depends on the owner being present is structurally incapable of handling it.

So the capture has to happen where the deletion actually happens: in the database.

2. Design — capture in Postgres, delete from a scheduled job

row deleted / photo replaced queue row nightly (client, cascade, or RPC) --> storage_cleanup_queue --> /api/cron/storage-cleanup AFTER trigger (url, queued_at) service role, batch remove | still referenced? ------+--> skip & drop from queue older than grace? ------+--> remove object

S1 — One URL → (bucket, path) helper

Today that derivation is a bare split() duplicated in two places (upload-image.ts:66, DiagnosisImagesTab.tsx:117). Add storagePathFromPublicUrl() to src/lib/storage-url.ts, splitting on the /storage/v1/object/public/ constant rather than the bucket name, stripping query and hash, decoding percent-encoding, and — the important part — returning null when the host is not the current project. Legacy rows carry an old Supabase hostname; those objects live in a different project and must never be passed to a delete call here.

S2 — The queue table and triggers

CREATE TABLE public.storage_cleanup_queue (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  image_url    text NOT NULL UNIQUE,   -- UNIQUE makes re-queuing idempotent
  source_table text NOT NULL,
  queued_at    timestamptz NOT NULL DEFAULT now(),
  attempts     int NOT NULL DEFAULT 0,
  last_error   text
);

One generic trigger function, told by TG_ARGV which column(s) to watch and whether each is text or text[]:

  • AFTER DELETE — queue every URL on the old row.
  • AFTER UPDATE — queue every URL present in OLD but absent in NEW. That is exactly the “replaced or removed” case, and for inspections.image_urls it is a plain array difference.

Applied to all six image-bearing tables: inspections, varroa_checks, apiaries, wild_colonies (two columns), wild_colony_inspections, diagnosis_images. Because it fires in the database it catches client deletes, FK cascades, hard_delete_user and any future RPC alike — without any of them knowing it exists.

RLS on, no policies: this is machinery, not user data, and only the service role touches it.

S3 — The sweeper

src/app/api/cron/storage-cleanup/route.ts, service role, authorised by CRON_SECRET, registered as a nightly job in vercel.json (which currently declares no crons). It takes a batch, derives bucket and path with the S1 helper, removes them per bucket in one call, deletes the queue rows that succeeded, and records attempts/last_error on the ones that did not, so a persistent failure is visible rather than silent.

S4 — The two safety rails that matter

  1. Never delete a URL a row still references. Before removing anything the sweeper re-checks the six tables via one SQL function. A photo can legitimately come back — an update queues a URL and a later edit restores it — and deleting a live photo is far worse than leaving an orphan. This is the single most important line in the design.
  2. A grace period. Only act on rows queued more than N days ago, so a mistaken delete is recoverable for that window. Orphaned photos cost pennies; a destroyed one is gone.

S5 — Simplify the one existing implementation

DiagnosisImagesTab.tsx:111-143 deletes the storage object first and the row second, and swallows the storage error. If the row delete then fails, the row survives pointing at a deleted object — a permanently broken image, which is worse than an orphan. With the trigger in place that code becomes “delete the row” and the queue handles the rest.

3. What this deliberately does not cover

Uploads that never reached a row are invisible to a database trigger. The inspection form already cleans those up (records/page.tsx:781, 847, 913), but the apiary, varroa-check, wild-colony and diagnosis upload flows have no equivalent — a failed save after a successful upload still orphans there. That is a separate, smaller fix in four flows; I will flag it, not fold it in.

4. One thing I noticed and am not treating as a bug

The comment at records/page.tsx:829 says image_urls[1] and useRecordsData.ts:216 uses imageUrls[0]. Both are correct — Postgres arrays are 1-indexed, JavaScript arrays are 0-indexed, and they refer to the same first photo. No change needed.

5. Decisions I need from you

Three, asked alongside this plan. My recommendations: all six tables (the trigger is one function either way), a 7-day grace period, and yes to tightening the storage policy — today any signed-in user can delete any object in inspection-images, including other beekeepers' photos, and once cleanup is server-side the app no longer needs that permission.

8. Review

What changed

Five MCP migrations, one new API route, four changed files. Photos that are replaced, removed, or whose record is deleted now leave Storage too.

PieceWhat it does

Verified against the live database

All on throwaway probe tables, dropped afterwards. Array diff on replace, full set on delete, scalar replace, and — the one that matters — a row removed by an FK cascade queued its photo, which is the case no client-side fix could ever reach. An edit touching no photo queues nothing. A photo removed then restored is correctly reported as still referenced and skipped.

The audit: 24 orphans, 94 MB

About 17% of your 541 MB of image storage was already waste from past deletes. Those objects were queued, not deleted, so they pass through the same guard and the same 7-day grace as everything else.

The storage hole you approved closing

Both buckets allowed any authenticated user to delete or update any object — one beekeeper could have deleted another's photos. Replaced with a single owner-scoped policy (owner = auth.uid()), which is exactly what the client's own partial-upload undo needs and nothing more.

QA audit — four findings, fixed

  1. High: the sweeper could be aimed at any bucket. Queued URLs come from user-editable columns, so a crafted value could name a bucket the guard does not protect — and the sweeper bypasses RLS. Now an explicit allowlist.
  2. High: 200 sequential round-trips per run. One batched SQL call now answers the whole batch, and a failure there aborts the run rather than silently skipping.
  3. Medium: a permanently failing object was retried nightly forever; now capped, with last_error kept for inspection.
  4. Low: constant-time secret comparison, de-duplication of two URLs resolving to one object, and a set instead of a linear scan.

Verification

tsc clean in src/; eslint clean; records tests 32 passed; get_advisors reports nothing new beyond an INFO note that the queue table has RLS with no policies, which is the intended deny-all. Both new functions are executable by service_role only.

Over to you — one thing blocks this in production

CRON_SECRET must be set in the Vercel project. Vercel sends it as a bearer token to scheduled routes; without it the route returns 500 and the sweep never runs. Nothing is deleted until you set it — the safe failure direction. Once set, the 24 backfilled orphans are removed on the first run after their 7 days elapse (11 September).

Scope note

Uploads that never reached a row stay uncovered outside the inspection form — a database trigger cannot see them. The apiary, varroa-check and wild-colony upload flows still orphan on a failed save after a successful upload. Separate, smaller fix; flagged not folded in.

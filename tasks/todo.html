Reusable jar-label QR codes for honey provenance

Raised: 27 August 2026 · Status: decisions locked (§10) — awaiting go-ahead, nothing built yet

Decisions taken 27 August 2026.
  • Two label designs — one per jar size. Two rows in the table, permanently.
  • Lot and BBD go on the label — either printed into the run, or hand-written into a printed placeholder. Either way the lot is on the jar, so the exact-batch fallback always works.
  • current is the resolve mode, and the only one built in v1.
  • The public page does not repeat the jar size — it is printed beside the QR already.

1. The problem

Today the QR code is minted per batch. BatchesTab.tsx:605 builds:

https://www.hivecraic.com/trace/{trace_code}[?w={net_weight_g}]

… where trace_code is an 8-character code stored on the batch row (batch_runs.trace_code), and ?w= narrows the public page to one jar size within that batch.

That model assumes one print run per batch. The new requirement inverts it:

  • Labels are printed commercially, in large quantities, well in advance.
  • There is one label design per jar size (e.g. 227 g, 340 g, 454 g).
  • Each design will be applied across many batches over months or years.

So the QR can no longer name a batch. It must name something permanent, and the batch has to be resolved at scan time.

Two facts still have to be physically on the jar — and this shapes the whole design.
The lot mark and the best-before date are mandatory on-pack information under EU food labelling rules; a QR pointing at a web page does not satisfy either. Both change per batch, so either the print run is batch-specific, or the label carries a printed placeholder that is written in at bottling.

Confirmed: lot and BBD will be printed into the run or hand-written into a placeholder. Either way the lot code is on the jar. That gives a guaranteed fallback — a consumer can always identify their exact batch by reading it — which is what makes the whole scheme safe rather than a guess. (Still worth confirming the exact format requirement with your packaging supplier before committing to a run.)

2. What we can and cannot honestly promise a scanner

This is the crux, and it drives the recommendation.

ScenarioCan a static QR resolve it correctly?
Jar bought this week, from current stockYes — the label points at whatever is being bottled now
Jar bought in March, scanned in SeptemberNo — the label has since moved on to a later batch

A design that silently shows “the current batch” and nothing else will, sooner or later, tell a customer their jar came from a batch it did not. For a feature whose entire value is trust, that is the one failure mode we cannot ship. Everything below is built so the right lot stays reachable.

3. Recommendation — Jar Labels: a permanent code that points at a batch

Recommended approach.

Introduce a Jar Label: a small, permanent, user-owned record representing one printed label design. The QR encodes the label; the label points at the batch currently being bottled into it.

Printed label (thousands) → Jar Label code (permanent) → Batch (re-pointed each bottling)
This is a pattern the app already runs in production. QR Tags (docs/feature/qr-tags.md) do exactly this for hives — a permanent HC-XXXXXX badge code reassigned to whichever hive it is stuck to. Same indirection, same reassignment UI, same public-read RLS shape. We are reusing a proven idea, not inventing one.

Scale check — this is small

You need one code per label design, not one per jar. Two jar sizes = two rows in the table, permanently. There is no bulk-generation UI to build and no thousands of codes to manage. That is what keeps this change genuinely small.

The scan flow

Consumer scans the 340 g label ↓ /j/HJ4K7P ↓ get_public_jar_label_info('HJ4K7P') ↓ ● Label facts → product name, jar size, net weight (printed, so always true) ● Current batch → lot code, bottled date, BBD, origins, story, map ● Footer → "Bought a while ago? Find your lot →"

The footer link is the honesty valve, and it costs one line of UI. It opens a short list of this producer’s public batches bottled into that jar size, plus a “type the lot from your jar” box. A customer with a nine-month-old jar reads L-2026-01-003 off the lid and lands on the exact right page.

4. Flexibility: what appears when the QR is scanned

Two independent knobs, both requested.

4a. Resolve mode — which batch is shown

v1 builds current only. A scan shows the batch the label currently points at, with the “find your lot” footer beneath it. That is the behaviour you asked for and it is one render path.

The resolve_mode column is still created, with a CHECK constraint listing all three values, so the other two modes can be switched on later without a migration and without reprinting anything:

ModeWhat a scan showsv1
currentThe batch currently assigned, with the “find your lot” footerBuilt
pickThe lot chooser first: “Which lot code is on your jar?”Deferred — nearly free once the chooser exists, it just renders first
landingProduct and producer story only, no batch claim at allDeferred

Because the code never changes, the mode is switchable at any time on already-printed labels. That is the flexibility the print-in-advance constraint takes away, given back — at the cost of one column today.

4b. Presentation layering — what fields are shown

The public-page copy fields (public_title, public_origin, public_story, show_apiary_image, show_feedback) currently live only on batch_runs, which means retyping them for every single batch. With generic labels that gets worse, not better. Resolve each field through three layers, first non-null wins:

LayerOwnsWhy there
1. Batch (batch_runs)Lot code, bottled date, BBD, origins, floral sources, per-batch story overrideFacts that are only true of this batch
2. Jar Label (trace_labels)Product name, jar size, net weight, default title/origin/story, display togglesFacts printed on the label, plus the presentation that suits this product
3. Producer default (profiles)Fallback title, origin line, story, togglesSet once, inherited by everything

Per-label display toggles let one design read as a rich story page and another as a bare compliance card:

show_story ☑ show_origin_map ☐ show_apiary_image ☑ show_lot_details ☑ show_floral ☑ show_feedback ☐
Net weight stops being a URL hack — and stops being displayed. The jar size and net weight are printed on the label right beside the QR, so the page does not repeat them; there is no ?w={grams} and no Net Weight row. The columns still exist on trace_labels because they identify the design and key the lot chooser (§5) — they are simply not rendered. The existing ?w= deep-link stays in place for legacy batch QRs already on jars in the wild.

5. Proposed schema — one new table

CREATE TABLE trace_labels (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id           UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
  code              TEXT NOT NULL UNIQUE,        -- 'HJ4K7P', unambiguous alphabet
  name              TEXT NOT NULL,               -- 'Wildflower 340 g'
  jar_size_ml       INTEGER,
  jar_weight_g      INTEGER,                     -- printed net weight
  current_batch_id  UUID REFERENCES batch_runs(id) ON DELETE SET NULL,
  resolve_mode      TEXT NOT NULL DEFAULT 'current'
    CHECK (resolve_mode IN ('current', 'pick', 'landing')),  -- only 'current' rendered in v1
  is_active         BOOLEAN NOT NULL DEFAULT true,
  public_title      TEXT,
  public_origin     TEXT,
  public_story      TEXT,
  show_story        BOOLEAN NOT NULL DEFAULT true,
  show_origin_map   BOOLEAN NOT NULL DEFAULT true,
  show_apiary_image BOOLEAN NOT NULL DEFAULT true,
  show_floral       BOOLEAN NOT NULL DEFAULT true,
  show_lot_details  BOOLEAN NOT NULL DEFAULT true,
  show_feedback     BOOLEAN NOT NULL DEFAULT true,
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  assigned_at       TIMESTAMPTZ
);
No assignment-history table in v1. The lot chooser is derived: public batches belonging to this user whose batch_jars rows carry a matching jar_weight_g. That is the same set in practice, and it avoids a second table plus the write path needed to keep it correct. A real history table can be added later if the derived list proves too loose.

Code generation reuses generateTagCode() from src/lib/qr-tags.ts (already excludes 0/O and 1/I/L) with an HJ prefix, so a hand-typed code is unambiguous.

RLS

  • SELECT — public read, same as qr_tags, so the scan page works for any visitor
  • INSERT / UPDATE / DELETE — owner only
  • The public RPC is SECURITY DEFINER and returns batch data only when batch_runs.is_public = true

6. Route and backward compatibility

URLResolvesStatus
/trace/{8-char}A specific batch, as todayUnchanged. Jars already in circulation keep working, forever
/trace/{8-char}?w={g}One jar size within that batchUnchanged
/j/{code}A jar label → its current batchNew
/j/{code}?lot=L-2026-01-003A jar label → that specific batchNew — what the lot chooser links to

A separate /j/ path rather than overloading /trace/: it is shorter (denser QR, so it prints smaller and scans better on a curved jar), and it keeps the two resolvers from having to disambiguate code formats.

The public page is largely shared. get_public_jar_label_info(p_code, p_lot) resolves label → batch and returns the same JSON shape that get_public_batch_info already returns, plus the label block. The existing page component then renders both sources with no fork in the rendering logic.

7. What the printed label carries

+----------------------------------+ | WILDFLOWER HONEY | pre-printed | Pure Irish Honey | pre-printed | | | NET WEIGHT 340 g | pre-printed - one design per size | | | +----------+ LOT ......... | ◀ printed per run, or hand-written | | QR code | BBD ......... | ◀ printed per run, or hand-written | | | | | +----------+ Scan to trace | pre-printed, never changes | this honey | | | | Rico Zmarzly, Co. Galway | pre-printed +----------------------------------+

Only two things vary per batch, and both are on the jar by law anyway (§1): the lot and the best-before date. Whether they are printed into the run or written into the placeholder by hand, they add no cost — and they are what makes the lot fallback in §3 always work.

Everything else on the label — product name, net weight, QR, producer block — is fixed for the life of the design. Two designs, two QR codes, printed once.

OptionVerdict
Keep per-batch QRs, print labels per batchRejected — defeats the whole point of bulk commercial printing
Static QR to a producer landing page only; consumer always types the lotViable and perfectly honest, but every scan demands typing. Survives as the deferred resolve_mode = 'landing' rather than becoming the default
Pre-print the label body only; apply a QR + lot sticker per batch from the QL-820NWBThe most rigorous option — every jar carries its true batch. Rejected as the default because it puts a per-jar sticker step into every bottling run. Still available: nothing here blocks it, and per-batch QRs keep working
Label points at current batch, no lot fallbackRejected — will eventually show a customer the wrong provenance

Addendum — payment links on the scan page

Raised: 27 August 2026 · Status: decisions locked (A1) — awaiting go-ahead, nothing built

The customer already has their phone out and is on your page. The second sticker was solving a problem the QR has now made unnecessary, so folding payment into the scan is the right instinct.

Decisions taken 27 August 2026.
  • Pay for this jar — honesty box / farm gate / market stall. Panel sits above the provenance with the price shown large.
  • Direct sales only, no shops — so there is no retailer to undercut, and new labels can default to payment on.
  • Jar labels only — /trace/ is untouched. No producer-level payment config needed.

A1. What this is, and what follows from it

This is a point-of-sale feature, not a reorder feature. The customer is standing at the stall holding the jar. That drives three things:

  • Placement is top, above the provenance card — paying is why they scanned; the story is a bonus they read afterwards.
  • The amount must be on screen. Not optional: with a Revolut link the payer types the amount themselves, so the displayed price is the only thing telling them what to send. Getting this wrong means underpayment, silently.
  • It has to work outdoors on a phone in sunlight — large amount, large buttons, high contrast. The 50+ eyesight rule applies with a stall-in-a-field multiplier.

Because only one mode is wanted, no payment_mode column is needed — one fewer thing to build and explain.

A2. Do not construct the provider URLs — store the ones you paste

This is the single most important implementation decision.

It is tempting to store a Revolut username and build revolut.me/<name>/<amount>. Don’t. Each provider has its own link format, they change them, and amount syntax differs per provider. Storing the finished link you generated in their own app means:

  • Stripe and SumUp links already carry the price, currency and product name — no duplication of your pricing in two places
  • A provider changing its URL format cannot break your printed labels
  • Adding a fourth provider later is a config change, not a code change
The three behave differently, and that is fine:
  • Stripe — a Payment Link is per price, so you generate one per jar size. Fixed amount, card + wallets.
  • SumUp — same shape: a payment link per amount.
  • Revolut — a personal revolut.me link is per person, not per price; the payer types the amount. This is why the display price in A4 matters: with Revolut it is the only thing telling them what to send.
Exact hostnames should be taken from your real links when you paste them, not guessed here.

A3. Where the configuration lives

On the jar label, because a label already is one jar size — and one jar size is one price. A 227 g and a 454 g label want different Stripe links and different displayed amounts, which falls out for free.

Producer-level defaults were considered and rejected for v1: with two label designs, pasting a Revolut link twice is not a problem worth a second layer of resolution to solve. Add it later if the repetition ever bites.

A4. Schema — five columns on trace_labels

ALTER TABLE trace_labels
  ADD COLUMN show_payment      BOOLEAN NOT NULL DEFAULT false,
  ADD COLUMN payment_revolut_url TEXT,
  ADD COLUMN payment_stripe_url  TEXT,
  ADD COLUMN payment_sumup_url   TEXT,
  ADD COLUMN payment_amount    NUMERIC(10,2),   -- display only, never enforced
  ADD COLUMN payment_currency  TEXT NOT NULL DEFAULT 'EUR',
  ADD COLUMN payment_note      TEXT;            -- "Collection from Athenry"

The column default stays false so nothing created outside the form can start asking for money by accident; the form defaults a new label to on, since there is no retail channel to protect. The panel is hidden anyway until a valid link exists, so an on-by-default toggle changes nothing visible until it is configured.

payment_amount is required whenever show_payment is on — enforced in the form, for the Revolut reason in A1. It stays display-only in the database: Stripe and SumUp enforce their own amounts, and we must never imply we have verified a payment.

Naming matters here. profiles.stripe_customer_id already exists and is HiveCraic’s own subscription billing — you paying for the app. The beekeeper’s Stripe account for selling honey is an unrelated thing. Keeping every new column under a payment_* prefix on trace_labels keeps the two from ever being wired together by mistake.

A5. Security — the part that is not optional

🔴 An unvalidated URL here turns HiveCraic into a phishing redirect.
trace_labels is user-editable and /j/ is public and unauthenticated. Without validation, any user could paste any URL and use a page on your domain — carrying your trust badge and a producer’s name — to lend credibility to a fake payment page. That is a reputational problem for HiveCraic, not just for the one account.

Mitigations, all cheap:

  1. Hostname allowlist, enforced in a DB CHECK and in the form. Only known payment domains accepted; anything else is rejected at save time with a clear message. Derive the exact list from your real links.
  2. HTTPS only — reject any http:// link.
  3. Never collect card details on our page. We render a link out to the provider’s own domain and nothing more. No iframes, no embedded fields, no payment data touching HiveCraic. This also keeps PCI scope at zero.
  4. rel="noopener noreferrer" on the outbound link.
  5. Show the destination — a small “you will be taken to Stripe to pay securely” line. A payment button appearing after a QR scan is exactly the shape of a scam, so naming the destination is what separates yours from one.

A6. Retail channel — not a concern here

Confirmed direct sales only, so there is no retailer to undercut and payment can be on for every design. The per-label toggle is kept anyway: it costs one boolean, and the day a shop does take stock, turning payment off for that design is the whole fix.

A6b. What we must never imply

We are showing a link, not taking a payment. HiveCraic never learns whether the customer actually paid — Revolut, Stripe and SumUp all settle outside the app.

So the page must never say “paid”, show a tick, or otherwise imply confirmation, and the Jar Labels UI must not grow a “payments received” view that looks like a ledger it cannot honestly keep. If you ever want reconciliation, that is a Stripe/SumUp webhook feature and a much bigger piece of work — worth naming now so it is not half-built by accident.

A7. What it looks like

┌──────────────────────────────────┐ │ Pay for this jar │ │ Wildflower Honey · 340 g │ │ │ │ € 8.00 │ │ │ │ [ Pay by card ] [ Revolut ] │ │ │ │ Collection from Athenry. │ │ You'll be taken to Stripe to │ │ pay securely. │ └──────────────────────────────────┘
  • One button per configured provider — label them by what the customer recognises (“Pay by card” for Stripe/SumUp, “Revolut” for Revolut), not by our column names.
  • Large touch targets and a large amount — the same reduced-eyesight audience applies, often outdoors in sunlight.
  • Whole panel hidden unless show_payment is on and at least one valid link is set.

Addendum B — payment methods on the profile

Raised: 27 August 2026 · Status: proposal, awaiting go-ahead

Right now the three links are pasted per jar label. With two designs that means pasting the same Revolut link twice, and it puts an account-level fact in a product-level place. Moving the accounts to the profile is right.

B1. What moves, and what does not

Lives onHoldsWhy there
ProfileThe three account links, an enable switch, default currencyThese are who you are paid as. They do not vary by jar
Jar labelshow_payment, payment_amount, note, and optional per-size link overridesThe price is per jar size, so it cannot live on the profile
Why the override still has to exist. A Stripe Payment Link is per price — a 227 g and a 454 g jar need different links, so a single profile-level Stripe link cannot serve both. Revolut is the opposite: one revolut.me link per person, with the payer typing the amount.

So: the profile holds the default, and a label may override it. Resolution is label link ?? profile link — the same override idiom already used for the copy fields, not a new concept to learn. In practice you would set Revolut once on the profile and never touch it, and set a Stripe link per label.

B2. Naming — keep well clear of the app’s own billing

profiles already carries stripe_customer_id, and /api/stripe/webhook already exists — both for HiveCraic’s own subscription billing, on HiveCraic’s Stripe account. Your honey-selling Stripe account is a completely different thing.

New profile columns therefore use a sales_ prefix, not payment_ or stripe_, so nobody can ever wire honey income into the app’s subscription plumbing by autocomplete.

Addendum C — payments into the P&L

Raised: 27 August 2026 · Status: proposal — needs a decision before any code

🔴 Read this first: HiveCraic cannot currently know that a payment happened.

We render a link. The customer pays on Revolut, Stripe or SumUp, and all three settle entirely outside this app. Nothing reports back. So if we book an income row when someone taps the button, we are writing revenue that may never have been received into your accounts — money that then flows into your tax return.

People tap and abandon constantly: the card is in the other coat, the signal drops, they change their mind. Taps will always exceed payments. Booking a tap as income is fabricating a financial record, and that is not something to build.

C1. What each provider can actually tell us

ProviderCan it confirm a payment?What it would take
StripeYes, reliablyA checkout.session.completed webhook from your Stripe account. But see C2 — this is not as simple as it sounds
SumUpProbablyTheir API supports webhooks; the payment-link event shape needs verifying against a real account before promising it
Revolut (revolut.me)NoA personal Revolut link has no API and no webhook. Revolut Business has an API, but that is a different account type. There is no automated path here at all

C2. Why the Stripe webhook is not a small job

/api/stripe/webhook already exists — but it is bound to HiveCraic’s own Stripe account through a single STRIPE_SECRET_KEY / STRIPE_WEBHOOK_SECRET pair, for app subscriptions. Your honey sales land in your Stripe account, which HiveCraic holds no keys for. Bridging that needs one of:

  • Stripe Connect — the correct multi-tenant answer, and a substantial piece of work with its own onboarding flow.
  • Per-user webhook secrets — each beekeeper adds a webhook in their own Stripe dashboard and pastes the signing secret to us. That means storing a credential per user, with all the handling that implies, and a dashboard configuration step that most of this app’s audience will not complete.

Neither belongs in a first version.

C3. Recommendation — record the tap, book only on confirmation

Two layers. Layer 1 is honest, works for all three providers, needs no keys or webhooks, and still saves you the typing.

Customer taps "Pay by card" ↓ /j/{code}/pay/stripe ← records an INTENT, then redirects ↓ Stripe / SumUp / Revolut ← the money moves here, outside HiveCraic ↓ Jar sales - to confirm (3) ← you check your banking app and tick ↓ financial_records (income) ← ONLY now does it reach the P&L

An intent is never income. It is a prompt: a pre-filled list of what someone tried to pay for, so confirming a day’s stall takes three taps instead of typing three records. You reconcile against your Revolut or Stripe app, which is the only place the truth actually lives.

Layer 2, later

Once Stripe Connect or per-user secrets exist, a verified checkout.session.completed can auto-confirm its own intent, and card sales stop needing the manual tick. Revolut will always need it.

C4. Schema

CREATE TABLE jar_payment_intents (
  id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id             UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
  trace_label_id      UUID NOT NULL REFERENCES trace_labels(id) ON DELETE CASCADE,
  batch_id            UUID REFERENCES batch_runs(id) ON DELETE SET NULL,  -- what it pointed at then
  provider            TEXT NOT NULL CHECK (provider IN ('revolut','stripe','sumup')),
  amount              NUMERIC(10,2),
  currency            TEXT NOT NULL DEFAULT 'EUR',
  status              TEXT NOT NULL DEFAULT 'pending'
                        CHECK (status IN ('pending','confirmed','dismissed')),
  financial_record_id UUID REFERENCES financial_records(id) ON DELETE SET NULL,
  confirmed_at        TIMESTAMPTZ,
  created_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);

financial_records needs no change: it already carries a crm_order_id FK, so linking a booked row back to its source is an established pattern. Confirmed intents post as income under the existing Honey Sales category (income_category, already in dropdown_values), described as e.g. “Wildflower 340 g — L-2026-08-001”.

No personal data is captured — no name, no email, no IP. An intent is a label, a provider, an amount and a timestamp.

C5. Things that will go wrong, and what to do about them

RiskHandling
Taps always exceed paymentsThe list is called “to confirm”, never “sales”. Unconfirmed rows never touch the P&L, and there is a one-tap Dismiss
The endpoint is public and unauthenticated — anyone can hit it repeatedly and fill your list with noiseNothing financial is at stake, but the list needs to stay usable: rate-limit per label, and cap what one label can accrue in a day. Old pending rows auto-expire
An extra redirect between tap and paymentA server redirect, so it costs one hop. Worth measuring — anything that adds friction at the moment of payment is a bad trade, and if it feels slow the honest answer is to drop intent tracking and keep a pre-filled manual entry
Double counting against a record you also enter by handConfirming links the intent to the record it created, so it cannot be confirmed twice
RefundsOut of scope. Adjust in the P&L as you would today

C6. The honest alternative, if the above is more than you want

Skip intents entirely. Add a “Record a jar sale” button on the Jar Labels card that opens the P&L form pre-filled with the label’s price, today’s date, Honey Sales, and a description naming the label and its current lot. One tap per sale, no tracking, no new table, no public endpoint, nothing that can ever be wrong.

It is a fraction of the work and carries none of the risk. Worth considering before committing to C3 — if a stall sells fifteen jars, fifteen taps on a list is not obviously better than one summary entry.

C7. Decision — C6 ✔ built 27 August 2026

C6 chosen: pre-filled manual entry. No intent tracking, no public endpoint, no new table, and no redirect hop between tapping and paying. Nothing can ever be recorded that did not happen.

🐝 CRM Module — Implementation Plan

Goal: A subscription-gated CRM module to capture customers, take & fulfil orders, and recognise sales revenue inside the existing income/expense ledger. No inventory tracking. British English throughout.

Decisions confirmed

Order structure: Itemised line items (product type, qty, unit price).
Revenue trigger: Income posts to the ledger when an order is marked Paid.
Category mapping: Auto per product type — Queens → Queen Sales, Honey → Honey Sales, Nuc → Nucleus Sales, etc.
Menu & gating: New Sales nav group (Customers, Orders), completely hidden unless the subscription is active.

What we reuse (no new infrastructure)

  • Subscription gate: existing profiles.subscription_expires_at / is_active via the get_subscription_status RPC — same check already gating Data Export.
  • Finance integration: existing financial_records table + income categories in dropdown_values (Honey Sales, Queen Sales, Nucleus Sales already exist).
  • Currency: EUR/GBP auto-switch via profiles.is_uk_ni_resident — reused, no new logic.
  • Conventions: UUID PK, user_id scoping, RLS auth.uid() = user_id, detail-hook race guards, mobile-card + desktop-table list pages.

Data model — 3 new tables + 1 additive column

crm_customers

id uuid PK · user_id uuid (FK auth.users, cascade)
name text NOT NULL · company text NULL · email text NULL · phone text NULL
address_line1/2, city, county, postcode, country  (all NULL — only for shipping)
notes text NULL · created_at · updated_at

crm_orders

id uuid PK · user_id uuid · customer_id uuid (FK crm_customers, cascade)
order_number text NOT NULL          (per-account, app-generated e.g. ORD-2026-001)
status text  CHECK in (pending, fulfilled, cancelled)   DEFAULT 'pending'
payment_status text CHECK in (unpaid, paid)             DEFAULT 'unpaid'
order_date date NOT NULL · fulfilled_date date NULL · paid_date date NULL
total_amount numeric(10,2) NOT NULL DEFAULT 0   (derived from line items)
notes text NULL · created_at · updated_at

crm_order_items

id uuid PK · order_id uuid (FK crm_orders, cascade) · user_id uuid
product_type text CHECK in (queens, honey, nuc, wax, propolis, pollination, other)
description text NULL · quantity numeric(10,2) NOT NULL DEFAULT 1
unit_price numeric(10,2) NOT NULL DEFAULT 0
line_total numeric(10,2)  (quantity × unit_price, kept in app)

financial_records — additive column only

+ crm_order_id uuid NULL REFERENCES crm_orders(id) ON DELETE SET NULL
Why a column, not a link on the order: marking an order Paid can create several income rows (one per category). Tagging each row with crm_order_id lets us cleanly reverse them if the order is un-paid or cancelled, and never touches manually-entered records.

Revenue recognition flow

When an order is marked Paid: group its line items by product_type → category, sum each group, and insert one financial_records income row per category (date = paid_date, description = Order #ORD-… — {customer name}, crm_order_id set). Marking it back to Unpaid or Cancelled deletes the rows tagged with that crm_order_id. This keeps the existing P&L reports accurate by category with zero double-entry.

Implementation phases

  • Create crm_customers, crm_orders, crm_order_items with indexes on user_id + FKs and updated_at triggers.
  • Add full RLS (auth.uid() = user_id for select/insert/update/delete) to all three.
  • Add crm_order_id column to financial_records.
  • Confirm the income category dropdown_values IDs to map against.

Phase 2 — Types & subscription hook

  • Add src/types/crm.ts (Customer, Order, OrderItem + FormData interfaces).

Phase 3 — Navigation (hidden when unsubscribed)

  • Render crmNavItems only when subscription active in Sidebar.tsx, MobileDrawer.tsx, BottomNavBar.tsx — same shape as the existing userRole === 'Admin' gate.

Phase 4 — Customers

Phase 5 — Orders & fulfilment

  • src/app/dashboard/crm/orders/[id]/page.tsx — detail: customer, line items editor, status (pending→fulfilled→cancelled), payment (unpaid↔paid).
  • Order-number generator (per-account sequence) and total recompute from line items.

Phase 6 — Finance integration

  • On Paid: insert income financial_records (one per category) tagged with crm_order_id.
  • On Unpaid/Cancelled: delete the order's tagged income rows.
  • Verify the rows appear correctly in the existing P&L tool by category.

Phase 7 — Docs

  • Create docs/features/crm-module.md (schema, flow, gating).
  • Update this file's Review section.

Scope guardrails

  • No inventory tracking. No changes to existing finance UI beyond the new income rows flowing in.
  • CRM orders are standalone in v1 — not wired to specific queen/hive records.
  • Smallest possible footprint: additive column on financial_records, separate nav array, isolated crm/ route tree.

Review

All seven phases implemented. Summary of changes:

  • Database (Supabase MCP): migration create_crm_module created crm_customers, crm_orders, crm_order_items (UUID PK, user_id-scoped, full RLS, indexes, updated_at triggers) and added the nullable crm_order_id column to financial_records. Security advisor reports no RLS issues on the new tables.
  • Types & gating: src/types/crm.ts; useHasActiveSubscription hook (wraps get_subscription_status, fails closed).
  • Navigation: crmNavItems + Sales group in navigation.ts; rendered only for active subscribers in Sidebar and MobileDrawer. Bottom nav unaffected (CRM not flagged bottomNav).
  • Route guard: crm/layout.tsx redirects non-subscribers.
  • Customers: list + inline create/edit form with optional collapsible shipping address.
  • Orders: list with status/payment badges + filter; inline New Order form; detail page with line-item editor, fulfil/reopen, mark paid/unpaid, cancel, delete.
  • Finance integration: crm-finance.ts posts one income row per product category on Paid (tagged crm_order_id), reverses on Unpaid/Cancel/Delete, re-posts idempotently on edit. Category IDs resolved at runtime by value.
  • Docs: docs/features/crm-module.md.

Quality Audit — Hardening Pass

A senior code review followed implementation. Findings and fixes:

  • Critical — non-atomic money mutations: all multi-step client write sequences (create, save items, pay/unpay, cancel) replaced with single-transaction Postgres functions (crm_create_order, crm_save_order_items, crm_set_order_payment, crm_cancel_order, _crm_recognise_revenue), SECURITY INVOKER so RLS still applies. No more half-failed states.
  • Critical — silent revenue loss: posting now raises if any product type can't map to an income category, instead of dropping the line.
  • High — order-number race & 1000+ lexical bug: numbering moved inside the create transaction using a numeric max; UNIQUE(user_id, order_number) is the final guard.
  • Medium — inconsistent delete semantics: standardised — Unpaid/Cancel un-recognise income; Delete keeps it (historical fact) consistently for direct and cascade deletes.
  • Medium — redundant RPCs: useHasActiveSubscription now shares a cached, deduped result across nav surfaces.
  • Security: all CRM functions pinned to search_path = '' with fully-qualified identifiers.
  • DRY: deleted crm-finance.ts, crm-orders.ts, and the duplicated TS category map; SQL is now the single source of truth. Client handlers are thin RPC calls.

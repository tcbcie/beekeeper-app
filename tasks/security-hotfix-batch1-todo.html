Security Hotfix Batch 1

Status: Implemented 15/10/2026. Database is live; the app code is awaiting deployment. Source: docs/features/full-app-audit-report.md, findings SEC-C1, C2, H1, H2, H4 and a related sign-up hole.
Deferred to batch 2: SEC-H3 (scale tokens: needs select('*') changes in auth.ts and the profile page), SEC-H5 (service-role key in a trigger: needs you to rotate the key), and SEC-M1 / L1.

The principle throughout is to fix it in the database, where the hole is, and change app code only where a page relied on the hole. Every database change is a single MCP migration with a matching rollback. The app stays the same for normal users.

1. SEC-C1: users editing their own subscription and status

There is already a trigger, prevent_role_self_change, that protects role. I will add the same kind of guard for the money and status columns.

New BEFORE UPDATE trigger on profiles. When the caller is a normal logged-in user (not an admin, not the service role, not an internal SECURITY DEFINER function such as activate_subscription), it rejects any change to: is_active, subscription_expires_at, subscription_type, subscription_price, used_registration_code_id, current_subscription_code_id, is_association_member, stripe_customer_id, deleted_at, original_email, email, last_subscription_reminder_sent.
Unchanged: names, mobile, address, breeder code, association choice, memberships, reminders and every enable_* preference stay user-editable (checked against profile/page.tsx). The admin edits in User Management still work through is_admin(), and Stripe and code activation still work because they run with elevated rights.
Drop the unused "Users can insert own profile" policy. Profiles are only ever created by the sign-up trigger; no app code inserts them.

2. Sign-up trusting browser data

handle_new_user stops reading registration_code_id from sign-up metadata. The app never sends it, so only a crafted sign-up could use it. Codes are still redeemed through activate_subscription and Stripe, which check whether a code is active and how often it has been used.

3. SEC-C2: reading other users' data through functions

get_dashboard_overview and get_recent_activity: refuse unless p_user_id is the caller. The dashboard always passes its own ID, so no app change is needed.
get_user_email: return the email only for the caller, an admin, or someone the caller shares a team or rearing group with (owner or member). Otherwise return 'Unknown', as it already does for missing users. That covers both callers (the apiary team page and rearing groups).

4. SEC-H1: forgeable auto-accept-invitations edge function

You: (done 17/10/2026, verified 404) delete it in the Supabase dashboard (Edge Functions → auto-accept-invitations → Delete). The MCP tools cannot delete functions.
Me: remove supabase/functions/auto-accept-invitations/ from the repo. Nothing calls the function; team auto-accept is already done by a safe database trigger. Behaviour does not change.

5. SEC-H2: invitations readable by anyone

Replace both USING (true) read rules with: the team or group owner, or the invitee (their login email matches).
The accept and decline links open before login, so add two small functions, get_team_invitation(id) and get_rearing_group_invitation(id). Each returns one invitation by its unguessable ID, in the same shape the pages already use (including the team or group name).
Swap the single read query in 4 pages to call these: accept-invitation, decline-invitation, accept-rearing-group-invitation, decline-rearing-group-invitation.

6. SEC-H4: all registration codes readable

Make registration_codes readable by admins only. Drop the "read all codes" rule and the three dead lowercase 'admin' rules; the existing 'Admin' rule already covers admins.
Add a small function, lookup_registration_code(code), that returns one code by its exact text, in the same shape. Swap the 2 queries in RenewSubscriptionModal.tsx to use it.

7. Checks and docs

Every new function: search_path = public, with explicit GRANT EXECUTE (both learned from earlier bugs). Then run get_advisors.
Verify the guards with read-only queries and dry-runs inside a transaction that is rolled back, so no data changes.
Lint and type-check the 5 changed files, then run the qa-engineer audit.
Update the docs: this plan in docs/features/security-hotfix-batch1-plan.md, the findings register, and memory notes for the new live-only database objects.

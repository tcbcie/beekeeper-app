Voice Transcription Accuracy — Implementation Plan

Improves recognition of apiculture vocabulary in the existing voice-notes feature (docs/features/voice-notes-field.md). Endpoint: src/app/api/voice-notes-transcribe/route.ts. Hook: src/hooks/useVoiceRecorder.ts.

Headline approach

Three phases, each independently shippable. Phase 1 alone is expected to eliminate the majority of misrecognitions and requires no database changes. Phases 2 and 3 are gated on real user evidence collected after Phase 1 lands.

Phase 1 — Domain biasing (no DB, ~30 min)

Expected to deliver the bulk of accuracy improvement. Ship and measure before doing more.

1.1 Whisper prompt parameter

The Whisper API accepts a single ‘previous segment’ string up to ~224 tokens that biases the model. Pack a curated apiculture glossary into it. 

// In src/app/api/voice-notes-transcribe/route.ts (module-scope const)
const APICULTURE_PROMPT =
  'Beekeeping inspection note. Common vocabulary: varroa, Varroa destructor, ' +
  'propolis, queen excluder, brood box, super, supers, supersedure, ' +
  'drone laying, laying worker, foulbrood, AFB, EFB, Nosema, chalkbrood, ' +
  'sacbrood, deformed wing virus, uncapping, smoker, hive tool, mating nuc, ' +
  'graft, grafting, Jenter, Cupkit, Cloake board, oxalic acid, formic acid, ' +
  'Apiguard, Apivar, sealed brood, open brood, capped brood, eggs, larvae, ' +
  'queen cells, swarm cells, supersedure cells, apiary, eircode, ' +
  'Buckfast, Carniolan, Italian, Native Irish black bee, NIHBS.'

whisperResult = await client.audio.transcriptions.create({
  model: 'whisper-1',

1.2 Cleanup LLM glossary

Extend CLEANUP_SYSTEM_PROMPT with explicit misheard→correct examples so GPT-4o-mini self-corrects the transcript:

const CLEANUP_SYSTEM_PROMPT = `You are cleaning up dictated beekeeping notes...
[existing rules]

Correct misheard beekeeping terminology where the speaker's intent is clear, e.g.:
  "borrow a" / "boroughs" / "barrow"   → "varroa"
  "proper list" / "propers"            → "propolis"
  "super seed" / "super seeded"        → "supersede" / "supersedure"
  "drone lying"                        → "drone laying"
  "fowl brood" / "fall brood"          → "foulbrood"
  "queen excluder" stays as-is.
Never invent a correction if the spoken word is unclear — leave it as the speaker said it.`

1.3 Upgrade transcription model (optional, same PR)

Swap whisper-1 → gpt-4o-transcribe (or gpt-4o-mini-transcribe for cost). Same client.audio.transcriptions.create() signature. Materially better on accented / noisy audio. Keep the prompt param — it is still respected.

Phase 2 — Per-user glossary gated on Phase 1 evidence

Only build this once Phase 1 is in users' hands and we have evidence individual users have terms the global glossary cannot cover (regional names, treatment brands, queen breeding line names, etc.).

2.1 Schema (via Supabase MCP, per CLAUDE.md)

create table public.voice_glossary (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  phrase text not null,
  boost smallint not null default 1,                       -- 1..5, higher = pack first
  source text not null default 'manual',                   -- 'manual' | 'accepted_candidate'
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (user_id, lower(phrase))
);

alter table public.voice_glossary enable row level security;
create policy voice_glossary_owner on public.voice_glossary
  for all using (auth.uid() = user_id) with check (auth.uid() = user_id);
create index voice_glossary_user_boost_idx on public.voice_glossary (user_id, boost desc, updated_at desc);

2.2 API integration

In voice-notes-transcribe/route.ts, after auth/subscription gating:

  1. Select user's phrases ordered by boost desc, updated_at desc.
  2. Greedy-pack into a string while staying under ~200 tokens (rough heuristic: 1 token ≈ 4 chars). Cap exists because Whisper truncates at 224.
  3. Prepend to APICULTURE_PROMPT: user phrases first (higher relevance), domain phrases as fallback.
  4. Also append the user list to the cleanup system prompt under a ‘User-specific terms’ section.

2.3 Settings UI

New page src/app/dashboard/settings/voice-glossary/page.tsx (mobile-first, matches existing settings pattern):

  • List of phrases with inline edit and a 1–5 boost slider.
  • ‘Add phrase’ input with optimistic insert.
  • Delete via swipe / trash icon.
  • Link from the Account/Settings menu and from a small ‘Improve transcription’ link below the Notes voice button.

Phase 3 — Correction feedback loop gated on Phase 2

Closes the loop: every save with edits becomes a learning signal — without storing audio.

3.1 Capture pairs (cleaned vs. final)

  1. API already returns cleaned. Add a stable cleanedId (uuid) so the client can later reference it.
  2. Form keeps cleanedId + cleaned in local state for the current note only (no DB write yet).
  3. On inspection save, if the field that received the dictation was edited, POST { cleanedId, original: cleaned, final: notes } to a new endpoint /api/voice-notes-feedback.

3.2 Candidate mining (server)

Cheap token-diff to spot probable corrections:

  • Tokenise both texts, align with a standard diff (e.g. diff-match-patch or hand-rolled token LCS — small dependency).
  • For each replaced span, compute Levenshtein distance between dropped phrase and inserted phrase. If ≤30% of the dropped length and the inserted phrase contains a non-stopword, record as a candidate.
  • Store in voice_glossary_candidates (user_id, heard, corrected, occurrences, last_seen_at) — aggregate by lowercased pair.
create table public.voice_glossary_candidates (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  heard text not null,
  corrected text not null,
  occurrences int not null default 1,
  last_seen_at timestamptz not null default now(),
  dismissed_at timestamptz,
  unique (user_id, lower(heard), lower(corrected))
);
-- same RLS policy pattern as voice_glossary.

3.3 Review UI

  • On settings page (and as a small banner the next time the voice button is used), surface candidates with ≥2 occurrences.
  • Three actions per candidate: Add to glossary, Ignore, Snooze.
  • Adding writes a row to voice_glossary with source = 'accepted_candidate' and bumps boost = 3.
  • Never auto-add — always review-gated.

Out of scope (deliberately)

  • Whisper fine-tuning. Requires audio retention, which docs/features/voice-notes-field.md explicitly forbids. Not justified at current scale.
  • Server-side noise suppression. Whisper / gpt-4o-transcribe handle bee hum well. Measure WER before adding rnnoise or similar.
  • Direct hardware mic integration. A short note in the feature doc recommending a Bluetooth lapel mic is the right ergonomic fix, not in-app code.
  • Real-time / streaming transcription. Existing record-then-transcribe flow is sufficient for the Notes use case.
  • Multi-language vocabulary packs. App is British-English-first per CLAUDE.md; revisit if internationalised.

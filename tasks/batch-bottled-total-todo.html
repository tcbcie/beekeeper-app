Batch Card — “Bottled” Weight Line

Goal

On each batch card in Honey Provenance → Batches, show — directly below Total — how much of the batch has already been bottled into jars, so the beekeeper can see at a glance how much of the bulk honey is still unbottled.

Current state

L-2026-08-002 · Public

Bottled: 14/8/2026    Best Before: 31/12/2029
Jars: 212ml · 245g × 11, 320ml · 380g × 17
Total: 187.52 kg    Bulk Honey: 12

  • Total = sum of the linked bulk honey containers (raw honey into the batch).
  • Jar rows already carry net weight (g) and count — the bottled figure is simply Σ(net weight × count), which the app already computes inside the batch form as “Proposed bottled output”, but never shows on the card.

Proposed change

Add one derived line to the batch card details grid, immediately after Total:

Total: 187.52 kg    Bottled: 9.16 kg (28 jars)

Computation (no schema change, no extra query — the jar rows are already fetched):

// Honey already jarred from this batch: Σ(net weight × jar count).
// Falls back to the legacy scalar columns when a batch has no batch_jars rows.
const bottledKg = (batch: BatchRun) => {
  const rows = batch.jars?.length
    ? batch.jars
    : [{ jar_weight_g: batch.jar_weight_g, jar_count: batch.jar_count }]
  const grams = rows.reduce((sum, j) => sum + (j.jar_weight_g ?? 0) * (j.jar_count ?? 0), 0)
  return grams / 1000
}
Label clash to resolve: the card already uses the label Bottled: for the batch date (14/8/2026). Two rows both labelled “Bottled” in the same grid would be confusing. Recommendation: rename the date row to Bottled On: and use Bottled: for the new weight line. (Alternative: leave the date as “Bottled” and label the new line “Bottled Weight”.)

Follow-up: per-size breakdown

After first review the breakdown by jar size was added. bottledTotals() now also returns a sizes[] array (one entry per weighed jar size, each with its own kg), rendered as an indented list under the Bottled total. Chosen over folding kg into the existing Jars line so the Bottled figure stays self-contained and auditable.

  • The breakdown is suppressed on single-size batches, where it would only repeat the total.
  • The same weight/count guards apply, so a size missing a net weight appears in neither the breakdown nor the total.
  • The legacy fallback yields exactly one size, so it never renders a breakdown.
  • Re-verified: npx tsc --noEmit still 96 errors, all in tests/, none new; npx eslint clean.

Follow-up: remaining unbottled honey

Added an Unbottled line — Total − Bottled — closing the loop between honey in and honey out. It appears only when the batch has a total weight and something has been bottled; before that it would simply repeat Total.

Edge caseHandling
More jarred than the recorded intake (negative remainder) Reported in amber as Unbottled: none — 2.40 kg more bottled than the recorded total. Deliberately not clamped silently to zero: the gap means the Total was overridden or bulk sources were not all linked, and hiding it would hide a data problem.
Floating-point rounding on an exactly-fully-bottled batch A 5 g tolerance (< -0.005) prevents a spurious “over-bottled by 0.00 kg” warning; anything inside the tolerance displays as 0.00 kg.
total_weight_kg wire format The only numeric (rather than integer) column involved, so it is coerced with Number() and checked with Number.isFinite before arithmetic instead of trusting the wire format.
  • Re-verified: npx tsc --noEmit still 96 errors, all in tests/, none new; npx eslint clean.

Follow-up: percentages

Both lines now carry their share of the batch's recorded intake — Bottled: 9.16 kg (5% · 28 jars) and Unbottled: 178.36 kg (95%). The share was folded into the Bottled line's existing parenthetical rather than added as a second bracket, keeping the line readable.

Edge caseHandling
Rounding making the two shares sum to 101% The unbottled share is derived as 100 − bottled%, not computed independently, so the pair always sums to 100% whichever way each would have rounded on its own.
A real but tiny share rounding to “0%” formatShare() renders <1% whenever the rounded share is 0 but the weight is not, so a genuinely bottled batch never reads as 0%.
Batch with no total weight, or a total of zero Percentages are omitted entirely — there is nothing to divide by, and the guard also rules out Infinity/NaN reaching the UI.

QA audit (Principal Quality Architect review)

No Critical or High findings. The change is a pure client-side derivation over data already in memory — no new I/O, no new state, no effect dependencies, so no race, leak or stale-closure surface.

SeverityFindingResolution
🟡 Medium Falsy-zero render on the adjacent Total line. {batch.total_weight_kg && (…)} renders a bare 0 text node into the grid when the total is exactly 0, because 0 is falsy but still a valid React child. Pre-existing, and directly adjacent to the new line. Fixed — changed to != null, so a zero total renders “Total: 0 kg” rather than a stray “0”.
🟡 Medium Legacy fallback could be misread as overcounting. batch_runs.jar_weight_g holds the first size's weight while jar_count holds the total across sizes, so multiplying them looks unsafe. It is in fact safe — the fallback only fires when a batch has no batch_jars rows, which by definition means a single jar size — but nothing recorded that invariant. Documented in the helper's comment so a future reader does not "fix" it into a bug.
🟡 Medium Jar rows without a net weight. Such rows are skipped from the kg sum; if they were still counted in the jar total, the line would imply un-weighed jars contributed weight. Kept skipping them from both totals, so kg and jar count always describe the same set of weighed jars — and documented that this is deliberate.
🟢 Verified No NaN / string-coercion risk. Queried the live schema: batch_jars.jar_weight_g, jar_count, jar_size_ml and the batch_runs equivalents are all integer, so PostgREST returns JSON numbers, never strings. The existing null / <= 0 guards are sufficient; no extra Number.isFinite wrapper needed. No change — guard confirmed adequate rather than padded.
⚪ Low Sub-10 g batches. A batch totalling under 5 g would display “0.00 kg”. Left as-is: real jars are ≥ 100 g and EU labelling requires a net weight, so guarding this would add branching for an unreachable case. Noted, not changed (simplicity over speculative hardening).
⚪ Low Accessibility. New row reuses the sibling rows' text-sm text-text-secondary with a font-medium label, matching the existing grid — no new small-text or low-contrast surface for the 50+ audience. No change needed.

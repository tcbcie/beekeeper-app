Batch 16: Double-Submit Guards

Status: Done 19/10/2026. Tested by you; committed and pushed. Approved with the recommendations: A, the orphan support page gets the guard; B, the lineage cycle goes to a later queens batch; C, the invitation index comes later. This is Phase 2 fix batch 4.

Three agents checked every double-submit finding. They are all real. Most handlers have no guard at all. The rest use a React state flag (if (saving) return), which two quick taps can both get past, because the second tap lands before React re-renders. The results are duplicate hives, apiaries, queens, nucs, tasks, colonies, tickets, invitations and traceability batches, the last of which each use up a lot number and trace code.

The shared fix

One new hook, src/hooks/useSubmitLock.ts. A ref is the real lock, because it changes instantly with no re-render needed. The state copy only drives disabled and "Saving…". The lock is released in finally, so an error or early return can never leave it stuck.

const { submitting, run } = useSubmitLock()

const handleSubmit = (e: React.FormEvent) => {
  e.preventDefault()               // always outside run(): a locked second submit must not reload the page
  if (!valid) return               // quick validation stays outside
  void run(async () => { ...the existing save code, unchanged... })
}
<Button type="submit" disabled={submitting}>

Each site then gets the same three-line change: wrap the save in run(), disable the button, and drop the old state flag where there was one. Save logic is otherwise untouched.

Multiple Jar Sizes per Batch

Problem

When bottling a batch, the user is restricted to a single jar size (jar_size_ml, jar_weight_g, jar_count are scalar columns on batch_runs). A real bottling run often fills two or more different jar sizes from the same blended bulk-honey sources. We need to capture each jar size with its own net weight and count, and total the batch across all of them.

Design

Source of truth: new batch_jars table

ColumnTypeNotes
iduuid PKdefault gen_random_uuid()
batch_iduuid FK → batch_runs(id)ON DELETE CASCADE
jar_size_mlintegere.g. 227, 340, 454
jar_weight_gintegernet weight per jar (EU compliance)
jar_countintegernumber of jars of this size
created_attimestamptzdefault now()

RLS mirrors batch_runs (owner via the parent batch's user_id). Same pattern as batch_containers.

Backward compatibility (legacy columns stay)

The existing scalar columns on batch_runs remain and are kept populated from the first jar config (size + weight), with jar_count = the sum of all configs. This keeps the AI traceability tools and any other legacy reader working with an accurate total jar count without rewriting them in this change.

Approach (minimal, isolated)

  • Form state: replace the three scalar fields in BatchFormData with a jars: JarConfig[] array ({ jar_size_ml, jar_weight_g, jar_count } as strings). Always at least one row.
  • Form UI: the current Jar Size / Net Weight / Jar Count trio becomes one repeatable row with a remove (✕) button; an "+ Add jar size" button appends a row. Existing dropdown options (jarSizeOptions) reused per row.
  • Total weight auto-calc: sum of (jar_weight_g × jar_count) / 1000 across all rows (replaces the single-row effect).
  • Submit: write the batch, then replace its batch_jars rows (delete-then-insert, same as the harvest-link pattern). Populate legacy columns from first row + summed count.
  • Edit: load batch_jars into the form array (fallback to a single row from legacy columns if a batch somehow has none).
  • Batch list: show each jar size as a line (e.g. 454 g × 24); total stays.
  • Public trace page: list each size's net weight + count (per your choice).
  • Backfill migration: one row into batch_jars for every existing batch_runs row that has a jar_size_ml.
JarConfig validation: rows with a blank/zero jar size are skipped on save. A batch with no valid jar rows saves with zero jars (same as today's empty fields). Net weight and count parse through the existing NaN-safe guards.

Review

What changed

  • DB: new batch_jars table (FK → batch_runs, ON DELETE CASCADE, RLS via parent batch). Backfilled 4 existing batches. Updated get_public_batch_info RPC to return a jars array.
  • Types: added JarConfig and BatchJar; BatchFormData.jars: JarConfig[] replaces the three scalar fields; BatchRun.jars?: BatchJar[].
  • Form: repeatable jar rows (size / net weight / count) with add + remove; at least one row always kept. Labels show only on the first row to keep it compact.
  • Total weight: auto-sums (net weight × count) across all rows, NaN-guarded.
  • Submit: parses + filters jar rows (skips rows with no valid size), delete-then-insert into batch_jars with checked errors, and keeps legacy columns in sync (first size/weight, total count).
  • Display: batch card shows one "Jars" line listing each size (454ml · 340g × 24); public trace page lists each size's net weight with count, falling back to the legacy column.

Known simplification

The AI traceability tools still read the legacy batch_runs columns. Because those stay populated (primary size + total count), the AI summary's total-jar count remains accurate; only the per-batch jar size reflects the first size. Acceptable for the secondary AI surface; can be revisited if needed.

Customer Credit from Order Overpayments — Plan & To-Do

Goal: When a customer pays more than an order's total, keep the surplus on record as customer credit. The credit is visible on the customer account and can be optionally applied to another order as payment. This supersedes the earlier order-only overpayment plan.

Confirmed findings

  • Payment is a single scalar crm_orders.amount_paid, clamped to [0, total_amount]; surplus is silently dropped in crm_set_order_amount_paid (v_amount := LEAST(GREATEST(…,0), v_total)) and re-clamped in _crm_apply_payment_state.
  • No customer-credit concept exists anywhere (types, tables, UI) — greenfield.
  • All crm_* tables are user_id-scoped with the identical 4-policy RLS pattern (auth.uid() = user_id). All money mutations are atomic SQL RPCs (SET search_path = public, SECURITY INVOKER, EXECUTE to authenticated only); client-side money orchestration is explicitly forbidden.
  • Revenue is safe: _crm_recognise_revenue books SUM(quantity × unit_price) = order total, never amount_paid. Credit does not distort the P&L. Surplus cash is a liability/credit, not income, and correctly appears as revenue only once applied to an order that then fully pays.
  • Customer rollups live in SQL view crm_customer_summary; customer detail page loads customer + orders via Promise.all.

Design (confirmed with user: customer-level credit, applied optionally to another order)

  • Single source of truth = a credit ledger. New table crm_customer_credit (append-style, signed amounts). Customer balance = SUM(amount), always >= 0.
  • Overpayment is swept to the ledger (orders keep amount_paid ∈ [0, total]). A surplus becomes a + ledger entry linked to the source order.
  • Credit is applied manually to a chosen order via a new atomic RPC (a − ledger entry + bump that order's amount_paid), capped at the order's remaining balance so credit never creates a new overpayment loop.
  • payment_status stays binary; no enum change. "Overpaid"/credit shown as derived UI.

Ledger table shape

crm_customer_credit (
  id uuid pk default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  customer_id uuid not null references crm_customers(id) on delete cascade,
  order_id uuid references crm_orders(id) on delete set null,
  amount numeric(10,2) not null,        -- + = credit added, − = credit applied
  reason text not null check (reason in
    ('order_overpayment','applied_to_order','manual_adjustment')),
  created_at timestamptz default now()
)  -- RLS enabled, 4 policies mirroring crm_orders

Money-correctness notes (why this stays consistent)

  • Revenue is always the order total, per order. Surplus cash is never booked as income until it is applied to an order that then fully pays — so no double-counting and no inflated P&L.
  • Ledger balance is the single source of truth and is guarded >= 0 on every debit.
  • Applied credit is capped at the target order's remaining balance, so credit can never itself generate a new overpayment.
  • All mutations are atomic server RPCs; the client never orchestrates multi-step money changes.

Out of scope (v1)

  • Applying credit at order-creation time (apply on the detail page after creation instead).
  • Refunds / paying credit back out as cash; per-payment method/date ledger for cash itself.
  • Cross-customer credit transfer.

Security Batch 10: Database Low Findings (DB-13, DB-16, DB-17, DB-18)

Status: Done 17/10/2026; tested by you, committed and pushed. DB-12 and DB-14 were already closed in batch 6. Database only: no app code changes.

What I found (live database, 17/10/2026)

IDProblem
DB-13When editing a task on a shared hive, the owner (user_id) can be set to any user. The app itself always sets it to the person editing.
DB-16Comments on diagnosis photos can be read by every logged-in user, while the photos themselves are limited to their owner, power users and admins.
DB-17
  • Both photo buckets let anyone, without a login, list every file. The apiary-images folder names are user IDs, and wild-colony photos may carry GPS data.
  • There are no file-type limits, and apiary-images has no size limit. Any logged-in user can upload any file to any path.
  • The app only uploads JPEG, PNG, GIF and WebP up to 10 MB, and never lists files. It deletes with remove() only to undo a failed save, and that needs the uploader to be able to "see" their own file.
DB-18
  • Anonymous visitors hold 480 table write permissions. The database rules block every one of them today (I checked that no write rule works without a sign-in), but the permissions shouldn't exist.
  • Anonymous visitors can call helper functions such as can_access_hive(hive, user) or is_team_member(team, user). These answer yes or no about other users' data.
  • activate_subscription doesn't lock the code, so two simultaneous redemptions can exceed its maximum uses.
  • Honey feedback (anonymous) has no comment length limit and no rate limit, and is accepted even when the beekeeper turned feedback off.
  • Two leftover backup tables from 29/08/2026 (changelog_dupe_backup_20260829, queen_assignments_nuc_fix_backup_20260829).

Plan (one migration through MCP)

DB-13: a trigger on tasks_events means a task's owner can stay the same or become the person editing it, never someone else. This matches what the app already does.
DB-16: a comment is readable only if you can see its photo: the photo's owner, power users and admins, as for the photos themselves.
DB-17, storage:
  • Replace the "anyone can read" rules with "you can see your own files". Public image links keep working, because public buckets serve them without these rules. Listing other people's files stops. The undo-delete keeps working because it only touches your own upload.
  • Both buckets accept only JPEG, PNG, GIF and WebP, up to 10 MB, the same limits the app already enforces.
  • Uploads must go into the folders the app uses: apiary-images into your own user-ID folder; inspection-images into inspections/, varroa-checks/, diagnoses/, wild-colonies/ or wild-colony-inspections/.
DB-18:
  • Revoke all table write permissions from anonymous visitors, including for future tables. Read permissions stay: the public trace, jar and embed pages and the community GDD view use them.
  • Revoke the yes/no helper functions that take a user ID (can_access_*, check_user_owns_apiary, is_team_*, is_rearing_group_*, has_valid_invitation, get_user_role, is_admin(user), get_rearing_group_member_user_ids) from anonymous visitors. Logged-in users keep them, because the database rules use them. The logged-out pages only call public functions, never these.
  • activate_subscription locks the code row (FOR UPDATE), so its maximum uses can't be exceeded.
  • Feedback: comments are capped at 1,000 characters, a batch accepts at most 30 feedback entries an hour, and feedback is refused when the beekeeper turned it off.
  • Drop the two backup tables from 29/08/2026.

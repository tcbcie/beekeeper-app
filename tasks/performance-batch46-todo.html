Batch 46: Performance

Status: Implemented 29/10/2026, waiting for your test. This is the performance batch you added on 25/10/2026. Three agents looked at what each page downloads, the database and data requests, and the screens, offline cache and scales. They used read-only timings on the live database. Each item below is a small change. The ones with the biggest gain for the least risk come first in each section.

A. The database

Mel's knowledge search scans everything: each search reads all 5,609 knowledge-base rows. It takes 0.5 to 1 second on average and up to 3.8 seconds. The same search using its index takes under 1 millisecond. The cause is a setting on the database function that stops it using the index. One migration rewrites the function so it uses the index, and I'll confirm the plan afterwards.
Record lists check every row one by one: the read rules on inspections, feedings, harvests, varroa checks and varroa treatments call an access check for each row. For the largest account's 560 inspections that costs 14.6 ms where it could take 0.3 ms. This affects the records page, the hives list, hive detail and reports. Each rule gets a quick "it's your own hive" path first, which is the check's own first step, then the full check for team hives. Who can see what doesn't change.
Small tidy-ups the checker flags: one missing index (queens by distribution), and two invitation rules that re-read the signed-in user on every row.
Housekeeping:
  • The background web-request log: the database's log of its own outgoing web requests (the reminder jobs' calls) holds 24 rows but takes 20 MB. Clearing it is the database's single biggest use of time: 4.8 hours so far. It gets compacted once.
  • The scheduled-job history: 41 MB so far. A daily job will drop entries older than 7 days.
It shares the small server that pages use.
Decision 1: database changes. The second and fourth items change security rules and run housekeeping on the live database. Done (you approved). Every account sees exactly the same rows as before, checked for all five tables, then again under real sign-in for the largest account and a team member.

B. Requests from the app

The account check: every open tab checks every 30 seconds whether your account is still active, even when the app is in the background. That's about 250,000 requests so far, the most of anything in the app, and it keeps phones' radios awake. It will skip the check while the app is in the background and check once when you come back.
Decision 2: how often to check while the app is open. Done: every 5 minutes (you approved), plus a check each time you come back to the app. A disabled account is locked out within 5 minutes. The server routes that need an active account still check it on every call.
Dashboard team figures: up to 10 requests, 5 of them one after another, load the "Teams & Collaboration" figures, but that panel starts closed. They now load when you open it, using the shared team list.
Apiaries page: it makes 5 requests one after another, the last one fetching every inspection ever recorded just to find the latest date per apiary. It goes down to 3 requests, fetching only the latest inspection per hive.

C. Scales

The inspection form: to fill in one weight, it runs the full scale summary: 8 Wolf calls one after another, or 7 BEEP calls. It will ask for the latest reading only, which is 1 call.
Wolf summary: the latest values come from the 48-hour readings it already fetches, so it makes 7 calls instead of 8, with the same result. I'm leaving out merging the 7-day and 30-day calls, because Wolf doesn't document how a daily request treats the first and last day.
Wolf battery tile: it never shows. The panel will ask for the battery level once when it opens.
Unused scale code: two Wolf display components that nothing uses get deleted. One of them would have checked every 5 minutes even in the background.

D. What pages download

QR code logo: every QR code embeds a 613 KB logo. A 128 px copy of about 8 KB replaces it. QR pages, printing and the QR tags page get lighter.
Records page: all five record forms (about 4,400 lines, the inspection form alone 2,400) load before you open one. They now load when opened, as do the QR code pop-up on inspection cards and the long form sections on the Hives and Queens lists.
Reports: all nine reports load; now only the one you open does.
Apiaries list: the Irish grid conversion library (about 35 KB) now loads only when a grid reference is worked out.
Opening the installed app: it opens at the home page, which loads, checks your sign-in, and then moves to the dashboard. It will open straight at the dashboard.
Public trace page: the page jar customers scan shows the apiary photo full size, up to 10 MB. It now gets a phone-sized copy.

E. Long lists and the offline cache

The records page shows all records at once: up to 735 for the largest account, and every one is redrawn on each key press in search. It will show 50 at a time with a large "Show more" button. Search stops redrawing on every key press, and a record you jump to from a link is always shown.
A weak signal: when the signal is poor but not gone, the app can wait tens of seconds for a page before showing the saved one. After 4 seconds it now shows the saved page, and updates it when the network answers.
Old app files pile up: each update adds code files to your phone's cache and none are removed until the next version number change. Only the newest 400 are kept.
Photos re-download after an hour: they're now kept for 7 days. I chose 7 days, not the 30 in the plan, because a deleted photo is removed for good after 7 days and copies shouldn't outlive it by much.
Left out on purpose:
  • Hives list history: loading only the latest records on the hives list needs a new database function. The faster rules above make the current way cheap.
  • The profile read: it's read 3 to 4 times per page, but the reads run side by side, so the gain is small.
  • Merging BEEP's 7 calls: they run side by side, so merging would mainly spare BEEP, and the long window might thin the data.
  • Sign-in on a weak signal: it touches sign-in behaviour.
  • For the UI review batch: the design font (DM Sans) is never loaded, so the app shows Arial.

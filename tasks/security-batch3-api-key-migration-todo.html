Batch 3: Supabase API Key Migration

Status: Done 17/10/2026; the leaked key is dead. auto-accept-invitations deleted 17/10 (404). Codex token revoked and old env file deleted 17/10. Nothing left open. Findings: SEC-H9 (and the remainder of SEC-H5).
Deadline: Supabase retires the legacy anon/service_role keys at the end of 2026, so this has to happen anyway.

Resolved 17/10/2026: the leaked key below is now refused everywhere (see Review).
Why it mattered: the service-role key that sat in the old trigger can still open the whole database, bypassing every access rule. Supabase no longer lets you rotate the legacy keys. The only way to kill that key is to move to the new keys and then deactivate the legacy ones.

What I found (from Supabase's current docs and the codebase)

  • The new keys are sb_publishable_… (replaces anon, safe in the browser) and sb_secret_… (replaces service_role, server only; refused if used from a browser). Your project already has a publishable key.
  • The app reads only two environment variables: NEXT_PUBLIC_SUPABASE_ANON_KEY (5 files) and SUPABASE_SERVICE_ROLE_KEY (25 server files). We keep the variable names and change only their values, so no app code changes.
  • Edge functions: the 5 in the repo read SUPABASE_SERVICE_ROLE_KEY. After deactivation they must read the new key from SUPABASE_SECRET_KEYS, a JSON list that Supabase adds automatically. The two invitation functions also need verify_jwt off, because the new keys aren't JWTs; they already check the signed-in user themselves.
  • Hard-coded key: public/embed/tcbc-research-widget.js contains the legacy anon JWT. It must switch to the publishable key, which is public by design, so this is safe.
  • Scheduled jobs still send the legacy anon key as a leftover. It can be removed: both functions now use the webhook secret.
  • Local scripts (add-changelog, bump-version, sync-storage, ingest, reset-local) read the service key from your local .env files. They keep working once you update those values.
  • Unused function: generate-vegetation-info is deployed but nothing in the app calls it, and its source isn't in the repo.
  • Your supabase-js 2.75 and @supabase/ssr 0.7 already support the new keys.

Found while verifying: deactivation only blocks legacy keys used as API keys. A legacy JWT sent as Authorization: Bearer is still trusted. With the publishable key as apikey on REST, or on its own on Storage, it returns 200. That's because the legacy anon/service_role keys are JWTs signed with the legacy JWT secret, which still signs every user session. So the leaked service-role JWT very likely still has full access until that secret is revoked (step 4b).

4b. Move to JWT signing keys and revoke the legacy JWT secret (this is what actually kills the leaked key)

Checked first: nothing in the app depends on the legacy secret. All edge functions run with verify_jwt off. No code verifies tokens locally; it uses getUser() against the auth server. No signed storage URLs are used. Impersonation uses generateLink, which the auth server handles.

You Supabase → Project Settings → JWT Keys → Migrate JWT secret. This imports the legacy secret and creates a standby ES256 key. No user impact.
You Wait about 5 minutes (Supabase throttles key changes), then click Rotate keys. New logins get ES256 tokens and nobody is signed out.
You About 1 hour 15 minutes later (the access-token lifetime), Revoke the legacy JWT secret under "Previously used". Doing it sooner only signs out users who are active at that moment; they just log in again.
Me Verify: the legacy JWT as Bearer is refused on REST and Storage, and login, the dashboard, scheduled jobs and edge functions all still work.

Lesson: on Supabase, "Deactivate legacy API keys" only stops the legacy keys being used as API keys. Because they are JWTs signed with the legacy JWT secret, they stayed valid as Authorization: Bearer tokens until that secret was revoked through the JWT signing keys migration. Any future leak of a legacy-style JWT needs both steps.

Distributed cells/virgins inherit the wrong mating station

Problem

When a sealed cell or virgin queen is distributed to a beekeeper, the recipient's queen record is stamped with the batch's mating station and eircode (e.g. TBKA Kilcornan / H91RHH4) instead of the destination apiary it was assigned to (AP01 - Colm). An unmated queen has not mated at the batch station — it will mate at its destination.

Root cause

createQueenForRecipient in src/hooks/useGraftDistributions.ts (lines 318–321) always derives mating_station / mated_at_eircode from batch.mating_apiary_* regardless of distribution type. A secondary defect: promote_distributed_queen_on_mating uses COALESCE(mated_at_eircode, mating_location), so the stale batch eircode can never be replaced when mating is later confirmed.

Constraint: get_recipient_apiaries exposes only id + name (no eircode by design), so the destination eircode must be resolved server-side in the SECURITY DEFINER RPC.

Decisions

  • Cell/virgin with a destination apiary → station & mated-at from that apiary.
  • Cell/virgin without a destination apiary → leave station/mated-at blank until mated.
  • Mated-queen distributions → unchanged (genuinely mated at the batch station).
  • Correct the lineage string too (use destination apiary name, not the batch station).

Review

Two SECURITY DEFINER RPCs were updated (via migration) and one client hook (src/hooks/useGraftDistributions.ts) edited. The fix applies only to cell and virgin distributions; mated-queen distributions keep the batch mating station. Type-check is clean for the changed hook (remaining errors are pre-existing test-file noise).

New behaviour: distributing a cell/virgin to an apiary stamps that apiary as the mating station and (server-side) its eircode as “mated at”; the lineage string reflects the destination apiary. With no apiary chosen, both stay blank until mating is confirmed.

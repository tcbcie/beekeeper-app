Batch 20: Shared API Sign-in Check

Status: Done 22/10/2026. Tested by you; committed and pushed. Approved with the helper unit test. This is Phase 2 fix batch 8.

21 API route files each repeat the same 25–35 lines:

  • build a secret-key Supabase client, with a fail-fast environment check;
  • read the Authorization header and verify the token;
  • often, check that the account is active, or that the caller is an admin.

The copies have drifted. There are three wordings for the same 401, and none of them checks that the header really starts with Bearer. The project rules ask for less duplication, but this batch is mainly so the next fix to sign-in happens in one place.

The helper: src/lib/server/api-auth.ts

getServiceSupabase()                       // one secret-key client (moved from the AI tools, which re-export it)
requireUser(request, { requireActive })    // → { user, supabaseAdmin } or { response: 401/403 }
requireAdmin(request)                      // → same, plus role = Admin and active (403 otherwise)

const auth = await requireUser(request, { requireActive: true })
if ('response' in auth) return auth.response
const { user, supabaseAdmin } = auth
  • The token is only accepted as Authorization: Bearer <token>.
  • One British wording: 401 Unauthorised, and 403 Account is not active / Admin access required. No client code reads these strings.
  • requireActive runs the same is_active lookup the routes run today. Routes that already read is_active in a wider profile query (chat, voice notes, invoice email, checkout, scale device lists) keep their query and skip the extra one.

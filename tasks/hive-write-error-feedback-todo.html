Defensive error feedback for hive write handlers

Priority: Low. Currently harmless — the affected controls are owner-gated in the UI and the hives RLS enforces owner-only writes, so these handlers do not silently fail in practice today. This task is a hardening follow-up so they degrade gracefully if those controls are ever surfaced more broadly (e.g. reused in a new view, or RLS/ownership rules change).

Background

The hive create/edit handler (handleSubmit in src/app/dashboard/hives/page.tsx) was hardened to extract a message from non-Error throwables (Supabase returns PostgrestError plain objects), so a failed save always surfaces a toast. Several sibling hive-write handlers still either swallow errors with no user feedback or only console.error.

Sites to harden

File & handlerCurrent behaviour
hives/page.tsx — handleDelete On error it does nothing (no toast); on a 0-row no-op it still calls fetchHives, so a failed/blocked delete looks like success.
hives/[id]/page.tsx — handleDeviceSelect, handleWolfScaleSelect An RLS-filtered UPDATE returns 0 rows with no error, so a blocked scale assignment silently no-ops; a real error path lacks a user-facing toast.

Suggested pattern

Reuse the same defensive extraction added to handleSubmit, and give the user feedback on failure:

const message =
  error instanceof Error
    ? error.message
    : error && typeof error === 'object' && 'message' in error
      ? String((error as { message: unknown }).message)
      : 'An unexpected error occurred.'
toast.error(`<action> failed: ${message}`)

For handleDelete, also confirm a row was actually removed (request { count: 'exact' } or a .select()) before showing success / refreshing, so a no-op blocked delete is not reported as success.

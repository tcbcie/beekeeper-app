Security Batch 7: API Routes (API-02 to API-08)

Status: Done 17/10/2026; tested by you, committed and pushed. Findings: seven Medium API findings from the Phase 1 audit.

Keep out of git until shipped: the repository is public and these holes are open.

What I found

Every route below uses the secret key, so database rules don't apply and each route must do its own checks.

IDProblem
API-02The BEEP and Wolf data routes check that you can access a hive, then use the hive owner's BEEP/Wolf token with whatever device ID you send. They never compare it with the hive's own device. A team member could read any scale in the owner's BEEP/Wolf account, including ones not shared. Team members can also set a shared hive's device ID themselves, so the route fix needs a database guard as well.
API-03The invoice email goes to any address the user types, from info@hivecraic.com, with user-written content (spam and phishing risk). The 25-an-hour limit can be beaten by sending in parallel, because it counts first and only records after sending. If the count fails, the email goes anyway. The seller name has no length cap.
API-04/api/users/list gives every logged-in user the ID and name of every user. It has two callers: the admin transfer screen, and the apiary-owner "Transfer Ownership" picker, which only needs one person.
API-05Registration codes can be guessed without limit, through checkout and through the lookup_registration_code / activate_subscription database functions. A correct free individual code means a free subscription. Error messages tell a typo apart from a real code.
API-06The admin "Export Complete Database" includes every user's password hash, sign-in and recovery tokens, and BEEP/Wolf tokens. It runs with one click, with no password re-entry. If the error path fails, it also returns internal error text.
API-07No rate limits on AI chat, voice transcription (OpenAI, paid per use), news search or geocoding (Google, paid). News and geocoding don't even need a subscription.
API-08Admin actions are only written to console logs. Impersonation isn't recorded in the database, exiting isn't logged at all, and the user is never told.

Plan

A. One shared, race-proof rate limiter (used by B, C and F)

A new table api_rate_events (user, bucket, time; RLS on, no client access) and a function consume_rate_limit(user, bucket, limit, window). It locks per user and bucket, counts, and records in one step, so parallel requests can't slip past. It is called with the secret key only.
src/lib/rate-limit.ts: a short helper the routes call. It fails closed: if the check itself errors, the request is refused with a "try again shortly" message.

B. API-07: limits on paid routes

Chat 30 an hour, 150 a day. Voice transcription 20 an hour, 60 a day. News search and geocoding 60 an hour each. Over the limit returns 429 with a plain message, which the screens already show as an error.

C. API-03: invoice email

The server only sends to the customer's saved email or your own account email (a copy for yourself). The invoice screen shows the recipient as a choice between those two instead of a free text box. If the customer has no email, it says to add one to the customer first.
The 25-an-hour limit moves to the shared limiter and is reserved before sending. The seller name is capped at 100 characters.

D. API-02: scale data

In both data routes: when a hiveId is given (which uses the owner's token), the device or scale ID must match that hive's own beep_device_id / wolf_scale_id, otherwise 403. Without hiveId, the route still uses your own token, so it can only reach your own account; the history charts use this.
Database guard: only the hive's owner can change its scale columns (beep_device_*, wolf_scale_*). Team members can't point a shared hive at a different device.
Return a generic error instead of passing on raw BEEP/Wolf error text.

E. API-04 and API-05

API-04: /api/users/list becomes admin-only. The apiary owner's "Transfer Ownership" changes from a list of all users to "enter the new owner's email", checked against the existing exact-match lookup, before the same transfer function runs.
API-05: lookup_registration_code, activate_subscription and checkout share a limit of 10 code attempts per user per hour. Checkout uses one message for "no such code / wrong kind of code / not linked".

F. API-06 and API-08: admin export and audit trail

New admin_audit_log table: append-only, and readable by admins only. Each row records who did what to whom, and when.
Logged from the server routes: impersonation start, impersonation exit (through a new small call when the banner's Exit is used), role change, database export, and viewing a user's apiaries.
Logged by database triggers, so nothing can bypass them: an admin changing another user's account status, deletion, restore, subscription expiry or role (on profiles), hard deletes, and apiary ownership transfers.
The user gets an email when an admin starts impersonating them: "An administrator signed in to your account on … to help with support".
Export: password hashes, sign-in and recovery tokens, and BEEP/Wolf tokens are left out by default. An "include sign-in secrets (needed for a full restore)" tick box puts them back. Any full export requires you to re-enter your password, which the server checks. The error response no longer includes internal details.

G. Verify and close

Database changes through MCP, with rolled-back tests (limiter under parallel load; scale-column guard; audit triggers; code-attempt limit). Then the security advisors.
Type-check, lint, qa-engineer review, docs (BEEP, Wolf, CRM, ownership transfer, impersonation, export) and the findings register.

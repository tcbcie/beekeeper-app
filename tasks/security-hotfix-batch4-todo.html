Security Batch 4: Cross-Account Holes in the Sharing Rules

Status: Database applied and verified on 17/10/2026; the app changes are waiting for your test and deploy. D9 and D10 were both accepted. Found: Phase 1A database audit, 17/10/2026. I checked each one myself against the live policies.

Committed 17/10/2026, once every hole below was closed in the live database. Until then the file stayed out of git, because the repository is public.

The common root cause

Several access rules check that a row belongs to the person saving it, but not the other IDs on the row. Those other IDs then unlock access elsewhere:

  • who is being added as a member;
  • which apiary is the mating apiary;
  • who the recipient is.

Other users' IDs are easy to get from the app's own search and recipient lookups.

IDHoleWhat an attacker (any logged-in user) gets
Critical DB-01A team or group owner can add any user as a member, without consent. For existing users, the app does this by design ("added directly").Create a rearing group, add the victim, then read the victim's whole queen-rearing record (all batches, grafts, distributions including recipients' contact details) and the victim's profile (email, mobile, address).
Critical DB-02A batch's mating_apiary_id is never checked, yet it grants group members access to that apiary.Point a batch in your own group at the victim's apiary, then read and edit or delete the victim's hives there, and see the apiary's exact location.
Critical DB-03A distribution's recipient columns are never checked, yet they unlock the recipient's apiary and profile.Create a distribution "to" the victim, then read their apiary's location and their profile contact details, and place queens into their hives.
High DB-05Support-ticket and treatment-product admin rights trust a role in the old del_user_profiles table, which users can write themselves.Make yourself "Admin" there, then read, edit or delete every support ticket and rewrite the global treatment product list.
High API-01The nightly photo clean-up checks references by exact URL text, but deletes by the parsed file path. The parser drops ?…, decodes %xx and resolves ../.Put the victim's photo URL with ?x=1 added into one of your own records, then remove it. A week later the clean-up deletes the victim's photo. File names can be listed from the public buckets.
High DB-06Four database views bypass access rules. One of them (shared_gdd_records_community) is readable without logging in.Anyone on the internet can read exact apiary coordinates for every shared GDD record, including 46 apiaries that did not opt in to location sharing. The "obfuscated" maps can be reversed to about 1 km.

Decisions needed

#QuestionRecommendation
D9Team and group invitations for existing users: keep "added directly", or require them to accept?Require acceptance. Existing users get a pending invitation, shown in-app and by email, and accept it with one tap. Without consent there is no way to stop DB-01. New users keep the automatic add on sign-up, because signing up from the invitation is the consent.
D10Distributions to people outside your groups and teams (at least 5 of 20 today): what may the distributor see about that recipient?Their name and apiary name only (served by a narrow lookup), until the recipient shares a group or team with you. Full details, meaning email, apiary location and Eircode, stay available for co-members, who are now consenting because of D9. Queens are placed into a recipient's hive only for co-members or yourself; for anyone else they're created unplaced in the recipient's account.

Plan (minimal, database-first)

A. No decision needed: I can start straight away

DB-02: rearing_batches insert and update must check two things. First, mating_apiary_id must be an apiary the batch owner can access directly (owned or team-shared). Second, rearing_group_id must be a group the owner owns or belongs to. Then check the 6 existing batches whose mating apiary is owned by neither the batch owner nor the group owner, to confirm they're legitimate team-shared apiaries before the rule goes live.
DB-03 (integrity): a distribution's recipient apiary and hive must belong to the recipient (today 0 rows break this).
DB-05: switch the support-ticket and treatment-product admin rules to is_current_user_admin(). Stop users writing to del_user_profiles; check first that nothing in the app writes to it.
DB-06: set the 4 views to respect access rules (security_invoker), or revoke anonymous access. Return coordinates only where the apiary owner chose to share their location, and only obfuscated. Seed the obfuscation so it can't be reversed. Check that the community map and the GDD pages still work.
API-01: in src/app/api/cron/storage-cleanup/route.ts, delete a queued file only if its URL is exactly the canonical public URL of the path it resolves to. Anything else (query string, fragment, encoded or ../ variants) is dropped from the queue without deleting. That's one comparison, using a small helper in src/lib/storage-url.ts.

B. After D9

DB-01: members can only be added through new accept_team_invitation and accept_rearing_group_invitation RPCs. These check that the invitation is pending, unexpired and sent to the caller's email. Owners can still add themselves, and the sign-up trigger is unchanged.
App changes:
  • The team and rearing-group pages create a pending invitation for existing users and send the email.
  • The two accept pages call the RPCs. This also fixes their current self-insert, which the database would refuse.
  • Show pending invitations in-app (check what already exists first).
Close the side door: members can't change their own group_id or role (DB-09).

C. After D10

DB-03 (exposure): remove the distribution branches from the apiaries and profiles access rules. Add a lookup that returns recipient details for the caller's own distributions: full details for co-members and yourself, name and apiary name for everyone else. Then update the 4 places that read them (useGraftDistributions, useQueenTracker, useReportsData, the CRM order page).
create_queen_for_distribution: place queens into a recipient's hive only for yourself or a co-member.

D. Verify and close

For each hole, a rolled-back SQL test that runs as a test user (inside a transaction that is always rolled back, so no data changes) and shows the attack is refused while the normal flow still works. Then run the advisors and the qa-engineer review.
You test: inviting an existing user, accepting, the rearing-group report, the queen tracker, distributions (to a member and to an outsider), the community map and the GDD pages.
Docs (feature docs for teams, rearing groups and distributions; findings register), memory note, commit.
Not in this batch: the Medium and Low database findings (DB-04, DB-07 to DB-18) go into the findings register and later batches. One exception: DB-09 is included above because it's a one-line guard on the same table.

WP01 – Establish the behavioural baseline

Plan: docs/features/mobile-first-implementation-plan.html (WP01 and its two refinements). Evidence: docs/reviews/mobile-first-findings-verification-2026-11-04.md.

WP01 changes no app code. Its output is a scenario matrix that gates the behaviour fixes in WP02–WP07. Each scenario is recorded as passes, fails, code-established (the code makes the outcome certain, but it was not run) or untested.

How the scenarios are run

  • From the code – everything the verification already settled, with file:line evidence. No session needed.
  • In Chrome, on a disposable account – the browser on a desktop window and at phone widths (320/390 px): create versus edit, dirty exits, Start again, step ticks, keyboard focus, hive context, dashboard two taps. Never on your real account.
  • On your phones – a short checklist for you: iOS swipe Back, Android double Back, offline save in flight mode, enlarged text, installed app.
  • Not run – failure injection (lost response after a failed queue write, full storage, a crash between steps). Doing this safely needs a test harness or a database branch. These stay "code-established", as the plan allows.

Owner decisions – accepted 04/11/2026

  1. Winter label (WP03). Change it to "Winter: just check food". In winter the only rows the card can show are food checks: Heft, and Record feed when a scale hive loses weight. So this label is always true, and "nothing to do" never contradicts the rows below. Update dashboard-today-screen.md to match.
  2. "Need inspection" in winter (WP09). Yes, switch it off from November to February, like the dashboard. Counting every hive as overdue in winter nudges people to open hives in the cold, which is poor practice. Use the same rule as the dashboard (more than 14 days, on local dates), so the two screens agree, and fix the UTC day count at the same time.
  3. Super fullness carry-forward (WP04). No. Each visit should start with "not recorded", with last visit's reading shown beside it as a hint ("Last time 60%, 12 Oct"). Otherwise an untouched form re-saves old readings as new observations. The same principle suggests the stores dial should stop seeding 50. That is noted for WP04/WP09 but not decided here.
  4. Remembered hive from Hives (WP07). No. When started from Hives, pass the apiary being viewed and leave the hive for the beekeeper to choose. The remembered hive still applies when starting from Records. This matches the plan's rule of "never silently choosing a hive".

Review

Code pass and Chrome runs done. Phone checklist is with you. Results are in docs/features/mobile-first-wp01-baseline.md.

  • 11 scenarios run in Chrome on the demo account at desktop width. Every one behaved as the code predicted.
  • Confirmed defects: Home leaves an open inspection without asking (new and edit), and the last typing before leaving is lost; Start again deletes the draft with no question; the hive is not shown on later steps; edit mode says "Nothing has been recorded yet."; Next and Save are the same colour; Shift+Tab can escape a dialog.
  • Confirmed working: Close and sidebar links ask before discarding; ticks mean "visited"; on a desktop, New inspection opens directly.
  • Phone widths could not be reached (the window would not narrow, and the site rightly refuses to be framed), so S03, S23 and S30 joined the phone checklist.
  • Not run: failure injection and the two-tab edit, which would need a test harness or saved edits. They stay code-established.
  • Clean-up checked in the database: no new demo records, and the edited inspection is unchanged.
  • No app code changed, so no QA audit applies.

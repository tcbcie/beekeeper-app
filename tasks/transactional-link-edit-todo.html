Transactional Link Editing (audit MEDIUM 1)

Problem

Editing a batch or a bulk container replaced its junction rows with a delete-then-insert across two separate Supabase calls. If the re-insert failed after the delete succeeded, the record was left with zero links (data loss), with only a toast shown.

Fix

Two plpgsql RPCs perform delete + insert inside a single (atomic) function body:

  • replace_batch_links(p_batch_id, p_container_ids uuid[], p_jars jsonb) — replaces batch_containers and batch_jars together.
  • replace_container_harvests(p_container_id, p_harvest_ids uuid[]) — replaces container_harvests.

Both are SECURITY DEFINER with an explicit auth.uid() ownership check, and EXECUTE is granted to authenticated only (revoked from anon/public — flagged by the Supabase linter and fixed).

Used by both create and edit. On create the delete is a no-op, so the container and jar writes also become atomic as a bonus. The parent batch_runs/bulk_containers UPDATE/INSERT remains a single prior statement (atomic on its own); only the multi-step link replacement needed wrapping.

Tasks

1. Create replace_batch_links RPC (transactional)
2. Create replace_container_harvests RPC (transactional)
3. Lock EXECUTE to authenticated (linter fix)
4. Route batch create + edit through replace_batch_links
5. Route container edit through replace_container_harvests
6. Update feature documentation
7. User verifies build & tests

Review

  • 4 migrations: two function definitions + one grant lockdown migration.
  • Client: removed the separate delete/insert blocks in handleBatchSubmit and handleContainerSubmit, replaced with one supabase.rpc(...) call each. Net reduction in client code.
  • Container multi-bucket create left unchanged (single bulk insert, no delete-then-insert, so not the flagged risk).
  • Security: ownership enforced inside the definer functions; anon callers get "Not authorised" (and now cannot EXECUTE at all).

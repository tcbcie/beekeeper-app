Batch 26: Lineage, Invitations and Dashboard Dates

Status: Implemented 23/10/2026, waiting for your test. This is Phase 2 fix batch 13. Three agents explored the code, and every fact below was checked against the live database: no lineage cycles exist today, there are no duplicate invitations, and the dashboard function is identical to the repo copy.

A. Queen lineage cycles (C6-08)

How it goes wrong today, when editing queen M:

Mother picker offers "Queen 26 (mated)" ← reared from M's own graft, never filtered Save → RPC creates register record D with mother = M → cycle check runs now, but D isn't in the page's list, so it passes → M.mother = D ⇒ M → D → M (a daughter as her own mother's mother)
Also found: the queen form never shows a failed save. Supabase returns errors as plain objects, and the form only reports real Error objects. A duplicate queen number or a database refusal just does nothing. The same happens in two admin drop-down forms.
Database guard (essential): a check that a queen can't be her own parent, plus a trigger. When mother or father changes, the trigger walks up the family tree and refuses the change if the queen is already among her new parent's ancestors. The message reads: "Queen 12 can't have one of her own descendants as a parent." It also covers other users' queens and anything the page didn't load. It's saved as a migration file and applied through MCP. Execution is revoked from app users (it runs as a trigger only), and I'll run the advisors afterwards.
Form: the cycle check runs before the reared queen is added to the register, so a refused save leaves no stray record. Reared candidates from this queen's own line are hidden from the mother picker; each candidate now carries its would-be mother, the same rule the database function uses.
Errors shown: the queen form and the two drop-down forms show the real message (or a plain fallback) for any failed save.

B. Invitations

Both invitation tables already have a unique rule on (team or group, email, status), so exact duplicate pending invitations can't happen. But the rule is wrong in two ways:

  • It blocks re-joining: it allows only one "accepted" row per email. If someone who left a group is invited again, accepting fails, because their old accepted row is still there. 3 former rearing-group members are in that position today.
  • It's case-sensitive: Anne@x.ie and anne@x.ie count as different people. The app lower-cases emails, but the database doesn't enforce it.
Database: the old three-column rule is replaced with "one pending invitation per team (or group) and email, ignoring case". Accepted and declined history no longer blocks anything. No existing rows conflict (checked).
Pages (apiary team and rearing team): the "already invited" check reads a list instead of expecting exactly one row, which silently failed when two rows matched. If the database refuses a duplicate, the page shows "An invitation has already been sent to this email." instead of a generic error. The rearing-team page now checks the delete of a declined invitation, as the apiary-team page already does.

C. Dashboard dates (UTC)

The dashboard database function used the database's UTC date. Between midnight and 1 am Irish summer time, "tasks due today" counted yesterday's tasks, and the windows (inspections in 7 days, hives not inspected in 14, varroa in 30, queen checks in 21, queens over 2 years) were a day out. Fix: one line works out today in Europe/Dublin, used everywhere in the function. The function's name and inputs are unchanged, so the app and its permissions need no changes. The function still refuses anyone but the signed-in user.

Not changed (noted)

  • Other date fallbacks: a few database functions fill in a date when the app sends none (order date, paid date, colony movement). They should use the Irish date the next time they're changed. The reminder e-mail function has a similar UTC date issue; that's server-side and separate.
  • Expired invitations still count as pending, as now. The owner cancels and re-invites.

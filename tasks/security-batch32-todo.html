Batch 32: Exports and Saves

Status: Implemented 23/10/2026, waiting for your test. This is Phase 2 fix batch 19 and the first batch of Medium findings. It covers the last open High finding (C9a-02, the personal data export), the spreadsheet exports, and record edits and deletes that report success when nothing changed. Three agents checked each finding against the code and the live database.

A. Personal data export (Settings → Export): C9a-02

The non-admin "Export my data" SQL file currently reads all 72 tables with no owner filter. RLS decides what comes back, so the file contains:

  • reference data every user can see, such as the knowledge base, news, dropdowns and associations;
  • other people's rows: team-mates' hives and records, shared GDD records, all conservation areas, and wild colonies for power users.

Your own profile row is always missing, because select('*') on profiles is refused by the column grants. A failed table only shows up as a comment at the bottom of the file, under a "success" message. The 1,000-row cut-off was already fixed in batch 25.

Read only the user's own tables: the same USER_EXPORT_TABLES list the Profile page export uses, each filtered on user_id.
Add the user's own profile row, read with PROFILE_COLUMNS, the column list the app is allowed to select.
If a table fails, stop and show an error, as the Profile page export already does, instead of downloading an incomplete file marked "success".
Remove the file header line saying "visibility depends on your row-level security permissions".
The admin "complete" export runs on the server and is unchanged. Some owned tables have no user_id column, for example jar batch containers and teams you own. These are missing from both personal exports today; that's a separate, small gap and is noted for later.

B. Spreadsheet (CSV) exports: C9a-19, C8a-11, C8a-12 and the Chunk 6 CSV item

There are six CSV exports. The two CRM ones (orders and customers) already use the safe shared helper in src/lib/csv.ts. It neutralises formulas, quotes cells properly and adds the marker Excel needs for é and £. The other four have their own code, with no formula guard and no Excel marker:

  • Queens list: it includes team-mates' queens, so a team-mate's performance notes could hold a formula that runs when you open the file in Excel. This is the realistic risk.
  • Reports: all 7, plus the nuc reports. They share one function.
  • Profit & Loss.
  • Profile page "Export as CSV" backup: its quoting is broken. A note with a quote mark or line break splits the row, and lists shift every column after them.
Fix the shared helper first. Real numbers and numeric text such as -8.12 are left alone. Today a negative number would be prefixed with ', which turns Irish longitudes and sub-zero temperatures into text. Lists and objects are written as JSON, and dates as ISO dates.
Switch the four writers to the helper: the report function (which fixes all 9 report buttons at once), Profit & Loss, the queens list and the Profile CSV backup. The column headers stay the same, except "Marking Color" becomes "Marking Colour".
The app never reads these CSV files back in, so the change can't break anything. Text cells that start with =, +, - or @, such as a phone number +353…, show a leading ' in some spreadsheet apps. That's the standard safeguard, and the CRM exports already do it.

C. Record edits and deletes that "work" but don't: C4-07

A team-mate can see every record on a shared hive, but the database only lets the beekeeper who recorded it change or delete it. The record cards still offer Edit and Delete to everyone, and the database reports no error when it changes nothing. So these seven actions say "saved" or "deleted" while nothing changes:

  • edit or delete a feeding;
  • edit or delete a harvest;
  • edit or delete a varroa check;
  • delete a treatment.

The varroa check edit also keeps a newly uploaded photo that no record uses.

Each of the 7 actions asks the database which rows changed. When none did, it shows "Only the beekeeper who recorded this … can change it", and the varroa check edit removes the unused photo. This is the same pattern the inspection and treatment edits already use.
The five record cards show Edit and Delete only on your own records. Team-mates' records stay visible, with "Recorded by", but read-only.
In the same save handlers, show the real database message instead of "Unknown error". Supabase errors aren't Error objects.

D. Checked, not changed: C3-06 and C9a-11

  • C3-06 (hive edits): anyone who can see a hive can also edit it, so a blocked save can't happen in normal use. The only fix is a wrong code comment in HiveFormSection.tsx, which claims only the owner can edit a hive.
  • C9a-11 (admin screens): these are only blocked if an admin's role is removed while the page is open. I'll mark this low priority and make no change.
